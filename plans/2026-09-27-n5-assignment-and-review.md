## 一、分工原则

沿用 N2–N4 的三条原则：

1. **按「错了会不会静默地错」分配，不按工作量分配。**
2. **延续对上游代码的熟悉度**，减少「按猜测理解接口」的风险。
3. **审查者 ≠ 实现者**，Astra 只读审查、不承担 N5 任何实现。

N5 另加一条：

4. **生产操作的执行者与决定者分开。** 任何 Railway 控制台操作、生产迁移、真实 Key 配置，**决定权始终在用户**；
   实现者只负责把配置、文档与验收脚本准备好，并在每一项执行前提交「做什么、影响什么、如何回滚」的说明。

## 三、执行者之间的交接约定

- **0 → A / B / C**：N4 完成、入口-N5 通过后才开工。D-N5-1 至 D-N5-3 已于 2026-09-28 裁定。
- **D-N5-3 折中（默认不启用）**：用户提出时间节点时，Opus 完成 N4-A 后直接接做 N5-A，此时 A 的入口条件改为
  「N3 验收通过 + N4-A 完成」，其余阶段不变；Astra 批次 1（N5-1、N5-2）随之前移，其他批次不动。
- **A ‖ B 在 `app/main.py` 与中间件上串行**：A 挂 MCP 路由（不挂 `X-Session-Id` 依赖），B 加追踪中间件（不得在鉴权前解析 MCP 正文）。
  先完成的一方在进度快照写明中间件实际顺序，另一方改完后同时跑 A 的鉴权顺序测试与 B 的追踪测试。
- **A、B 在 Alembic 上串行**：`mcp_credentials` 与 `model_price_versions` / `llm_usage` 新列各一份迁移；创建前后确认唯一 head。
- **A、B → C**：A 把凭证 CLI 用法、B 把新增环境变量（三级预算上限、价格版本来源）以要点交给 Sol，
  由 Sol 统一改写 `docs/deployment.md`，不并行编辑同一文件。
- **C 的生产操作流程**（每一项都走一遍，不因「上一项已同意」而跳过）：
  1. Sol 在对话中列出：要做的操作、影响的服务、预期结果、失败时如何回滚；
  2. 用户明确同意（或选择亲自执行）；
  3. 执行后把命令、时间、结果写进 `docs/history/deploy-preflight-<date>.md`；
  4. 若结果不符合预期，**停下报告**，不自行尝试第二种做法。
- **C → D**：部署完成、三项前置条件验收记录齐备后，D 才开始 Task 3（性能基准）与 Task 7（演示）。
  D 的 Task 1、2、5、6、9 可以更早在本地开始，但矩阵里依赖部署的格子保持「未执行」。
- **Sonnet（D Task 1–6）→ Opus（D Task 7–9）**：Sonnet 交付验收矩阵与评测报告后，Opus 据此写演示脚本与收口快照；
  **收口快照中的每一个「通过」都必须能在矩阵里找到对应证据行**。
- 任一执行者发现上游实际接口与计划不一致：停下，按 PRD → 契约 → 计划 → 索引修正，不在自己的实现里吸收差异。

| **批次 5** | D Task 1、2、4 完成后、最终快照之前 | **N5-5** | 在「宣称完成」之前最后一次核对证据链 |

按当前分工，**Astra 共需 6 次审查会话**（与 N2–N4 持平）。批次 2、4 都属于 N5-3，但**不建议合并**：
批次 2 审的是代码，批次 4 审的是公网实测记录，两者之间隔着一次生产部署。

### 审查流程

沿用 N2 的四步流程（清单 §二 规则 1）。差异有一点：**批次 3、4 涉及生产环境，Astra 只读部署配置、脚本与验收记录，
不登录 Railway、不执行任何线上操作**；需要线上证据时，由 Sol 按 §三流程在用户同意后取得并写入记录。
