## 2. 当前能力与主要缺口

| 能力 | 代码与文档核对结果 | 对业务效果的限制 |
| --- | --- | --- |
| Agent 主链路 | `backend/app/agent/graph.py` 定义 12 个节点，包含意图校验、查询、回答、审核和保存 | 主要围绕一次查询组织流程，没有持续经营问题的状态管理 |
| 知识检索 | `backend/app/knowledge/retrieval.py` 按业务域、关键词检索；复合问法有加权排序；文本存在字符预算 | 没有分块语义检索与重排，口语、长文档和跨文档证据组合能力有限 |
| 规则回答 | `graph.py` 的 `_knowledge_answer()` 展示命中文档正文及来源 | 检索后综合归纳、条款级引用和引用核验能力尚未形成 |
| 经营分析输入 | `answer_service.py` 的 `AnswerFacts` 包含问题、指标和查询结果 | 未独立携带业务知识、商家约束和历史行动经验；升级检索后还需打通消费链路 |
| 记忆沉淀 | 最近 80 轮同商家同分类成功问答进入压缩，按商家和分类覆盖一份文本 | 长期事实、短期目标、历史案例没有独立生命周期 |
| 记忆召回 | 团队知识命中后直接返回，未命中才使用商家记忆 | 记忆主要作为知识兜底，难以持续参与个性化建议 |
| 记忆质量 | 历史筛选条件是 `processing_status == SUCCEEDED`；未按反馈或质量状态进一步筛选 | 请求成功不代表内容正确，低质量回答可能进入后续记忆 |
| 记忆失败处理 | 压缩降级后仍调用覆盖写入；后台任务异常记日志 | 有用旧记忆可能被信息较少的兜底替换；任务缺少持久恢复链路 |
| 日报 | 六项固定指标、两条规则建议、请求时幂等物化 | 尚无主动异常发现、诊断案件与持续跟进；当前日报本身并非模型生成 |
| 反馈与 Chat BI | 保存采纳、点赞、点踩，汇总回答指标 | 无法说明建议是否执行、执行质量及经营结果 |

上述结论来自静态检查，未在本轮运行服务或测试。并发记忆覆盖、真实检索效果等问题仍需专项用例验证。

### 2.1 优先解决的产品问题

1. 商家知道数字变化后，仍需自己查明细、找规则、组织处理材料。
2. 建议与历史行动脱节，同一问题可能被反复建议，却无人跟进。
3. 商家个性化约束没有稳定进入建议生成过程。
4. 系统记录了“用户喜欢回答”，但无法判断“业务任务完成了没有”。

## 3. 路线选择与首期交付

| 路线 | 收益 | 局限 |
| --- | --- | --- |
| 先单独升级 RAG | 改善规则检索、引用和回答依据 | 不能单独解决执行与复盘缺口 |
| 先单独升级记忆 | 改善商家偏好适配，减少重复解释 | 没有真实处置记录时，仍可能只是积累更多摘要 |
| 围绕退款场景建设完整链路 | 同时检验诊断、知识、记忆和行动的价值 | 需要限制首期业务范围，避免演变成全能运营平台 |

**建议采用第三条路线的最小版本。** 先验证单条建议的跟进价值，保留现有记忆召回方式。

### 3.1 首期范围建议

- 围绕一个退款异常生成一条有证据的建议，记录人工执行结果并在到期后由用户点击复查。
- 优先复用订单、订单项、商品、退款与工单数据；新增分析维度必须通过白名单工具提供。
- 首期由用户请求或日报页面入口触发；记录复查日期并展示待复查状态，不承诺到期自动运行。
- 行动先采用人工执行和回填，不接自动退款、改价、下架或批量外呼。
- 验证商家身份和真实数据授权是接入真实业务的前置条件；演示 Token 不能直接承担真实生产商家鉴权。

### 3.2 首期不纳入

- 任意 SQL、自由脚本执行、开放式工具调用。
- 全业务域、多 Agent 自由协商或无限自我重试。
- 自动将商家记忆写回团队知识，或用用户反馈自动改线上 Prompt。
- 为技术展示而引入 Doris、独立向量数据库或第二个主数据库。
- 附件、OCR、对象存储的全量建设；这些沿用原计划，只有场景明确依赖时才纳入。
- 向量检索、pgvector、embedding、重排模型；先取得分块关键词基线及具体失败案例。
- 结构化记忆、旧摘要迁移、商家自助记忆入口；不与行动管理一起开工。
- 自动到期复查、持久任务队列、主动通知；手工复查验证价值后单独评估。

## 4. 首期业务闭环与后续方向

```text
经营数据与数据更新时间
  → 异常筛查与去重
  → 创建或更新经营问题
  → 受控查询、分解与证据整理
  → 检索适用规则（维持现行记忆回退边界）
  → 生成一条带证据的处理建议
  → 商家确认行动与观察时间
  → 人工执行、回填结果
  → 到期后由用户触发复查经营数据
  → 保存观察结果并关闭或继续跟进
```

核心持久对象是“经营问题及其行动”，而非一次聊天。一个问题可以跨会话、跨多天推进，并关联原始回答与证据。

### 4.1 示例体验

1. 日报提示某商品退款信号值得检查，并说明比较周期、样本量和数据截至时间。
2. 系统按商品、原因等允许维度排查，展示主要变化及对应明细入口。
3. 检索售后规则和运营 SOP，给出一条建议及待核查对象、处理步骤和证据位置。
4. 商家确认该行动，记录目标对象、计划完成时间和复查时间。
5. 执行后保存回执；到期点击复查，重新查询数据，记录改善、无改善或证据不足。
6. 首期保留行动和观察记录；将案例转成可召回记忆属于后续 E 方向。

“采纳回答”“计划执行”“实际完成”“观察到改善”必须是不同事件。缺少对照证据时，只能报告执行后变化，不能断言由 AI 或某项行动造成。

## 5. 技术整改设计

本节保留技术方向，不作为可直接执行的 B–F 任务清单。§3.1 的首期边界优先；商家约束并行输入、结构化记忆和自动后台任务仅在相应阶段获准后细化。

### 5.1 数据基础与受控诊断

先核实真实数据可得性，再定义异常口径：

- 检查业务时间、同步延迟、退款状态、退款与订单的关联完整率、商品标识和原因枚举。
- 将退款金额、退款笔数、退款率区分；退款率的分子、分母、订单归属期和观察窗口必须在指标口径中明确。
- 退款存在滞后，近期订单不能直接与已完整观察的历史订单比较而不加说明。
- 首期使用可解释的阈值与历史对比，纳入最小样本要求和重复提醒抑制；参数通过基线回放确定，不先拍定业务阈值。
- 诊断计划只能选择已注册的分析动作、允许维度和日期范围。查询、金额、比率和贡献拆解由后端计算。
- 数据支持的现象、可能解释、待验证事项分别输出，不把相关性写成因果。

主图只负责组织调用。异常检测、分析计算、证据打包各自放入专门模块，避免继续把业务逻辑堆进 `graph.py`。

### 5.2 RAG：从关键词匹配升级为可核验的业务证据

**先补内容，再做算法对照。** 当前文档规模较小，优先补齐真实售后条款、运营流程、指标说明和经过审核的案例。

检索链路建议：

```text
文档版本与适用范围校验
  → 按标题、条款和业务步骤分块
  → 分块关键词检索
  → 权限、生效时间和业务域过滤
  → 关键词排序与去重
  → 按预算组织证据
  → 生成回答与逐项引用
  → 引用真实性与适用性校验
```

- 文档与分块保留来源、版本、生效范围、段落定位和内容哈希；原始文档仍是事实来源。
- 团队公共知识与商家私有材料分别限定检索范围。私有检索在召回时就施加商家条件，不能靠模型或结果展示层隔离。
- 规则条款可引用，实时经营数字仍来自受控查询，不能从过期文本或记忆中回答当前金额。
- B 阶段只对比现有关键词基线与分块关键词方案。只有冻结评测集证明分块关键词未达门槛，且失败不是缺少内容、口径错误或前置闸门误拒造成，才提交混合检索评估；是否启用还需验证收益、延迟和资源成本。
- PostgreSQL 加 `pgvector` 是优先评估方案，不是已确定依赖；需核实部署支持、索引维护和中文检索效果。
- embedding 与 reranker 分别评估本地模型的资源、许可、中文效果和延迟；不假设 DeepSeek Chat Completions 提供 embedding。
- 文档新增、更新、归档需要同步索引状态；索引落后时明确显示版本差异或回退可核验的检索路径。
- 检索内容作为不可信资料使用，文档中的指令不能改变工具权限、商家范围或系统规则。
- 评测前置闸门的误拒绝：业务口语若提前被拦下，必须在保持零 LLM 闸门的前提下修正词汇或检索策略。

### 5.3 统一证据输入与回答审核

目前 `AnswerFacts` 只包含问题、指标和查询结果。建议扩展为内部证据包，分开承载：

| 输入 | 可信边界 | 回答约束 |
| --- | --- | --- |
| 查询与后端计算结果 | 受控查询事实 | 数字、范围和口径可追溯 |
| 有效业务条款 | 经维护的知识证据 | 明确适用范围及引用位置 |
| 商家约束与目标 | 同商家且状态有效的记忆 | 影响建议选择，不能改写平台规则 |
| 历史处置案例 | 带结果与适用条件的经验 | 作为参考，不作为当前因果证明 |

Reviewer 除现有数字与结构检查外，增加引用是否存在、规则是否适用、建议是否违反商家约束，以及是否夸大因果的检查。可确定的检查由代码完成，不全部交给第二次模型判断。

规则问答如新增综合生成，必须独立评测；纯明细的空正文不变量与已有回答模式保持有效。

### 5.4 后续 E 方向：拆分记忆用途、建立生命周期

| 类型 | 例子 | 失效或更新方式 |
| --- | --- | --- |
| 长期约束 | 不以降价作为优先方案 | 用户纠正、业务事实变化后替代 |
| 阶段目标 | 本月优先处理某商品退款 | 目标到期或完成 |
| 历史案例 | 某种处理执行后观察到的结果 | 保留发生时间和当时条件，不能当永久规则 |
| 当前任务 | 某项处理等待回执 | 由行动系统管理，记忆只引用其状态 |

候选记录应能追溯商家、类型、来源消息或行动、证据、观察时间、有效期、确认状态、替代关系和版本。这里是概念要求，不是新增 API 精确字段契约。

写入与维护原则：

- 不再将“请求成功”当作事实可信的充分条件；降级回答、被纠正内容和模型推测不得自动晋升为确认事实。
- 用户明确表达的偏好可形成有出处的候选约束；高影响约束需要明确确认。
- 点赞和采纳是参考信号，不能直接证明内容正确或动作有效。
- 按事实合并、去重和替代，保留长期事实，不只反复压缩最近 80 轮。
- 压缩失败保留上一有效版本，并记录候选处理失败；不以低信息兜底覆盖有效记忆。
- 同商家并发更新采用版本检查或任务串行化，避免较早快照覆盖较新结果。
- 提供可审计的纠错、撤销与失效机制；商家侧是否新增管理入口需先修订既有产品裁定。
- 定义会话删除对来源记录、派生记忆、检索索引和翻译缓存的影响；保留策略确定后再上线真实长期记忆。

**需要产品确认的变化：** 当前参考实现及项目约定均为“团队知识优先，未命中才用记忆”。将商家约束作为独立输入与知识同时使用，属于新增行为，不能作为普通重构悄悄修改。团队知识与商家记忆物理分离、商家记忆不自动升级为团队知识的边界继续保留。

### 5.5 经营问题、行动与后续自动调度

以下是概念划分，不预先锁定三张业务表加一张任务表。首期仅持久化问题、单条行动及观察所需信息，正式表数、字段及接口在 A 后确定；后台任务留给自动调度阶段：

- **经营问题：** 异常对象、检测窗口、数据版本、证据、诊断状态及关联会话。
- **行动记录：** 建议来源、处理对象、执行人、截止时间、状态、回执与失败原因。
- **效果观察：** 基线、观察窗口、后续指标、干扰因素和结果判断。
- **后台任务：** 幂等键、输入版本、状态、重试次数、租约和错误类别。

首期状态只覆盖确认、回填、复查、关闭和取消，记录操作者与时间；不因长期设想预建完整状态机。确切状态与失败语义在 D 规格中冻结。

若后续批准自动调度，长期任务不得依赖单次 HTTP 响应后的进程内回调。届时优先评估 PostgreSQL 任务表及独立执行进程，以事务性任务登记防止业务保存成功但任务丢失；达到吞吐需求后再评估 Redis 队列。

恢复设计必须包含：重复投递不重复创建行动、失败有限重试、过期租约恢复、旧版本任务不覆盖新结果、永久失败可见、停机后可恢复。多日任务的权威状态放在数据库，不依赖 LangGraph 内存状态。

### 5.6 反馈改进闭环

建立“反馈 → 问题归类 → 人工核验 → 修正 → 回归评测 → 发布验证”的流程：

- 区分查错数据、口径错误、规则引用不适用、建议不可执行、表达问题和执行后无改善。
- 保存最小必要的证据与版本，避免把完整敏感明细复制进运营日志。
- 确认过的失败案例进入脱敏评测集。

| 运营质量衡量 | `frontend/src/views/OpsDashboardView.vue`、后端 Chat BI 模块 | 任务完成、反馈归因和结果观察指标 |

正式接口变化遵循：PRD → 后端契约 §8 → 前后端计划 → 实现与生成产物 → 测试 → 进度与索引。`generated.ts` 禁止手改；组件只消费领域模型，不直接消费生成类型。

**图节点与对外兼容性：** 当前 `GRAPH_NODES` 的执行通过 `_step()` 形成阶段记录，并进入 SSE `step` 与最终 `thinking_steps`。新增、改名、删除或调整节点顺序必须检查节点标识、事件次序、双语标签、JSON/SSE 一致性和历史重放。若改变对外字段、枚举或语义，按上述契约链同步；仅内部拆分且对外表示不变时，以兼容性回归证明，不机械重生成无变化的 Schema。新节点不自动获得一次额外 LLM 预算。

## 8. 验证方案与验收指标

### 8.1 必须覆盖的反例

| 范围 | 关键反例 |
| --- | --- |
| RAG | 旧条款与新条款冲突；同名不同业务规则；语义接近但不适用；无资料；文档含越权指令 |
| 前置闸门 | 合法业务口语被误拒；英文业务提问；真正范围外问题仍被拦截 |
| 诊断 | 数据过期；零分母；低样本；退款时间滞后；跨周期口径不同；取消订单混入 |
| 记忆 | 低质量输出进入候选；用户纠错；并发覆盖；压缩失败；来源删除；跨商家召回 |
| 行动 | 重复确认；越权读取与更新；旧版本更新；重复执行回执；执行失败后误显示成功 |
| 后台任务 | 重复投递；进程中断；租约过期；任务过时；重试耗尽；预算不足 |
| 结果衡量 | 把采纳当完成；把点赞当准确；把自然波动当行动效果；样本不足仍报告改善 |

### 8.2 指标与判定方式

| 层次 | 指标 | 判定原则 |
| --- | --- | --- |
| 检索 | 标注证据召回率、引用正确率、闸门误拒绝率 | 在同一冻结问题集上比较基线与候选版本 |
| 回答 | 数字与口径正确率、规则适用性、建议可执行性 | 人工核验加确定性检查，Reviewer 通过率不能代替真值 |
| 记忆 | 有效约束命中、过期或错误记忆使用、纠错传播 | 固定案例验证约束生效且事实准确性不下降 |
| 业务 | 排查人工耗时、手动查表次数、行动完成率、到期复盘覆盖率 | 按任务记录，明确统计窗口与分母 |
| 经营 | 同类退款变化、重复问题情况 | 控制样本与周期差异，列明活动、季节性和其他干扰 |
| 工程 | 端到端延迟、单任务调用量、总成本、后台失败率 | 同时计算前台与后台资源，不将异步成本隐藏 |

现有 `user_accuracy_rate` 实际为点赞占有反应反馈的比例，`system_accuracy_rate` 实际为首次审核通过占回答的比例。保留兼容性时先明确展示说明；若更名或改变口径，按契约流程处理。

固定隔离、权限、状态、引用定位与数值反例必须全部通过（执行覆盖率 100%，失败数 0；预期拒绝按对应反例的期望值判断）。数值精度与金额舍入遵循指标口径，不凭页面近似相等放行。

**阈值冻结规则：** A12 取得基线后，在本节补入 B/C/D/F 的数值门槛；E 与自动调度分别在自身候选实现前冻结。每项必须记录评测集版本/哈希、样本数、指标分母、基线值、候选目标、比较规则和冻结日期。召回率同时冻结 top-k 与标注证据粒度；延迟记录环境及统计分位；成本记录单请求次数/token 与前后台总用量。退款最小样本、数据新鲜度和观察窗口同样在 C 实现前冻结。

**当前状态：尚无本轮基线，不填写虚构百分比。** 阈值未填齐不得启动对应候选实现或声称阶段验收通过。冻结评测集与调参样本分离，不用同一批验收结果反向选择门槛；变更语料或门槛须保留旧版本并重新建立对照。收益未达标时报告未达标，不能事后降低目标。

### 8.3 测试执行边界

自动化使用 Fake/mock LLM、可丢弃测试数据和独占测试库。运行前确认测试连接不指向生产；真实 PostgreSQL 全量测试会清理数据，不能在业务库执行。

按阶段选择相关用例，完整集成阶段再执行相应门禁：

```powershell
# 在 backend/；先确认环境仅指向可丢弃测试库
uv run ruff check .
uv run mypy app
uv run pytest

# 仅在独占、可丢弃 PostgreSQL 测试环境已就绪时执行
$env:REQUIRE_INTEGRATION_DB = '1'
uv run pytest
Remove-Item Env:REQUIRE_INTEGRATION_DB

# 在 frontend/
npm run lint
npm run typecheck
npm run test
npm run codegen:check
npm run build
```

新增状态流转和页面交互使用 mock Playwright 场景验证；依赖真实后端的测试须先核对启动钩子、后台任务和费用路径。模型效果验证需要真实调用时，作为独立人工验收，不混入默认测试套件。

### 8.4 评测语料存放与清库恢复

下列为 A12 实施时新增的路径，本次文档修订不创建语料或伪造验收结果：

| 路径 | 内容与恢复用途 |
| --- | --- |
| `backend/tests/fixtures/business_loop/README.md` | 数据来源、脱敏方式、导入次序、完整执行命令、测试库识别与恢复校验步骤 |
| `backend/tests/fixtures/business_loop/manifest.json` | 冻结版本、文件哈希、来源提交、业务时区、固定结束日期、随机种子、商家与业务数据预期数量 |
| `backend/tests/fixtures/business_loop/cases.jsonl` | 用例 ID、商家范围、语言、提问、证据定位及版本、期望数字或拒绝/降级结果；B7 原九题保持单独标识，不替换成更容易通过的问题 |
| `backend/tests/fixtures/business_loop/knowledge/` | 经脱敏且带来源信息的冻结知识副本；实际业务资料只在获准范围内纳入，不直接提交私有原文 |
| `docs/history/business-loop/` | 带执行日期的脱敏基线/评测报告、视觉证据和恢复校验结果；记录代码与语料版本，不保存密钥、完整请求及敏感明细 |

真实 PostgreSQL 全量 pytest 会清空 `knowledge_documents` 和经营数据表。语料的权威副本必须是文件，数据库只是可重建的运行副本。测试与验收最好使用分开的本地库；共用可丢弃库时禁止并行运行，按以下顺序恢复：

1. 核实连接指向独占可丢弃本地库，完成 Alembic 升级；若测试清空了商家身份数据，先按现有演示商家 seed 入口恢复身份。
2. 用 `backend/scripts/import_wiki.py --root <已核实的知识目录>` 恢复知识；导入器要求的目录结构在 README 中记录，并为冻结语料补相应装载步骤。参考目录始终只读；默认不加 `--overwrite`，避免覆盖人工维护内容。
3. 用 `backend/scripts/seed_demo_analytics.py` 恢复经营数据，显式使用 manifest 的天数与结束日期。随机种子沿用 `DEMO_ANALYTICS_SEED_BASE + 商家序号`，记录其值，不能随执行当天漂移。
4. 装载冻结用例需要的规则版本及特殊反例数据；核对商家、文档数量/哈希、经营数据日期范围和抽样聚合值，任一不符则停止评测。
5. 运行离线基线；真实模型评测只在 R3 授权后执行。再次跑清库测试后重复恢复，不沿用已失效的验收数据状态。

验收要求：从空本地测试库重复恢复两次，manifest 的数量、哈希与指定聚合值完全一致；README 不依赖某个仍存活的数据卷。导入和 seed 只用于可丢弃本地数据，不作为生产恢复工具。

## 9. 本方案的安全与预算落点

通用授权、密钥与参考目录规则直接遵循 `AGENTS.md`，本节只列新增链路需要落实的约束。

- 模型只输出结构化意图和受控行动建议，SQL 与业务数字计算继续由后端负责。
- 查询、证据、经营问题、行动、记忆、任务、导出与本地化缓存均按可信身份隔离。
- 降级继续使用现有 `analysis_sources`、`thinking_steps`、`quality_status`、`quality_notes`、`degraded`、`degraded_reason` 语义；新字段须先修改契约。
- 后台能力增加的 LLM 调用不能绕开每日预算；节点增加不得默认为提高现有单请求上限。
- 默认 `MAX_LLM_CALLS_PER_REQUEST=10`，当前最坏路径也为 10 次。沿用既有 D4 的优先顺序：确定性计算、重排或合并调用 → 评估减少重试的质量损失 → 确有必要才提出提高上限。提高前同时评估单请求 token、每日预算与最坏费用；后台记忆、本地化、复查不能借异步路径隐藏成本。
- 每个需要真实模型验证的任务单独列明 DeepSeek 接口、`deepseek-v4-flash`、预计调用次数/上限与费用；实际授权和范围沿用按 R3 执行，批准预算原则不等于批准调用。
- 首期不执行外部业务写操作；未来接入时需独立设计预览、授权、幂等、审计与失败补偿。

## 10. 上线与回退建议

1. 先用离线回放评测诊断和检索，再做限定范围演示；真实影子运行如会调用模型或访问生产，同样需要相应授权。
2. 新检索、新记忆读取和新诊断能力分别可控；任一模块关闭后保留既有安全查询与历史记录。
3. 首期手工复查只依赖已保存的业务状态；回退新能力时保留已确认行动、回执和审计记录。后续引入自动调度时，还需停止新任务领取并处理在途任务，不能仅关闭页面入口。
4. 持久化变更执行下述数据库回退要求；新记忆质量未验证前保留旧摘要。
5. 闭环试点通过后再扩大商家与业务域；主动通知和自动业务动作分别立项。

### 数据库迁移与回退要求

- 问题、行动、观察及后续任务/记忆/索引的持久化变化均通过 Alembic；概念数量不等于表数，不手工建表绕过迁移。迁移优先新增表或兼容列，保留旧代码所需结构。
- 实施时记录当前 revision、目标 revision、依赖关系、旧代码兼容性与数据回填范围。在空库与含旧版样本数据的本地副本上分别执行 `upgrade head`、`alembic check`，核对约束、商家隔离、行数与内容；不能只证明空库能建表。
- 优先采用应用回退并保留兼容的新结构。需要 `downgrade` 时先识别是否删除行动、回执、审计或记忆数据；破坏性 downgrade 不作为默认回退，使用经验证的兼容修复迁移或获准备份恢复方案。
- 需验证“升级 → 写入新业务记录 → 切回旧应用 → 再启用新应用”后旧功能可用、新记录仍在、状态不失真。后续记忆迁移单独演练旧摘要保护、来源与翻译缓存一致性；自动调度另验重复投递、租约恢复和旧任务不覆盖新结果。
- 本机已知的 `alembic_version` 引用已删除迁移号问题，仅在确认是一次性测试卷后重建。先核实 Docker 项目、容器、挂载卷和目标数据库，不在计划中提供可被误用的无条件删卷命令；重建后按 §8.4 恢复。生产库不得靠删卷、清版本表或随意 `stamp head` 处理版本不一致。
- 发布前在获准环境验证备份可恢复，记录恢复边界与停机需求。回退验收必须给出实际执行证据；仅写“有能力开关”不构成数据库回退方案。
