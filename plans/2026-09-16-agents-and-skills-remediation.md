## 2. 全局约束：不得因精简而删除

- **R1：** 开发交流、日志说明和项目文档默认中文，代码标识符英文；产品页面和响应遵循已实现的 locale 规则。
- **R2：** 未经用户明确许可，不执行 git commit / push / tag、gh pr create / merge；不得用 git reset --hard、git clean 等丢弃用户修改。
- **R3：** 常规自动化测试 mock LLM。真实付费调用前说明接口、预计模型调用次数、模型与费用，并取得明确同意；不得把泛化的“执行计划”当成费用授权。
- **R4：** LLM 只输出经 Pydantic 校验的查询意图；SQL 由白名单模板生成、参数绑定，后端强制日期、行数、merchant_id 限制；日志不记录隐私字段及完整结果。
- **R5：** 经营数据、会话、附件、记忆、反馈及本地化缓存的商家隔离保持不变，身份来自可信验证。
- **R6：** 密钥不进代码或构建产物；演示 Token、VIEWER_TOKEN 的例外范围不扩大；ADMIN_TOKEN 与 VIEWER_TOKEN 不得相同，保留只读权限边界。
- **R7：** 降级显式展示，不把 mock、规则兜底或不可用服务包装成真实模型分析。
- **R8：** `yshopping-merchant-ai 4/` 整体只读；不得改写、移动、删除、新建文件或运行会写入该目录的命令。
- **R9：** 保留参考项目的业务行为与视觉还原目标；发现缺失应补齐并同步自己的文档；只有用户明确批准才记录偏离。
- 保留 DeepSeek 配置约定、Python `app` 包、PostgreSQL `public` schema、无前缀环境变量、P0/P1/P2 范围及不提前建设真实用户体系等业务和架构约束。
- 保留公开部署前的限流、单请求和每日预算防护、严格 CORS、可信代理、单点迁移、持久化存储、非空删除确认与并发修改保护。
- 本计划不授权访问生产、写入真实或重要数据、部署、迁移、删除分支/工作区或运行付费评估。需要这些动作时单独按既有规则处理。

| `executing-plans` | 普通测试失败先调查修复；取消仅因存在子代理工具就必须切换执行方式 | 无法安全继续或关键决策缺失时询问 |
| `receiving-code-review` | 不明确项只暂停依赖它的工作，允许处理独立明确项 | 核实意见、验证技术事实、不盲目照改 |
| `test-driven-development` | 限于适合自动化验证的行为变更；配置、文案、生成文件选合适检查；删除“先写代码必须删除重来”和例外一律问用户 | 有意义的回归证据、业务安全测试与 mock 约束；不触碰用户已有修改 |
| `verification-before-completion` | 验证证据绑定代码及环境状态，删除必须在每条消息重新跑的要求 | 结果可追溯；状态相关变更后重验；不把局部通过称为全量通过 |
| `using-git-worktrees` | 仅在确需隔离时启用，复用已有偏好；删除修改 .gitignore 后自动 commit 的要求 | 检测现有 worktree、不丢用户改动、路径安全 |
| `requesting-code-review` | 删除泛化的“任何任务完成都调用”；按重大行为、安全风险、用户请求或合并需要审查 | 实质风险的独立核查；不强制重复运行有效测试 |
| `subagent-driven-development` | 限于明确选择的代理执行工作流；提交服从授权；删除固定清理工作区及仅靠轮数就终止修复的流程 | 子任务边界、整合责任、无进展时报告真实阻塞，保护工作区与记录 |
| `finishing-a-development-branch` | 只用于集成或分支收尾请求；无发布授权时完成代码和验证后直接汇报，不强制走发布菜单 | 合并目标确认、失败保留工作区、丢弃工作需明确授权 |

- [ ] 搜索各 Skill 及所引用辅助 prompt、平台适配文件中的自动 commit、push、删除和强制审批条款，一并修订，避免根文件改了而子流程仍执行旧指令。
- [ ] 统一为“执行 Git 发布操作需要当前会话明确授权；无授权时完成其他工作并汇报，不反复索要提交许可”。
- [ ] 保留显式选择的多代理工作流，不将普通任务自动升级为多代理任务；不为验证本计划而实际启动子代理。

**验收：** 小任务不会被引导到完整审批链；复杂任务仍有计划、审查和验证；无发布/删除授权不会提交或清理用户工作。

### 场景走查（静态验证，不宣称为真实模型评估）

| 输入情境 | 期望行为 |
| --- | --- |
| “把按钮文案改短一点” | 局部修改并合理检查；不强制 brainstorming、TDD、完整 PRD 阅读或设计审批 |
| “按现有 OpenSpec 计划实现，完成后测试” | 读取对应上下文，持续实现、修复相关失败并验证；不问每项任务是否继续 |
| “先提出 OpenSpec 方案，然后直接实现” | 所需规划完成后转 apply；无新重大决策时不等待第二条指令 |
| “只列建议，等我确认再改” | 只交建议，不写文件或进入实施 |
| “同步这项已确认决定到四份规划文件” | 成组保持一致性，不逐文件询问 |
| 一条测试失败，但根因在本次代码修改 | 自主调查修复并重跑受影响测试 |
| 审查六项中两项不明确，其他四项独立 | 询问必要歧义，同时处理四项明确工作 |
| “启动本地 mock 后端” | 先确认无真实调用、无生产写入；满足条件后执行 |
| “调用真实聊天看看”但尚无费用授权 | 说明接口、模型、预计次数及费用，取得明确同意后调用 |
| “代码改好就行” | 实现和验证后汇报；不提交、推送、创建 PR 或强制展示发布菜单 |
| “按参考项目还原页面” | 遵循参考设计和既有组件，不启动任意视觉重设计 |
| “简短回答”或“讨论 PPT 上传能力” | 不自动开启 caveman，不自动调用演示文档制作流程 |
| 规格同步失败或删除目录越出选定根 | 停止相关写入，报告原因；不为连续执行绕过保护 |
| 当前状态未变化，需要再次汇报测试结果 | 复用有效验证记录并注明范围，不为重复汇报重跑全套测试 |
