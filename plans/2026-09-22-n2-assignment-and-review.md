## 一、分工原则

1. **按「错了会不会静默地错」分配，而不是按工作量。** 高风险模块（A、B、C）给最熟悉对应层的模型，并由 Astra 必审；
   套路固定的模块（D、E、F）由实现模型自检，Astra 只在里程碑末抽审。
2. **延续 N1 的熟悉度。** Opus 实现了 N1-D（会话身份、统一 403、`require_owned()`），Sol 实现了 N1-C
   （库存三元组、事件账本、幂等表、迁移链），Sonnet 实现了 N1-B 与 N1-E（LLM 适配、评测骨架）。
   N2 让同一个模型继续使用自己建的地基，减少「按猜测理解上游接口」的风险。
3. **审查者 ≠ 实现者**（Astra 清单 §二 规则 2）。Astra 不承担 N2 的任何实现，所以 Astra 可以审全部必审项。
4. **Astra 额度有限**：必审项按批次合并成少数几次审查会话（见 §四），不逐任务单独开会话。

批次 3 与批次 4 的先后取决于 B、C 谁先完成，互不依赖。按当前分工，**Astra 共需 6 次审查会话**
（批次 0 可能因 N1 待审项较多拆成 2 次）。

### 审查流程

1. 实现者完成某 Task 且该 Task 验证全绿后，**不勾选**必审项对应的复选框，把范围（文件、测试命令、实测输出）交给 Astra；
2. Astra 只读审查，按 Astra 清单 §九 模板输出结论（通过 / 有条件通过 / 不通过）；
3. 「不通过」或「有条件通过」：由**原实现者**修复，修复后 Astra 复审同一审查项，直到通过；
4. 通过后实现者勾选复选框，结论写入该 Task 的执行记录或 `docs/project-progress.md` 验证结果，
   Astra 清单只更新 §三 的状态列；
5. 审查同样受 R2、R3 约束：不执行 Git 发布操作，不运行任何真实 LLM 调用。

### 额度不足时的后备

Astra 额度耗尽时，必审项改由非实现者的强模型审查，并在结论里注明「后备审查」：

| 审查项 | 实现者 | 后备审查者 |
| --- | --- | --- |
| N2-1、N2-2、N2-3、N2-4 | Opus | Sol |
| N2-5、N2-6 | Sol | Opus |
| N2-7 | Opus、Sol | 避开被审部分的实现者；A、C 部分由 Sol 审，B 部分由 Opus 审 |
| N2-8 | Sonnet（E）、Terra（F） | Opus 或 Sol |

后备审查不降低证据要求；Astra 恢复额度后，**N2-3、N2-4**（模型自批与审批证据）仍建议由 Astra 补审一次。
