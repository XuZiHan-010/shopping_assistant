## 一、分工原则

沿用 N2 定下的三条原则，本次不再重复论证：

1. **按「错了会不会静默地错」分配，不按工作量分配。**
2. **延续对上游代码的熟悉度**，减少「按猜测理解接口」的风险。
3. **审查者 ≠ 实现者**，Astra 只读审查、不承担 N3 任何实现。

N3 的延续关系比 N2 更直接：三个阶段都**直接建在** N2 某个模块之上，不是新领域，
所以「谁最熟悉这份地基」这条直接决定分工，具体见下表「理由」列。

## 三、执行者之间的交接约定

- **A → B / C 交接**：A Task 1–6（Skill 加载器 + 草稿按种类分派 + 工具循环接入）全部完成并通过 N3-1 审查后，
  B、C 才能注册各自的新草稿种类（`AFTER_SALE_DECISION`、`CONTENT_CHANGE`、`PRICE_CHANGE`、`COUPON`）与 Skill 正文；
  提前注册会撞上 A 还在改的分派表接口。
- **B ‖ C 并行**：按模块路线图 §三，C 的 Task 0、1、4、5、6（业绩洞察、定价促销、导出、口径问答）不依赖 B，
  可与 B 同时开工；C 的 Task 2（完整简报）、Task 3 步骤 3（S2 场景）、Task 7（内容缺口信号）需要 B Task 11
  （顾客信号服务）先落地，属于任务级依赖，不阻塞 C 其余任务先动手。
- **`docs/api.json` 与生成类型**：B、C 都会新增 v2 路径，导出仍按 N2 定下的规则串行化——
  一次只让一个执行者重写，重写前在进度快照登记「正在导出」；两份 `generated.ts` 禁止手改。
- **Alembic 链**：C Task 3 需要新迁移（`drafts.batch_id`）；B 若发现需要迁移，创建前后都确认
  `uv run alembic heads` 恰好一个 head，不与 C 同时对同一测试库升降级。
- **草稿分派表**（A Task 5 产出）：B 注册 `AFTER_SALE_DECISION`，C 注册 `CONTENT_CHANGE` / `PRICE_CHANGE` / `COUPON`；
  重复注册同一种类由分派表启动自检拦截，不需要人工协调，但两边都要先读 A 产出的 `HandlerResult` 协议签名。
- **Sol（B 后端）与 Sonnet/Terra（B、C 前端任务）交接**：B Task 9（顾客端售后页）、Task 12（商家端售后与信号界面）
  分别落在 Terra 建的 `shop/` 与 Sonnet 熟悉的 `frontend/`；Sol 完成 B 后端路由并导出 OpenAPI 后，
  两位前端执行者才能生成对应 Adapter，交接方式同 N2（在进度快照写明字段实际形状，不由前端执行者反推）。
- 任一执行者发现上游实际接口与计划不一致：停下，按 PRD → 契约 → 计划 → 索引修正，不在自己的实现里吸收差异
  （三份 N3 计划的入口条件已按此写明）。

## 五、审查排期（按批次合并，节省 Astra 额度）

| 批次 | 时机 | 审查项 | 为什么放在这里 |
| --- | --- | --- | --- |
| **批次 0** | N3 开工前 | **入口-N3** | 对照 N2 **最终**（已通过独立复审的）接口核对三份计划入口条件，早于任何实现 |
| **批次 1** | A Task 2 完成后、B / C 注册草稿种类或 Skill 前 | **N3-1** | 路径逃逸是 B、C 所有 Skill 正文的前提；返工时还没有业务 Skill 需要跟着改 |
| **批次 2** | B Task 4 完成后 | **N3-2** | 状态机定型后 B Task 5 起的两阶段确认、Task 8 的决定处理器才有稳定的迁移表可以依赖 |
| **批次 3** | B Task 5 完成后 | **N3-3** | 与批次 2 相邻但分开审——两阶段确认的证据机制和状态机是两类风险，合并审查会稀释注意力 |
| **批次 4** | C Task 5–6 完成、B Task 8、10 完成后 | **N3-4** | 导出/口径与售后决定处理器分属两个阶段，但都是「模型只能触达受控通道」这一类问题，适合一次会话交叉核对 |
| **批次 5** | N3 收尾前 | **N3-5** | 抽审项按清单规则可在里程碑验收前集中审 |

按当前分工，**Astra 共需 6 次审查会话**（与 N2 持平）。批次 2、3 可以视 B 的实际推进速度合并为一次，
但拆开审查能更早发现状态机本身的问题，不必等到两阶段确认也写完才回头改状态机。

### 审查流程

沿用 N2 的四步流程（清单 §二 规则 1），不重复列出；差异只有一点：
**A Task 5、Task 6 因为直接修改了 N2 刚复审通过的 `draft_apply.py` 与 `runner.py`，
批次 1 审查时 Astra 需要额外确认这两处改动没有回归 N2-3、N2-4 已验证的行为**
（草稿应用固定步骤顺序、证据同事务消费、模型无法自批），不能只看新增的分派测试。
