## 一、分工原则

沿用 N2、N3 的三条原则：

1. **按「错了会不会静默地错」分配，不按工作量分配。**
2. **延续对上游代码的熟悉度**，减少「按猜测理解接口」的风险。
3. **审查者 ≠ 实现者**，Astra 只读审查、不承担 N4 任何实现。

N4 与 N3 的差别在于：三个阶段**不是**建在同一块 N3 地基上，而是分别延伸 N2 / N1 的三块不同地基——
循环内核、幂等与账本类存储、评测骨架。所以三个阶段可以分给三个实现者并行，而不是像 N3 那样由 Opus 串起 A、C。

## 三、执行者之间的交接约定

- **0 → A / B / C**：N3 整体验收通过、入口-N4 通过后才开工。D-N4-1 至 D-N4-3 可与此并行裁定。
- **A ‖ B 在两端 Chat 服务上串行**：A Task 0（历史回放）、A Task 4（压缩接入循环）与 B Task 4 / 5（记忆注入）
  都改 `shop_chat.py`、`merchant_chat.py`、`runner.py`。一次只让一个执行者动这三份文件，动之前在进度快照登记
  「正在改 Chat 装配」，完成后写明提示词各段的实际顺序（参考：静态安全规则 → Skill 索引 → 语言指令 → 记忆注入 → 历史 → 本轮；
约束以 PRD A9 为准——安全规则在高优先级静态部分，按用户变化的内容不得打乱稳定前缀）。
- **B ‖ C 在 Alembic 上串行**：B Task 0 与 C Task 2 各自新增迁移。创建前后都确认 `uv run alembic heads` 恰好一个 head；
  **C Task 2 步骤 0 换 pgvector 镜像前**通知 A、B 暂停集成测试，换完 Sonnet 先跑全量回归并在进度快照报告结果。
- **`docs/api.json` 与生成类型**：B（5 条记忆路由）与 C（知识后台字段）都会重写，按 N2 规则串行：
  重写前登记「正在导出」；两份 `generated.ts` 禁止手改。
- **Sol（B 后端）→ Terra / Sonnet（B 前端）**：Sol 导出 OpenAPI 后，在进度快照写明 5 条路由的实际响应形状与错误码，
  前端执行者据此生成 Adapter，不从页面需求反推字段（同 N2、N3）。
- **E5 报告与 R3 申请**：A、B、C 各自产出 Fake 结构验证报告后，Astra 批次 3 一次审过三份评测集与口径；
  之后由用户决定是否合并提交一次真实评测申请（N4 总览 §三「费用点」）。**任何执行者不得自行发起真实调用。**
- 任一执行者发现上游实际接口与计划不一致：停下，按 PRD → 契约 → 计划 → 索引修正，不在自己的实现里吸收差异。
