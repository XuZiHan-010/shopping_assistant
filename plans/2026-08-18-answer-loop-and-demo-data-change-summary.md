## 一、为什么要改

2026-08-17～18 把 Borough 部署到 Railway 并第一次接真实 `deepseek-v4-flash`，暴露出一批只在真实模型下才会出现的问题——所有自动化测试用的都是 `FakeLlmClient`，它返回预先写好的合法 JSON，永远不会走到这些路径。

已经修掉并上线的（不在本计划范围）：

| 提交 | 问题 |
| --- | --- |
| `0bb53a0` | `understand` 提示词未声明 `QueryIntent` 输出契约，模型自造字段名 |
| `bfaf32b` | `classify` 同样缺契约，返回 `trend_query`/`退款退货域` 这类非法枚举值被静默降级 |
| `45b9a4c` | `LLM_MAX_OUTPUT_TOKENS_PER_CALL=1024` 对推理模型太小，正文永远返回空串 |
| `24051ba`、`b455dfc`、`37755f0` | 数字守卫把中文日期、时间窗口、斜杠日期误判为编造数字，连修三轮 |

**本计划要处理的是这些修复暴露出的结构性问题**：数字守卫是靠补正则在打地鼠、校验失败没有重试机会、降级原因对外说不清、演示数据会随日期失效。

## 二、三个建议方向（待用户明确确认）

| | 建议 | 含义 |
| --- | --- | --- |
| **D1** | 保留并升级数字守卫 | 不删除、也不再补日期正则。后端先算合计/最新/峰值/变化率等可信摘要，模型只能引用这些事实，守卫据此验证 |
| **D2** | 代码支持 3 轮、Railway 初期 2 轮，不立即翻倍预算 | 先关结构化步骤的 thinking、开 JSON Output、修可观测，再按实测标定 |
| **D3** | 自动刷新，但用「独立 Cron + 增量滚动」 | 不采用每日全量删除重建 |

一句话原则：**还原 yshopping 的产品行为与质量标准，但不复制它的技术局限。**

## 三、改什么

### A 段 · 先降本与补可观测（3 个任务 + 1 次实测）

| 改动 | 现状 | 改后 |
| --- | --- | --- |
| DeepSeek 上游错误 | `except (httpx.HTTPError, ValueError)` 一律压成无声降级，零日志 | 记录 `failure_kind`（`HTTP_401` / `TIMEOUT` / …）并写结构化日志，不记提示词正文与密钥 |
| 用量记账 | `input_tokens`/`output_tokens` 恒为 0；失败行记的是**悲观估算值** | 成功透传实际 token；失败同时记录 `reserved_tokens`、`usage_known` 与失败类型。401 等已知未计费用 0，超时等未知费用保留预留量，不能伪称实际为 0 |
| 结构化步骤 | classify / understand / 指标口径 / Reviewer 都带推理 | 用独立 `LlmCallOptions` 控制 JSON 与 thinking；正式实现采用 DeepSeek 官方 `thinking={"type":"disabled"}` + JSON Output。**回答生成保留推理**——趋势解读需要它 |

**实测依据**（`deepseek-v4-flash`，2026-08-18）：

| 变体 | classify | understand | completion | reasoning |
| --- | --- | --- | --- | --- |
| 基线 | 403 | 1612 | 700 | 624 |
| 旧实测请求 `reasoning_effort="none"` | 291 | **908** | **75** | **字段消失** |

understand 单次省 **44%**，延迟随 completion 同步下降，输出仍是合法 JSON。

> 上表保留的是既有实测记录，不代表继续使用非官方参数。实现必须改用 DeepSeek 官方 thinking 开关。`json_object` 必须与关闭推理**配对**使用：2026-08-17 单独启用时 `reasoning_tokens` 涨到 4096、`content` 返回空、`finish_reason=length`，反而更糟。

### B 段 · 质量循环与事实校验（6 个任务 + 1 次实测）

**核心是把两个割裂的循环合并成一个**：

```
现状：compose（0 次重试，一被拒就兜底）
      review（2 轮重试，但不告诉模型哪里错了）

改后：生成 → 本地校验 → 独立复核 → 把失败原因回喂 → 重试 → 用尽才兜底
```

| 改动 | 说明 |
| --- | --- |
| 宽松 JSON 解析 | 截取第一个 `{` 到最后一个 `}`，容忍围栏与前后废话（参考项目本来就这么做） |
| 统一质量循环 | 轮次可配置；解析失败并入 issues **继续重试**；缺 Reviewer 或 Reviewer 网络失败返回确定性摘要并标 `DEGRADED`。`NOT_RUN` 只用于本来不需要质量循环的回答 |
| 数字守卫升级 | 允许集 = 行内数值 ∪ `total_rows` ∪ 日期成分 ∪ **后端派生摘要**。只有完整、单指标、可解析日期的时间序列才派生合计/最新/峰值/变化率 |
| 兜底文案 | 完整时间序列可展示「合计 + 最新日期 + 峰值」；截断结果只标“预览”，非时间分组不说“最新”，非加和指标不跨日合计 |
| 降级原因分类 | `UPSTREAM` / `VALIDATION` / `BUDGET` 三种，文案据实说 |

**Railway 初期参数**：`QUALITY_MAX_ATTEMPTS=2`、`MAX_LLM_CALLS_PER_REQUEST=10`、`MAX_LLM_TOKENS_PER_REQUEST=25000`、日预算维持 `500000`。

> 调用次数定 10 而不是 8：`understand` 自带最多 3 次重试（`intent/service.py:27`），且 intent / catalog / answer / reviewer 共用同一个 `LlmBudget`，最坏路径是 9 次。定 8 会让 understand 一重试就把质量循环撞进「预算耗尽」降级。

### C 段 · 演示数据增量滚动（4 个任务）

| 改动 | 说明 |
| --- | --- |
| 目录与事实解耦 | 商品目录稳定生成，避免 `UNIQUE(merchant_id, product_code)` 冲突；订单、明细、退款、退货和工单按业务日确定生成，同日数据与窗口无关 |
| 增量滚动 Seed | 从每个商家的最大业务日追赶到当天，补齐全部漏跑日；单事务 + advisory lock；同日重跑 no-op；按外键顺序清理 180 天窗口外事实，商品不按日删除 |
| 独立 Cron Service | 每日 00:10（Asia/Shanghai）运行；用 `railway.cron.json`（无健康检查、无 `preDeployCommand`、失败不重启），采用只读取 4 个变量的 `SeedSettings`；除必需的 `DATABASE_URL` 外，不注入 LLM、管理员或导出签名密钥 |
| 隔离约束 | 新增独立写权限 `ALLOW_DEMO_DATA_REFRESH`，并在写入前要求数据库商家集合与默认演示商家集合精确相等；真实商家数据库永远不配置该 Cron |
| 旧全量脚本加锁 | `backend/scripts/seed_demo_analytics.py` 会 DELETE 六张表再重写，跑一次即抹掉滚动出的历史。加 `--force-full-rebuild` 显式确认，降为一次性重置工具 |

## 四、执行顺序

```
A1 错误码 ─→ A2 记账 ─→ A3 关推理 ─→ A4 实测 ──┐
                                              ├─→ B4 按实测标定预算
B1 宽松解析 ─→ B2 统一循环 ─→ B3 事实校验 ──────┘ ─→ B5 兜底文案 ─→ B6 降级分类 ─→ B7 实测

C1 单日解耦 ─→ C2 滚动 Seed ─→ C3 独立 Cron ─→ C4 文档登记
```

- **A 段必须先于 B4**：预算标定依赖 A4 的实测数字，不得拍脑袋填。
- **C1 必须先于 C2**：增量滚动依赖「按日确定性」这个前提。
- A / B / C 三段之间无其他依赖，C 段可与 A、B 并行。

## 五、代价与风险

| 项 | 说明 |
| --- | --- |
| **费用** | A 段实测约 1.5~2 万 token，B 段 9 题验收约 4~5 万 token，均按 R3 单独取得同意后执行。A1–A3、B1–B6、C1–C4 全部零 LLM 费用 |
| **历史兼容** | 不全量重灌现有演示历史；新生成器从当前最大业务日的下一天接管。若要整体重置，另做备份、维护窗口和单独审批 |
| **破坏性写入护栏** | Cron 即使运行在 `APP_ENV=production`，也必须同时具备独立显式写权限和演示商家集合精确匹配；任一不满足即在写入前失败 |
| **契约要完整传播** | `quality_attempts` 必须按 PRD → 后端精确契约 → 两处 Schema → OpenAPI 文档 → `generated.ts` → 前端 Adapter/契约测试的顺序改为 0～3；只改后端数字会让历史回放或前端解析失败 |
| **关推理是否伤准确性** | A4 的出口判据已包含这一项：4 条问题的 `answer_mode`/`category` 判定必须与基线一致，不一致则回退该步骤的关闭 |

## 六、有意偏离参考项目的三处（需登记进 `docs/yshopping-parity-audit.md` §5）

1. **数字守卫**——参考项目本地校验无数字检查，数字正确性完全交给质检 agent；我方保留确定性守卫并升级为事实校验。理由：确定性拦截优于纯模型判断。
2. **演示数据**——参考项目写死 2026-07-22~24 共 3 天且无刷新；我方 180 天滚动 + 每日增量。理由：参考做法会让所有相对时间问题从第一天起就查不到数据。
3. **结构化步骤关推理**——参考项目基于非推理模型，无此概念；我方对四个结构化步骤关闭 thinking，回答生成保留。理由见 A 段实测。
