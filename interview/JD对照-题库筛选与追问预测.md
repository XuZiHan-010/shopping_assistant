## 零、一句话结论

**题库的重心和 JD 的重心是错位的。**

题库按「小林 AI 教程的知识体系」组织——框架考古、协议前沿、推理原理；
JD 要的是「**应用层全栈 + 业务落地**」——识别可 AI 化节点、跑通全周期、推动产品化/标准化/规模化。

JD 里点名的 AI 关键词只有三个：**Prompt 工程、RAG、向量数据库基本原理**。
注意措辞是「**基本原理**」，不是「深入掌握」。

所以：**RAG 那份要全背，LangChain 那份基本可以不背。**

## 三、面试官最可能的「知识点 → 项目」追问

这是本文档的核心。题库回答的是「这个概念是什么」，而面试官真正会问的是「**在你项目里怎么落的、为什么这么落、下次怎么改**」。

以下按 JD 条目组织，每条给出**追问原文 + 你的抓手**。

---

### 3.1 JD 职责 1「识别可 AI 化的关键节点」

面试官几乎一定会从项目拐到**泡泡玛特自己的业务**。

| 可能的追问 | 你的抓手 |
| --- | --- |
| 「你这个商家助手，是怎么判断出'自然语言查经营数据'值得做 AI 化的？」 | 判据三条：① 高频重复；② 现有路径是「找数据同事提需求→等报表」，链路长；③ 输出可结构化校验（指标有口径、有数值，不是开放创作）。**第三条是关键**——可验证才敢上线 |
| 「如果让你看泡泡玛特的业务，你觉得哪些节点可以 AI 化？」 | 见下方「泡泡玛特场景清单」 |
| 「你怎么判断一个场景**不该**上 AI？」 | 反例是你项目里真实存在的：范围外提问在第 3 个节点就被前置闸门拦掉，**一次模型都不调**。判据：答案没有唯一正确性、或错了代价不可控、或规则能穷举时，不要上模型 |

**泡泡玛特场景清单**（准备 3 个，讲 1 个深的）：

1. **门店/线上销售问数**——和你项目 1:1 同构，最好讲。IP × 系列 × 区域 × 渠道的销量、库存周转、断货预警；口径统一（什么叫"一个 SKU"、隐藏款算不算）正是你做过的 `metric_definitions` 那套。
2. **IP 设计辅助与素材检索**——对应 JD 加分项 1（图形学）。可以诚实说「这块我没做过，但如果做，第一步是把历史设计稿 + 标签做成可检索资产库，而不是一上来接文生图」。
3. **抽盒机/社区的用户反馈聚合**——工单、评论、二手价舆情做分类与摘要，和你的 Chat BI 问题分类下钻同构。

### 3.2 JD 职责 2「模型选型 / 数据工程 / 业务试点与迭代优化」

| 可能的追问 | 你的抓手 |
| --- | --- |
| 「你选 `deepseek-v4-flash` 是怎么决策的？对比过什么？」 | 成本 + 中文 + JSON 稳定性三维；**并且要说出你实测踩过的坑**：`llm_max_output_tokens_per_call` 从 4096 提到 8000——因为它是推理模型，环比/同比这类多步推理会把 token 耗在 reasoning 上、正文吐空，被判定模型不可用而降级。这个细节证明你真的跑过而不是看文档选的 |
| 「什么情况下你会换到 `pro`？」 | 有量化触发条件：意图识别准确率 < 90%、或 Reviewer 失败率上升且根因是生成质量而非数据。**强调「先有指标再换模型」** |
| 「数据工程你做了什么？」 | 6 张经营表 + 180 天可重复 Seed + 业务时区日期解析 + 复合索引 `(merchant_id, business_date)`。**重点讲「口径」**：`metric_definitions` 表把业务口径和 SQL 口径都存下来，回答里带口径返回——这才是 Data Agent 和"套壳问数"的区别 |
| 「业务试点怎么做的？效果怎么衡量？」 | ⚠️ **诚实缺口**：你没有真实商家用户。可答：做了 Chat BI 衡量层（采纳率/准确率/平均思考时长/问题命中率/回答失效率，日粒度可重算汇总），指标体系是为试点准备的，但**没有真实用户数据**。别硬编 |
| 「迭代优化的闭环是什么？」 | 用户点赞点踩/采纳 → `feedback` 表 → Chat BI 分类下钻 → 定位是意图识别错、检索没召回、还是生成不合格 → 对应改 Prompt / 白名单 / 检索评分。**这条链路你真的通了** |

### 3.3 JD 职责 3「产品化、标准化、规模化」+ 加分项 4「AI 中台」

这是你最容易被低估、但其实**准备得最好**的一块。要主动往「中台」上靠。

| 可能的追问 | 你的抓手 |
| --- | --- |
| 「这套东西怎么复用到第二个业务线？」 | **拆成三层讲**：① 通用层——Agent 图、费用闸门、限流、质量循环、降级协议、本地化，换业务不用动；② 配置层——指标目录、维度白名单、知识库，是数据不是代码；③ 业务层——只有 SQL 模板和 Prompt 话术要改。**「加一个新指标不需要改 Agent 代码」就是标准化的证据** |
| 「成本怎么控？上量之后会不会失控？」 | 三道闸：单请求调用数上限 10（最坏路径 `classify 2 + understand 3 + metric catalog 1 + (answer+reviewer)×2` 算出来的，不是拍的）、单请求 token 上限 25000、每日预算熔断 500000。**加一句**：本地化调用走**独立预算**，不挤占问答额度，`llm_usage.purpose` 分 `AGENT`/`LOCALIZATION` 两条曲线 |
| 「线上出问题你怎么定位？」 | 现有：`/api/admin/ops/status` 给预算余量、限流命中、降级计数；`thinking_steps` 给每个节点耗时。**诚实缺口**：没有分布式 Trace，跨节点的单请求全链路还原不了，下一步该接 OpenTelemetry。**说缺口比吹全了更能得分** |
| 「多租户是怎么做的？」 | 这是往 AI 中台靠的最强牌：`merchant_id` 强制注入在查询层而非调用方；跨商家访问 403 + 写审计；连翻译缓存都按 `merchant_id`/`GLOBAL` 双作用域隔离，带 CHECK 约束和唯一索引。**并且有反例测试**——不是"我注意了"，是"我写了跨商家访问必须 403 的测试" |

### 3.4 JD 资格 5「RAG + 向量数据库基本原理」—— ⚠️ 最大风险点

**你的项目没有向量数据库，用的是关键词 + 确定性评分。** 这一定会被问到，处理不好会被判成「没做过真 RAG」。

| 追问 | 应对 |
| --- | --- |
| 「你这个不算 RAG 吧？没有 Embedding 也没有向量库。」 | **不要辩解说算**。正面拆：RAG 的本质是「检索外部知识注入上下文」，我完整做了检索、组装、注入、引用标注（`analysis_sources`）；**没做的是稠密向量召回那一段**。当时的判断是：知识库只有 23 篇团队文档、业务域固定四板块，**用向量库的召回收益盖不过引入一个新组件的运维成本**——这是规模决策，不是能力缺失 |
| 「那你怎么保证召回率？」 | 讲你**实测踩过的坑**（这是最有说服力的部分）：第一版「命中任一关键词就返回」，导致"商品"一个词命中全域三篇文档，关键词过滤退化成空过滤。改成：要求同时命中**业务词 + 动作/规则词**，标题(3)/路径(2)/正文(1)加权取 Top 3。**并且新增了同域干扰文档（"商品定价""商品库存"）作为必测反例**——因为原来的单文档测试结构上发现不了这个问题 |
| 「什么时候你会上向量库？」 | 给量化阈值：文档量过百、或出现「问法和文档用词不重合」的明显未命中、或需要跨业务域语义召回。选型顺序：先 pgvector（已有 PostgreSQL，不加组件）→ 量再大才独立向量库。**先混合检索（BM25 + 向量）再上 Reranker**，不要一步到位 |
| 「Embedding 模型你会怎么选？」（纯原理题，JD 明写） | 中文场景优先 BGE / M3E 系列；维度与召回质量、存储、检索延迟三者权衡；**必须固定版本**——换 Embedding 模型等于全库重新索引，这是运维成本的大头。再补一句你项目里的类比：你的 `LOCALIZATION_PROMPT_VERSION` 就是同一个思路——把模型版本做进缓存键 |

> 💡 **话术定调**：把「没上向量库」讲成一个**有判据的工程决策 + 有实测的替代方案 + 有触发条件的演进路线**，比含糊承认「没做过」强得多。

### 3.5 JD 资格 2「React、Vue3 及背后原理」—— ⚠️ 第二风险点

**你没有 React 项目。** JD 把 React 写在 Vue3 前面，说明他们可能在用 React。

| 追问 | 应对 |
| --- | --- |
| 「React 你写过吗？」 | **直接承认**：Vue3 是我的生产栈，React 我理解模型但没有项目。**立刻接住**：讲两者的核心差异你是清楚的——Vue 的响应式是编译期 + Proxy 依赖收集，精确到组件级更新；React 是整棵子树重渲染 + `memo`/`useMemo` 手动剪枝。**再补一句**：我这个项目是全栈独立做的，切框架的成本主要在心智模型，不在语法 |
| 「Vue3 的响应式原理讲一下」 | Proxy 拦截 get/set → `track` 收集依赖到 `effect` → `trigger` 触发更新；对比 Vue2 的 `Object.defineProperty` 无法监听新增属性和数组索引。**再往项目上拐**：讲你为什么某些地方用 `shallowRef`——ECharts 实例不能被深度代理 |
| 「你前端做过什么有难度的事？」 | **三个真实抓手**：① **SSE 用 `fetch` + `ReadableStream` 手写解析器，不用 `EventSource`**——因为 `EventSource` 不能带自定义请求头，而我们要传 `Authorization`；② **ECharts 不进首屏**：`manualChunks` 拆独立 chunk + `defineAsyncComponent`，静态门禁脚本 + e2e 网络观测**双重保证**；③ **生成类型 → Adapter → 领域模型的单向流**，组件不直接消费 `generated.ts`，每个 Adapter 配契约测试，后端改字段时立刻红 |
| 「i18n 怎么做的？」 | key 集合用 `satisfies MessageSchema` 编译期锁死中英一致，禁止 `t(key as any)` 绕过；**后端也有一套**，`SupportedLocale` 前后端字面量严格一致 |

### 3.6 JD 资格 4「MySQL 等关系型数据库 + 常用优化手段」—— ⚠️ 第三风险点

**你用的是 PostgreSQL，不是 MySQL。** 但优化手段大部分是通用的。

| 追问 | 应对 |
| --- | --- |
| 「为什么选 PostgreSQL 不用 MySQL？」 | 诚实：新项目没有必须对接的 MySQL 上游，PG 在聚合分析、JSON、CHECK 约束上更顺手。**明确说出你的项目约定是「不同时引入两个主库」**——这是架构纪律，不是偏好 |
| 「你做过哪些优化？」 | ① **复合索引前缀对齐多租户**：所有经营表都是 `(merchant_id, business_date)` 开头，因为每个查询都强制注入 `merchant_id`，前缀天然可用；② **约束下推**：日期范围、行数上限、`statement_timeout` 全部在 SQL 层限制，不在应用层过滤；③ **聚合下推**：「猜你想问」的频次统计把 `GROUP BY` + `ORDER BY` + `LIMIT` 全下推到 SQL，不拉全量到内存 |
| 「慢查询怎么定位？」 | `EXPLAIN ANALYZE` 看是否走索引、有没有 Seq Scan；PG 用 `pg_stat_statements`，MySQL 对应慢查询日志 + `EXPLAIN`。**主动说出 MySQL 的对应物**，证明你不是只会一种 |
| 「事务用得怎么样？」 | 有个真实细节可讲：历史推荐查询用 **savepoint 隔离**，统计查询失败只回落静态推荐，**不污染主聊天事务** |
| 「幂等怎么做的？」 | `answers` 表上 `client_request_id` 唯一约束，重复请求回读同一份结果；日报用 `daily-report:{report_date}` 做答案幂等键，并发首次请求回读同一份已完成报告 |
