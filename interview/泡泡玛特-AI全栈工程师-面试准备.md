## 二、项目介绍的三个版本

### 版本 A · 30 秒（自我介绍时）

> 我独立做了一个面向电商商家的对话式 Data Agent，全栈自己完成——后端 Python + FastAPI + LangGraph，前端 Vue3 + TypeScript，单一 PostgreSQL。商家用自然语言问经营数据，系统返回带口径、带图表、带行动建议的回答。
>
> 这个项目真正的难点不是接大模型，而是**让 AI 的输出在生产环境可信、可控、可算账**。

### 版本 B · 2 分钟（「详细说说」的第一层）

> 商家在对话框里问「最近 7 天退货量趋势怎么样」，系统会识别商家身份 → 判定问题是否在业务范围内 → 结构化理解意图 → 用后端模板 SQL 查询 PostgreSQL → 生成结论、图表和至少两条有数据依据的建议 → 交给独立 Reviewer 复核 → 落库并异步沉淀商家记忆。
>
> 我做的三个核心决策：
>
> **第一，模型永远碰不到 SQL。** 它只输出经 Pydantic 校验的结构化意图，SQL 由后端模板生成，值参数全部绑定，并且强制注入 `merchant_id`。
>
> **第二，加了一道零 LLM 的前置闸门。** 范围外的提问在流水线第 3 步就被拦掉，直接跳到最后，跳过全部 4 次模型调用。
>
> **第三，任何降级都必须对用户可见。** 模型超预算、数据库不可用、知识库没命中——全部在 API 字段和界面上显式标注。绝不把规则兜底伪装成真实模型分析。
>
> 最终真实付费验收：14 个场景 26 次调用、31,583 token；后端 1128 个测试全绿。

### 版本 C · 5 分钟（按「问题 → 设计 → 保障 → 工程化」四段走）

**① 我识别了什么可 AI 化的节点**

> 商家日常经营分析有四个痛点：数据散在订单、退款、商品、优惠券、工单多张表里，跨业务分析成本高；商家不知道指标怎么算，也不该接触数据库；回答常常只有一个数字，缺口径、缺趋势解释、缺「接下来做什么」；平台规则散落在文档和个人经验里。
>
> 这四点的共同特征是——**都卡在自然语言和结构化数据之间的翻译**。这是大模型该上的地方，也是它唯一该上的地方。

**② 我怎么设计的（画这张图）**

```
 1  load_context             识别商家与会话上下文
 2  retrieve_knowledge_index 读取业务知识索引
 3  prefilter_question       ⭐ 零 LLM 闸门 ──不相关──┐
 4  classify_intent          粗分类           [LLM]  │
 5  understand_intent        结构化意图       [LLM]  │
 6  validate_intent          ⭐ Pydantic 校验模型输出 │
 7  retrieve_knowledge_detail 取指标口径+商家记忆     │
 8  query_data               ⭐ 后端模板 SQL         │
 9  compose_answer           结论+图表+建议   [LLM]  │
10  quality_loop             ⭐ 独立 Reviewer [LLM]  │
11  suggest_questions        猜你想问 <─────────────┘
12  persist_answer           落库 + 异步沉淀记忆
```

> 模型只出现在 4、5、9、10 四个节点——它只负责**读懂人话**和**写出人话**。中间的校验、检索、查询全是确定性代码。
>
> **我把不确定的东西夹在确定性代码中间，这样 AI 出错的爆炸半径是可控的。**

**③ 我怎么保证它能上生产（四条防线）**

- **安全**：模型不生成 SQL；表名列名走白名单；所有查询强制 `merchant_id` 过滤；跨商家访问返回 403 并写审计日志。我专门写了反例测试。
- **成本**：单请求调用次数 + token 双闸门；每日全局预算熔断；`llm_usage` 表落每一次调用；本地化翻译用独立预算，不挤占问答额度。测试全程注入 FakeLlmClient，1128 个测试一分钱不花。
- **质量**：独立 Reviewer 是**另一次**模型调用，不过就重试，重试有上限；结果通过 `quality_status` / `quality_attempts` 对用户可见。
- **诚实**：任何降级在 API 字段和界面上显式标注。宁可告诉用户「这次没用真实模型」，也不编一个像样的答案。

**④ 工程化**

> 前后端契约是**单向自动生成**的：后端 Pydantic → FastAPI 导出 OpenAPI → 自动生成 TypeScript 类型 → 手写 Adapter 转领域模型。组件禁止直接消费生成类型。后端改字段，前端**编译期**就报错。
>
> CI 里有 6 个门禁脚本，不是功能是防线：类型契约有没有脱节、密钥有没有被打进构建产物、图表库有没有被误带进首屏、mock 数据有没有混进生产代码、测试夹具有没有过期、格式对不对。

## 三、AI Native：我们对 AI 做了什么

这一节是**和只会调 API 的候选人拉开差距的地方**。按「优化了什么 → 怎么做的 → 效果」讲。

### 3.1 成本优化：三层预算防线

| 层 | 机制 | 位置 |
| --- | --- | --- |
| **第 0 层** | 零 LLM 前置闸门，范围外提问不进 LLM 路径 | `backend/app/agent/prefilter.py` |
| **第 1 层** | 单请求预算：调用次数 + token 双上限，调用前「刷卡」 | `backend/app/llm/client.py` 的 `LlmBudget.charge_call()` |
| **第 2 层** | 每日全局熔断，靠 `llm_usage` 表统计 | `backend/app/llm/guard.py` 的 `LlmCostGuard` |

**讲法：**

> 预算耗尽不是抛错误页，而是**转成可见降级**——用规则兜底给出能用的回答，同时在界面上标注这次没走真实模型。这是刻意的：错误页让用户什么都拿不到，可见降级让用户拿到一个他知道其局限的答案。
>
> 而且两条费用曲线是分开的：`llm_usage.purpose` 区分 `AGENT` 和 `LOCALIZATION`，翻译不挤占问答的额度。
>
> 效果：14 个验收场景平均 **1.9 次调用/场景**。省钱是设计出来的，不是省出来的。

### 3.2 质量优化：生成与审核分离

> 生成答案和复核答案是**两次独立的模型调用**（代码里是 `answer_llm` 和 `reviewer_llm` 两个注入点）。Reviewer 有自己的 Prompt（`backend/app/prompts/reviewer.py`），不看生成过程，只看结果是否站得住。不过就重试，重试次数有上限。
>
> 为什么不让同一次调用自己检查自己？因为模型对自己刚写的内容有强烈的确认偏误。**换一个上下文重新问一遍，才有真正的第二意见。**
>
> 重试次数通过 `quality_attempts` 对用户可见——不是藏起来，而是告诉用户「这个回答改了两轮才通过」。

### 3.3 可靠性优化：把模型输出压缩成有限枚举

> 模型输出的不是自由文本，是结构化意图。看 `backend/app/intent/models.py` 的 `QueryIntent`——里面大量字段是 `Literal` 类型：
>
> ```python
> group_by: Literal["spu_id", "address_city_name"] | None = None
> filter_column: Literal["spu_id", "address_city_name"] | None = None
> ```
>
> 意思是模型只能从这个枚举里选，选别的直接被 Pydantic 拒掉。
>
> **本质是把「模型可能犯的错」从无限种压缩成有限种。** 有限种可以穷尽测试，无限种不能。

### 3.4 延迟优化：SSE 流式 + 真实进度

> `POST /api/chat` 默认返回 SSE 流，事件类型 `step` / `done` / `error`。用户在 1 秒内看到的是**真实的处理阶段**——「识别商家与会话上下文」「读取业务知识索引」……这 12 步不是假动画，每个节点都被 `_timed_node()` 包了计时器，跑到哪一步、花了多久实时推给前端。
>
> 一个细节：`done` 事件的载荷和非流式 `ChatResponse` **完全一致**，前端不为两条路径维护两套解析逻辑。

### 3.5 检索优化：刻意不用向量库

> 我做了检索增强，但用的是确定性的关键词加权打分——标题、路径、正文三档权重（`backend/app/knowledge/retrieval.py` 的 `_relevance_score`）。代码里明确写了这是刻意决策。
>
> 原因：我的知识域是**闭集**——指标口径、平台规则、业务域，词表已知且可枚举。这种场景下向量检索会引入三个我不想要的东西：嵌入模型的额外成本和延迟、召回结果不可解释、以及不确定性。
>
> 而第 3 步的前置闸门要拿检索得分来决定「要不要调模型」，这个判断必须 100% 可复现——否则同一个问题这次拦下次不拦，用户会觉得系统坏了。

### 3.6 AI 辅助开发（vibe coding）的方法论

> 这个项目基本是我用 Claude Code 全程驱动开发的，但核心不是「让 AI 随便写」，而是**把约束写进仓库，让 AI 每次开工前必须读**。
>
> 三个支柱：
>
> **① `AGENTS.md`——9 条不可违反的规则。** 面向用户的内容用中文；未经许可不准 git push；真实模型调用前必须先说明成本；LLM 不得生成 SQL；商家数据必须隔离；密钥不进代码；降级必须可见；参考项目只读；参考项目是需求基准。
>
> **② `docs/project-progress.md`——跨会话的外部记忆。** 只记当前快照：当前阶段、已完成、最近验证结果、下一步、已知风险。不记流水账。这样换一个会话、隔几天回来，AI 能直接接着干。
>
> **③ 文档权威顺序写死。** 产品范围只在 PRD、字段契约只在后端方案 §8、规则只在 AGENTS.md。冲突时按这个顺序判定，**不准就地改成自己顺手的样子**。
>
> 效果是 AI 的产出稳定性完全不一样——它不会今天一套明天另一套，也不会为了让测试通过就偷偷改需求。
>
> **我理解的 vibe coding 不是「少写代码」，是把人的角色从打字员变成架构师和审核者。** 所以我这个项目测试代码行数超过生产代码——AI 写得快，我必须验证得更快。

### B · 架构设计类（8 问）

**B1「为什么不让模型直接写 SQL？现在 Text2SQL 不是很成熟吗？」** ⭐ 送分题

> Text2SQL 在 demo 里效果很好，生产里有三个问题：一是模型可能查错表算错数，而商家会拿这个数字做决策；二是没法保证每条 SQL 都带商家隔离条件，漏一次就是数据泄露；三是没法限制扫描范围，一条没有时间条件的全表扫就能拖垮库。
>
> 所以我让模型输出结构化意图：
> ```json
> {"metric":"refund_count","date_from":"2026-09-03","date_to":"2026-09-09","granularity":"day"}
> ```
> 这个 JSON 过 Pydantic 校验——指标名在白名单、日期跨度有上限、行数有上限——然后由后端模板拼 SQL、绑定参数、强制注入 `merchant_id`。
>
> **本质是把模型可能犯的错从无限种压缩成有限枚举。** 校验层能穷尽，Text2SQL 不能。

**B2「为什么用 LangGraph 而不是自己写个流程？」**

> 主要是三个理由。一是**状态显式化**——12 个节点通过一个有类型的 `AgentState` 交换数据，不传无类型字典，第 9 步取一个第 5 步没放的键会在类型检查时暴露而不是线上炸。二是**条件路由是一等公民**——我的第 3 步要么往下走要么跳到第 11 步，用 `add_conditional_edges` 表达得很干净。三是节点可以单独测试，我的 unit 测试目录有 96 个文件，很多就是单节点的。
>
> 如果流程只有三四步且是直线，自己写确实更轻。但到 12 个节点 + 条件分支 + 每节点计时，框架的价值就出来了。

**B3「12 个节点会不会太长？延迟怎么办？」**

> 12 个节点里只有 4 个调模型，其余 8 个是本地计算和数据库查询，加起来通常在几十毫秒级。延迟主要来自模型调用。
>
> 我用两个办法处理：一是 SSE 流式，用户 1 秒内就能看到真实进度，不是干等；二是前置闸门直接砍掉不必要的调用。
>
> 而且顺序是有意义的——检索在意图识别之前，是为了让闸门能用检索得分做判断；Reviewer 在最后，是因为它必须看到完整结果。

**B4「商家数据隔离怎么做的？」**

> 三层。第一层，**不相信前端传来的商家编号**——商家身份从 Token 解析，前端发什么都不作数。第二层，所有数据访问必须穿过 Repository 层，那一层强制注入 `merchant_id`，Service 层不允许直接拼 SQL，所以只需要在一个地方保证隔离。第三层，跨商家访问返回 403 **并写审计日志**（`MerchantScopeService.require_conversation()` 里失败时调 `record_scope_violation`）。
>
> 而且这件事的**顺序**很关键——我在开发计划里把「可信身份和商家隔离」排在任何经营数据查询之前。如果先做查询再补隔离，就要重写 Repository 和 Service。

**B5「降级策略具体怎么设计的？」**

> 原则是**降级必须对用户可见**。API 响应里有一组专门的字段：`degraded`、`degraded_reason`、`quality_status`、`quality_attempts`、`quality_notes`、`analysis_sources`。
>
> `analysis_sources` 是个有序数组，主要来源在前——告诉用户这个回答是基于真实数据查询、知识库、还是规则兜底。闲聊和无效问题返回 `["NONE"]`，**不为了凑「至少一项」而编造来源**。
>
> 反例是我刻意避免的：前端不提供「没配后端地址就默认同源」的回退。看起来贴心，实际上是把配置错误伪装成接口 bug。**宁可响亮地崩溃，也不要安静地走错。**

**B6「数据库为什么只用 PostgreSQL，不上 Doris/ClickHouse？」**

> 因为现在的数据量根本用不上。我在文档里写了明确的启用条件：数据到千万级以上、PG 聚合明显成为瓶颈、需要跨多张宽表高并发分析、已经存在 ETL 体系——四条都不满足时引入分析型数据库只会增加运维面和数据一致性风险。
>
> 同样的判断也适用于 Redis：我留了接口但没启用，因为没有真实的缓存压力和异步队列需求。
>
> **技术选型上我刻意保持很小的组件面**，组件少，理解、开发、测试、部署的门槛都低很多。

**B7「如果并发上来了，这套架构哪里先撑不住？」**

> 第一个瓶颈是**模型调用**，不是数据库。单次问答最多 4 次串行调用，每次几百毫秒到几秒，这是延迟主体。优化方向是：4、5 两步的粗分类和细化意图有合并空间；Reviewer 可以按风险分级，低风险问题跳过。
>
> 第二个是**数据库连接池**——全异步不代表无限并发，连接数是硬上限。
>
> 第三个是**成本**而不是性能——并发上来后每日预算会先于服务器熔断。所以我把预算熔断做成了一等公民而不是事后补的开关。

**B8「为什么后端分那么多层？不觉得啰嗦吗？」**

> 分层的目的不是洁癖，是**把安全检查逼到必经之路上**。
>
> 因为所有数据访问都必须穿过 Repository，我只需要在那一层保证「永远带 `merchant_id` 过滤」，全项目的隔离就成立了。如果允许 Service 也直接写 SQL，我就得检查 19 个 Service 文件，而且每新增一个都要重新检查。
>
> 规则很简单：路由只做认身份、校验参数、调 Service；Service 写业务但不拼 SQL；Repository 碰数据库但不调 LLM。

### C · AI / 大模型类（10 问）

**C1「你用了 RAG 吗？向量数据库选的哪个？」** ⚠️ 高风险，别装

→ 见 [3.5 检索优化](#35-检索优化刻意不用向量库) 的完整讲法，然后**主动补缺口**：

> 向量库本身我目前是理论层面熟悉——embedding 把语义映射到高维空间、用余弦相似度召回、HNSW 或 IVF 做近似最近邻索引，pgvector 能直接在 PostgreSQL 里做所以不用额外组件。生产场景通常会做 hybrid：BM25 关键词召回加向量召回，再用 rerank 模型重排。
>
> 但我确实**没有在生产项目里真正跑过**，这是我接下来想补的。

**C2「什么时候该用向量检索，什么时候不该？」**（C1 的追问）

> 我的判断标准是三条：
>
> 1. **知识域是闭集还是开放集** —— 闭集（指标、规则、枚举）关键词就够，开放集（长文档、多轮语义）需要向量。
> 2. **召回结果需不需要可解释** —— 如果要告诉用户「这条答案来自哪一条知识」，关键词天然可解释，向量需要额外工作。
> 3. **判定需不需要确定性** —— 我的闸门要用得分做通过/拒绝的二元判断，必须可复现。

**C3「Prompt 工程做了什么？」**

> 四类 Prompt 完全独立，各有各的文件：意图识别、回答生成、Reviewer 审核、记忆提取，另外还有本地化翻译。分开的理由是它们的失败模式不同——意图识别要的是严格 JSON，回答生成要的是可读性，Reviewer 要的是挑刺而不是附和。
>
> 三个具体技巧：
>
> **① 结构化输出用专门的调用选项。** 我定义了 `STRUCTURED_CALL_OPTIONS = LlmCallOptions(json_output=True, thinking="disabled")`——要 JSON 时关掉思维链，因为思维链会让输出变长变贵，而且对严格 JSON 没帮助。
>
> **② Prompt 版本号进缓存键。** `LOCALIZATION_PROMPT_VERSION` 是翻译缓存键的一部分，改了 Prompt 缓存自动失效，不会拿旧 Prompt 的结果冒充新的。
>
> **③ 抵御注入。** 翻译 Prompt 处理的是商家输入的内容，属于不可信文本，系统提示里明确要求 JSON-only 并忽略源文本中的任何指令。

**C4「模型输出的 JSON 不合法怎么办？」**

> 这是必然会发生的，所以有专门的处理路径和测试。流程是：Pydantic 校验失败 → 记录失败类型 → 走降级路径（规则兜底或提示用户换个问法）→ 在响应里标注 `degraded` 和原因。
>
> 关键是**不重试无限次**。重试有上限，超了就降级，因为一个持续输出非法 JSON 的模型再试十次也不会突然变好，只会烧钱。
>
> 我的 `LlmFailureKind` 枚举把可安全记录和归因的失败类型列出来了：HTTP_401 / 403 / 429 / OTHER、TIMEOUT、NETWORK、BAD_PAYLOAD。分开是因为处理方式不同——429 该退避重试，401 该报警，BAD_PAYLOAD 该降级。

**C5「模型选型怎么考虑的？为什么是 DeepSeek？」**

> 三个因素：**成本**（这类高频内部工具，单次问答 4 次调用，模型单价直接决定能不能规模化）、**OpenAI 兼容 API**（换供应商不用重写客户端）、**中文能力**（业务场景是中文商家提问和中文知识库）。
>
> MVP 用 `deepseek-v4-flash`，`deepseek-v4-pro` 留作经费用评估后可配置的升级选项。这个升级路径是配置层的，不改代码。
>
> 而且我把模型抽象成了接口——`LlmClient` 是个 Protocol，只规定 `is_configured()` 和 `complete()` 两个方法，真实实现和 Fake 实现并存。换模型、换供应商、甚至换成本地模型，业务代码一行不用改。

**C6「怎么保证回答质量？」**
→ 见 [3.2 质量优化](#32-质量优化生成与审核分离)。

**C7「Reviewer 也是模型，它会不会也出错？」**（C6 的追问，好问题）

> 会。所以我没把它当成真理，而是当成**第二意见**。三个设计：
>
> 1. 重试有上限，Reviewer 反复不满意时不会无限循环——超了就以 `DEGRADED` 状态出，并把原因写进 `quality_notes` 给用户看。
> 2. Reviewer 的结论对用户可见而不是内部消化——用户能看到「改了两轮」和 Reviewer 的备注，由他自己判断。
> 3. `quality_status` 有 `NOT_RUN` 这个值——Reviewer 没跑（比如预算耗尽）时如实说没跑，而不是默认标成通过。
>
> **核心原则是：不假装确定性。** 一个诚实标注了不确定的系统，比一个假装什么都对的系统安全得多。

**C8「怎么做的评测？怎么知道它变好了还是变坏了？」**

> 两套，互补但不能互相替代：
>
> **Mock 测试**（1128 个后端测试）—— 注入 FakeLlmClient，保证逻辑正确、完全确定、一分钱不花。它测的是「给定模型这样输出，我的系统处理对不对」。
>
> **真实付费验收** —— 14 个精心设计的场景，覆盖 6 种回答模式、跨语言、翻译降级、零调用路径。它测的是「我对模型行为的假设成不成立」。
>
> 这两件事我踩过坑才想明白：**真实模型跑出过一个 Fake 测试永远触达不到的缺陷。** 因为 Fake 返回预设文本，它不会像真实模型那样输出边界形态的内容。所以真实验收要设计得少而准——14 个场景 26 次调用，不是随便跑跑。

**C9「AI 应用的安全风险你怎么看？」**

> 我分三类处理：
>
> **① 提示词注入** —— 商家输入和知识库正文都是不可信文本。翻译 Prompt 明确要求 JSON-only 并忽略源文本里的指令；更根本的是**模型的输出根本没有执行权**——它不生成 SQL、不调用工具、不能写数据库，注入成功了也只能影响一段文字。
>
> **② 数据越权** —— 身份从 Token 解析不信前端；Repository 层强制 `merchant_id`；越权 403 + 审计日志。
>
> **③ 信息泄露** —— 日志不记录隐私字段和完整查询结果；`/api/admin/ops/status` 明确禁止返回 Token、Prompt、经营数据和完整请求正文；前端构建产物有密钥扫描门禁。
>
> 另外权限设计上我分了两套凭证：商家 Token 用 `Authorization`，管理员 Token 用 `X-Admin-Token`。**刻意不共用一个头**——共用之后后端就分不清「商家在调管理接口」和「管理员在调商家接口」。

**C10「Agent 和普通的 LLM 调用有什么区别？」**（基础概念题，别答虚了）

> 普通调用是一次性的：文字进、文字出。Agent 是**多步编排 + 状态 + 条件路由**。
>
> 具体到我这个项目，区别体现在三点：
>
> 1. **有状态** —— 12 个节点共享一个 `AgentState`，后面的节点能看到前面的结果。
> 2. **有分支** —— 第 3 步的判定结果决定后面走哪条路。
> 3. **有外部动作** —— 查数据库、写审计、落库、触发异步记忆沉淀。
>
> 但我要强调一点：**我刻意没有做成「模型自主决定调用哪个工具」的那种 Agent。** 流程是我编排死的，模型只在固定的 4 个节点被咨询。因为自主调工具意味着行为不可枚举，而我需要每条路径都能被测试覆盖。

### D · 前端类（5 问）

**D1「你用 Vue，我们也有 React 的活，能上手吗？」**
→ 见[第七节 · 缺口 2](#缺口-2--没有-react-项目经验)。

**D2「Vue3 的响应式原理讲一下」** ⭐ JD 明写「及背后原理」，必考

> Vue3 用 `Proxy` 替代了 Vue2 的 `Object.defineProperty`。核心是三步：
>
> **依赖收集** —— 组件渲染时读取响应式数据，Proxy 的 `get` 拦截器把「当前正在执行的副作用函数」记到这个属性的依赖集合里。
>
> **触发更新** —— 数据被改写时 `set` 拦截器取出依赖集合，把里面的副作用函数重新排进调度队列。
>
> **异步批量** —— 同一个 tick 内的多次修改会被合并，在微任务里统一 flush，所以改三个值只重渲染一次。
>
> 相比 Vue2 的优势：能拦截属性新增和删除（Vue2 要 `$set`）、能拦截数组索引赋值和 `length`、惰性代理嵌套对象（用到才递归，大对象不用一上来就全遍历）。
>
> 和 React 的根本差别：Vue 是**推**——数据变了精确知道哪些组件要更新；React 是**拉**——状态变了整棵子树重新执行然后 diff。所以 Vue 不需要 `useMemo` 这类手动优化，但 React 的模型更简单更可预测。

**D3「Pinia 和 Vuex 有什么区别？为什么用 Pinia？」**

> Pinia 是 Vue 官方现在推荐的，三个实际差别：没有 mutation，直接改 state；TypeScript 类型推断天然成立，不用手写一堆泛型；没有嵌套模块，store 就是扁平的多个。
>
> 我这个项目有 5 个 store：`auth`（当前商家和令牌）、`chat`（会话消息）、`knowledge`（知识库编辑态）、`analytics`（看板数据）、`locale`（显示语言）。
>
> 有个设计我比较满意：**凭证不是直接 import store 拿的，而是注册了一个 provider 函数。** 因为 HTTP 请求可能在任何时刻发出，那时不一定在 Vue 组件的 setup 上下文里，隐式的 active pinia 取不到。所以 `main.ts` 里显式传 pinia 实例、注册一个 `() => ({...})` 的函数，请求瞬间现取。

**D4「前端性能做了什么优化？」**

> 最典型的是**首屏静态依赖门禁**。ECharts 很大，但首屏不需要图表——只有用户真的问了指标问题才需要。所以图表是懒加载的，而且我写了一个脚本 `scripts/check-first-paint.mjs` 扫生产构建，**阻止 ECharts 被预加载或经入口静态 import 链带入首屏**。
>
> 为什么要脚本而不是靠自觉？因为这种退化太容易发生了——某个组件不小心加一行顶层 import，整个懒加载就失效了，而且肉眼看不出来。**能自动化的约束就别靠人记。**
>
> 另外 SSE 流式本身也是感知性能优化——首字延迟从「等全部算完」压到 1 秒内。

**D5「TypeScript 类型安全了，为什么还要 zod 做运行时校验？」** ⭐ 好问题

> 因为 **TypeScript 的类型在编译后就消失了**。它保护的是我写代码的时候，保护不了运行时。后端返回的数据到底符不符合声明的类型，TS 管不了——它只是相信我写的类型声明。
>
> 所以边界上要用 zod 再校验一遍。这和后端用 Pydantic 校验模型输出是**完全同一个思路**：不信任外部来的数据，无论外部是用户、是模型、还是自己的后端。
>
> 我的契约链是这样的：后端 Pydantic → OpenAPI → 自动生成 TS 类型 → Adapter 层转换 → 领域模型。组件禁止直接消费生成类型。这样后端改字段，Adapter 的契约测试会立刻暴露不兼容。

### E · 后端 / 数据库类（5 问）

**E1「MySQL 熟吗？我们这边用 MySQL」**
→ 见[第七节 · 缺口 3](#缺口-3--用的是-postgresql-不是-mysql)。

**E2「数据库优化做过什么？」**

> 我这个项目数据量还没到需要大幅调优的程度，所以我做的是**预防性的**而不是救火式的：
>
> **① 约束下推。** 能让数据库拦的就别指望代码记得拦——NOT NULL、UNIQUE、CHECK 约束。因为应用代码有几百个写入点，约束只写一次。这个判断被真实验证过：光「漏填 NOT NULL 列」这类缺陷就出现过 4 次，每次都是数据库先拦住，没有一次流到线上。
>
> **② 查询范围强制收敛。** 日期跨度有上限、返回行数有上限，都在查询服务层强制，模型和用户都改不了。这从根上杜绝了全表扫。
>
> **③ 幂等唯一约束。** `answers` 表有 `client_request_id` 的唯一约束，用来做请求重放的幂等——网络重试不会产生两条回答。
>
> **④ 汇总表。** Chat BI 看板不实时聚合原始表，而是有一张日粒度的 `chatbi_qa_daily` 汇总表，由独立的 Cron 幂等重刷。这是最典型的「用空间换查询时间」。

**E3「异步用在哪里？为什么全异步？」**

> FastAPI + SQLAlchemy Async + psycopg 全链路异步。核心价值是**在等待时释放 CPU**——一次问答里有 4 次模型调用，每次几百毫秒到几秒，同步模型下这段时间线程就白占着。异步让同样的机器能服务多得多的并发。
>
> 但异步也有坑，我踩过一个很典型的：Windows 默认的 `ProactorEventLoop` 和 psycopg 的异步模式不兼容，直接起 uvicorn 会导致数据库静默降级——注意是**静默**，接口还能通，只是降级了。所以我写了专门的启动入口 `app/run.py`，显式传事件循环工厂给 `uvicorn.run(loop=...)`。
>
> 这件事也再次印证了那条原则：**静默降级是最难查的 bug。**

**E4「迁移怎么管理的？线上怎么发布？」**

> Alembic，现在 18 个版本。规则是**迁移在发布阶段执行，不能让每个 Worker 同时执行**——多实例同时跑迁移会互相冲突。
>
> 另外数据库连接必须有启动重试，因为部署时数据库可能比应用晚就绪几秒，没有重试就是一次无谓的启动失败。

**E5「怎么做的测试？1128 个测试都测什么？」**

> 分四层，目录就是这么分的：
>
> | 目录 | 文件数 | 测什么 |
> | --- | --- | --- |
> | `unit/` | 96 | 单函数、单节点、纯逻辑 |
> | `api/` | 28 | 接口契约、鉴权、错误格式 |
> | `integration/` | 33 | 真实 PostgreSQL 上的端到端 |
> | `support/` | 4 | 测试基础设施 |
>
> 重点覆盖的是**反例**而不是正例：跨商家访问必须 403、SQL 白名单外的列必须被拒、日期超限必须被截断、Reviewer 重试超上限必须降级、数据库不可用必须显式降级、模型输出非法 JSON 必须能处理。
>
> **正例证明功能能用，反例证明边界守得住。** 后者才是生产系统的价值所在。

### F · 工程质量 / 协作类（3 问）

**F1「这个项目你觉得做得不好的地方？」** ⭐ 必答好，别说「没有」

> 三个。

> **① 集成测试静默跳过。** 集成测试依赖真实 PostgreSQL，本机 Docker 不可用时会自动跳过——注意是静默跳过，测试报告还是绿的。结果有一段时间，好几个 Task 的工作从来没在真实库上验证过。后来第一次跑通就暴露了 2 个真实缺陷，其中一个挺严重：翻译降级时把商家自己的原话替换成了「翻译暂不可用，请重试」。

### H · 业务理解类（2 问）

**H1「你怎么识别一个业务场景能不能 AI 化？」**（对应工作职责第 1 条）

> 我的判断有三条：
>
> **① 瓶颈是不是在「翻译」上。** 我这个项目的四个痛点，共同特征是卡在自然语言和结构化数据之间。这种场景大模型有绝对优势。反过来，如果瓶颈是数据本身没有、或者规则本身没定义清楚，AI 解决不了。
>
> **② 错了的代价能不能承受、能不能被发现。** 经营数据分析这个场景，错了代价很大（商家会拿去做决策），所以必须配校验、复核和可见降级。如果是「推荐几个可能相关的文档」这种，错了代价小，可以更激进。
>
> **③ 有没有可枚举的输出空间。** 能把模型的输出约束成有限枚举的场景，工程上可控得多。完全开放的自由文本生成，质量保障成本会高一个数量级。

**H2「如果让你在我们这边做一个 AI 项目，你会怎么开始？」**

> 我会按三步走：
>
> **第一步，找一个「高频 + 低风险 + 有明确基线」的场景做试点。** 高频保证有数据能迭代，低风险保证做砸了不伤业务，有明确基线保证能判断好坏——不能是「感觉变好了」。
>
> **第二步，先把防线做出来再做功能。** 我这个项目的顺序是：工程骨架 → 身份隔离 → 数据模型 → 隔离反例测试 → 契约 → UI 联调 → 意图 → 安全查询 → 回答与 Reviewer → 费用防护 → 部署。**可信身份排在任何数据查询之前**，因为补隔离要重写整个数据层。
>
> **第三步，真实验收要早做但要小做。** 早做是因为 mock 测不出模型的真实行为；小做是因为它花钱。我的比例是 1128 个免费测试配 14 个付费场景。

## 七、三个缺口的诚实话术

> **总原则：主动承认 + 给出你已经理解的部分 + 说明你的补法。**
> 藏缺口的代价远大于承认。

### 缺口 1 · 没有向量数据库 / RAG 实战

**先讲你的判断（这是强项）**，再承认缺口：

> 我刻意没有用向量库，因为我的知识域是闭集，而且第 3 步闸门的判定必须 100% 可复现。这个决策我记录在案。
>
> 向量库本身我是理论层面熟悉——embedding 把语义映射到高维空间，用余弦相似度召回，HNSW 或 IVF-Flat 做近似最近邻索引，pgvector 能直接在 PostgreSQL 里做所以不用额外引组件。生产场景通常会做 hybrid：BM25 关键词召回加向量召回，再用 rerank 模型重排。
>
> 但我确实**没有在生产项目里真正跑过**，这是我接下来想补的。

**面试前必须能接住两层追问的词**：

| 概念 | 一句话理解 |
| --- | --- |
| Embedding | 把文本映射成高维向量，语义相近的向量距离近 |
| 余弦相似度 | 比较两个向量的方向夹角，不看长度 |
| HNSW | 分层可导航小世界图，近似最近邻的主流索引，快但不保证精确 |
| IVF-Flat | 先聚类分桶再桶内暴力搜，内存省但召回率略低 |
| Chunking | 长文档切块策略，块太大稀释语义、太小丢上下文 |
| pgvector | PostgreSQL 的向量扩展，不用额外组件 |
| Hybrid search | 关键词召回 + 向量召回合并，互补各自的盲区 |
| Rerank | 用更贵的交叉编码器模型对召回结果重排，提精度 |

### 缺口 2 · 没有 React 项目经验

> 我这个项目是 Vue3 + TypeScript，Composition API、Pinia、手写组件不用 UI 库。React 我理解它的模型——函数组件加 hooks，和 Vue3 的 Composition API 心智很接近，主要差别在响应式实现：Vue 是 Proxy 做依赖收集自动追踪，属于「推」；React 是显式依赖数组加重渲染加 diff，属于「拉」。所以 Vue 不需要 `useMemo` 这类手动优化，但 React 的模型更简单更可预测。
>
> 真正可迁移的是框架之下的东西：组件拆分粒度、状态该放哪一层、什么时候该提到全局、渲染时序、内存泄漏。
>
> 举个具体的：我做语言切换时踩过一个坑——恢复语言必须在 `mount()` 之前**同步**完成，否则首帧会闪一下中文再跳英文。这类问题在 React 里是一模一样的，换个框架不会消失。

### 缺口 3 · 用的是 PostgreSQL 不是 MySQL

> 我这个项目用的是 PostgreSQL，13 张表、18 次 Alembic 迁移，ORM 是 SQLAlchemy 2 全异步。
>
> 关系型数据库的核心能力是通用的——索引设计、约束下推、查询计划、连接池、事务隔离。我在这个项目里比较刻意的一点是**把能让数据库拦的约束都放在数据库层**，因为应用代码有几百个写入点，约束只写一次。这个判断被验证过 4 次。
>
> MySQL 和 PG 的差异我清楚：默认事务隔离级别（MySQL 是 RR，PG 是 RC）、JSON 支持的成熟度、窗口函数的版本门槛、`ON DUPLICATE KEY UPDATE` 对应 PG 的 `ON CONFLICT DO UPDATE`、以及 MySQL 的 InnoDB 聚簇索引导致主键选择更敏感。迁移过去不是问题。

## 八、反问面试官

> **一定要问。** 不问会被理解成不在意这个机会。挑 3 个，**优先前两个**。

1. **「团队现在的 AI 能力是怎么落地的？是每个业务线各自接模型，还是有统一的中台？」**
   → 直接对应 JD 里的「AI 中台建设经验」和「标准化、规模化」，问了说明你在想职责第 3 条。

2. **「AI 项目的效果怎么衡量？有没有明确的基线？」**
   → 让面试官意识到你想的是落地而不是炫技。而且他的回答能让你判断这个团队成不成熟。

3. **「成本是怎么管的？有没有预算约束和熔断机制？」**
   → 承接你项目里最有特色的部分，自然带出三层预算防线。

4. 「这个岗位入职后前三个月最希望解决的问题是什么？」

5. 「全栈的边界在哪里？是一个人端到端，还是和前端后端团队协作？」
