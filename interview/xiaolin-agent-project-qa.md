## 1. Borough 到底算不算 Agent，还是只是给大模型套了一个聊天页面？

**来源文章：** [1. 什么是 Agent？与大模型有什么本质不同？](https://xiaolinnote.com/ai/agent/1_whatisagent.html)

**项目状态：** 已实现（受约束的工作流型 Data Agent）

### 详细解答

面试时可以先给结论：Borough 不是一次 Prompt 直接生成答案的聊天壳，而是一个由后端编排、能检索知识、查询经营数据、校验结果、生成回答并持久化状态的 Data Agent；但它也不是让模型自由决定无限步行动的通用自主 Agent。

普通 LLM 调用的核心是“输入文本，输出文本”。Borough 在模型之外增加了身份与商家范围校验、知识检索、结构化意图、受控查询、图表和建议生成、独立 Reviewer、结果持久化与异步记忆沉淀。模型在部分节点负责概率性判断和生成，程序负责真正执行查询、权限控制和状态流转，执行结果再影响后续回答与质量状态，因此具备“感知—决策—行动—反馈”的闭环。

它的自主性是刻意受限的。图的节点顺序和允许的分支由开发者固定，模型不能临时发现任意工具、执行任意 SQL 或无限循环。对商家经营分析这种高数据安全、强口径约束的场景，可控性比“什么都让模型决定”更重要。

- [结构化 AgentState](../backend/app/agent/state.py)
- [Agent 主流程回归测试](../backend/tests/unit/agent/test_graph.py)
- [项目产品定义与核心流程](../docs/PRD.md)

### 设计取舍与缺口

当前称为“工作流型 Agent”最准确。它已经超出聊天机器人，但没有通用 ReAct 工具循环、开放式行动空间和任意长任务自主规划。只有未来加入更多异构工具、跨步骤动态重规划，而且评测证明固定流程限制了任务成功率时，才值得提升自主性。

### 可能追问

- 追问：只要用了 LangGraph 就算 Agent 吗？
  - 答题要点：不算。框架只是编排工具，关键要看系统是否维护状态、作出决策、执行外部动作并根据结果继续处理。
- 追问：这个 Agent 的“行动”是什么？
  - 答题要点：当前主要是只读动作，包括知识检索、受控经营查询、生成图表描述、保存回答和记忆；没有退款、改价等高风险写动作。

## 2. Borough 的 Agent 由哪些核心组件构成，它们在代码里分别落在哪里？

**来源文章：** [2. Agent 的基本架构由哪些核心组件构成？](https://xiaolinnote.com/ai/agent/2_components.html)

**项目状态：** 已实现

### 详细解答

可以按“模型、规划、工具、记忆”四部分回答。模型层由 DeepSeek 兼容客户端承载，分别服务于意图理解、回答生成、Reviewer 和记忆整理；规划层不是自由生成步骤，而是先把问题转为经过 Pydantic 校验的 `QueryIntent`，再由固定图决定后续节点；工具层是后端知识检索、指标目录、受控查询、可视化和持久化服务；记忆层包括会话与回答持久化，以及按商家、业务分类保存的长期记忆。

LangGraph 负责把这些部分组织成一条有类型的状态流。`AgentState` 保存问题、意图、知识、查询结果、质量状态、预算和执行步骤；节点只能通过这份状态交换结果。这样既能在 SSE 中展示处理轨迹，也能在单个节点出问题时明确降级原因。

这里要特别强调：System Prompt 只是模型组件的一部分，不是整个 Agent。权限、预算、SQL 安全、重试上限和商家隔离都必须由程序保证，不能交给 Prompt。

### 设计取舍与缺口

组件边界已比较清楚，但“规划”目前更接近结构化路由计划，而不是可递归拆解任意任务的 Planner；“工具”也没有用通用 Function Calling 动态注册。对当前稳定的电商经营域，这是减少不确定性的合理选择。

### 可能追问

- 追问：哪个组件是事实源？
  - 答题要点：经营数据库、指标目录和人工知识库是事实源；模型只做理解与表达，不能凭自己成为事实源。
- 追问：为什么要有显式 AgentState？
  - 答题要点：避免节点间传无类型字典；让输入输出、失败状态、预算和可观测字段可测试、可追踪。

## 3. Workflow、Agent 和 Tools 在 Borough 里分别是什么，为什么不让模型决定所有下一步？

**来源文章：** [3. Workflow，Agent，Tools 这三个的概念和区别介绍一下？](https://xiaolinnote.com/ai/agent/3_workflow_tools.html)

**项目状态：** 已实现

### 详细解答

三者最清晰的区分维度是“谁决定下一步”。Tool 是一个只负责执行的能力单元，本身不做决策；Agent 会结合目标和观察选择下一步；Workflow 则由开发者预先规定节点和主要流向。

在 Borough 中，`SafeQueryService`、知识检索、指标目录和持久化都可视为工具性能力。模型没有直接拿到这些服务的执行权，而是输出结构化意图；LangGraph Workflow 决定先检索索引、做范围闸门、分类和理解，再校验、查数据、生成和复核。唯一明显的条件分支之一是前置闸门：范围外问题直接跳过全部 LLM 节点，进入推荐问题与持久化。

不让模型决定所有下一步，主要因为数据分析链有严格顺序：必须先确定可信商家身份，再校验意图，再查受控数据，最后才能声称得到结论。若让模型自由跳过节点，它可能在没有数据时直接生成数字，也可能遗漏租户过滤或质量复核。

### 项目证据

- [图节点顺序和前置闸门条件边](../backend/app/agent/graph.py)
- [零 LLM 问题范围闸门](../backend/app/agent/prefilter.py)
- [安全查询工具边界](../backend/app/services/safe_query.py)
- [闸门拒答图回归](../backend/tests/unit/agent/test_graph_prefilter_rejection_response.py)

### 设计取舍与缺口

这种实现牺牲了开放域灵活性，换来路径可预测、测试容易、成本上限可计算和权限边界稳定。当前没有必要把这些后端服务包装成模型可自由选择的通用 Tools；若未来工具种类大量增长，可在“必要工具最小暴露”的前提下引入动态路由。

### 可能追问

- 追问：固定 Workflow 还有“智能”吗？
  - 答题要点：有。问题分类、结构化理解、回答组织和复核仍由模型完成，只是安全关键的顺序由程序掌控。
- 追问：前置闸门失败会不会误拒？
  - 答题要点：已有会话、问候语、语料不可用等情况会放行；拒答路径记录分数和阈值但不记录问题原文，便于调优并保护隐私。

## 4. Borough 采用了 ReAct、Plan-and-Execute 还是 Reflection？为什么这样选？

**来源文章：** [6. ReAct、Plan-and-Execute、Reflection 三种范式有什么核心区别？实际项目中该如何选型？](https://xiaolinnote.com/ai/agent/6_three_patterns.html)

**项目状态：** 已实现（固定 Workflow + 受控规划 + Reflection 的混合方案）

### 详细解答

Borough 不是标准 ReAct。它没有“思考—任意选工具—观察—再选工具”的开放循环，而是固定节点依次运行，因此不会由模型无限扩展行动路径。它也不是完整的通用 Plan-and-Execute，因为模型不会生成任意步骤列表；最接近规划的部分是两阶段意图识别和结构化查询计划，执行器再按安全模板查数据。

它明确使用了 Reflection 思路：先生成回答草稿，再做本地确定性校验和独立 Reviewer 复核；不通过时把具体问题反馈给下一轮生成，达到上限后返回确定性降级摘要。Reflection 在这里是质量增强层，而不是独立 Agent。

选型理由来自业务特征。经营分析流程固定、数据边界严格，所以固定 Workflow 更适合；意图和自然语言表达有不确定性，因此在局部使用 LLM；数字准确和建议可解释性要求较高，所以在最终回答上叠加有限 Reflection。这样比全量 ReAct 更容易算清最坏调用次数和 Token 成本。

### 项目证据

- [固定图和结构化执行链](../backend/app/agent/graph.py)
- [回答质量循环](../backend/app/services/quality_loop.py)
- [质量循环测试](../backend/tests/unit/services/test_quality_loop.py)
- [调用次数与质量轮次联动配置](../docs/deployment.md)

### 设计取舍与缺口

当前方案适合“问题域有限、动作可枚举、错误代价高”的场景。若未来出现长报告、多数据源研究或多个互相独立的子任务，可以增加显式 Planner 和有条件 Replan，但应先用评测证明固定图已经成为瓶颈。

### 可能追问

- 追问：为什么不直接上 ReAct？
  - 答题要点：自由循环会增加重复调用、延迟、成本和越权面；当前查询路径可预定义，没有足够收益抵消这些风险。
- 追问：Reflection 为什么必须有限轮？
  - 答题要点：每轮至少增加生成和复核调用；无限反思可能为了修改而修改，也会造成成本不可控。

## 5. Borough 如何拆解复杂经营问题？它支持动态任务拆分吗？

**来源文章：** [7. 复杂任务怎么做的任务拆分？为什么要拆分？效果如何提升？](https://xiaolinnote.com/ai/agent/7_tasksplit.html)

**项目状态：** 部分实现

### 详细解答

当前实现主要采用静态拆分。一次提问被分成范围判断、业务分类、结构化理解、白名单校验、知识检索、经营查询、回答生成、质量复核、推荐问题和持久化等原子节点。每个节点有明确职责与可测试输出，失败时可以定位到具体环节，而不是让一个超长 Prompt 同时做理解、查数和写结论。

在查询内部，Borough 也支持受控的“计划”。例如跨业务查询只允许订单到退款、订单到商品或订单—退款—商品三种计划；对比分析会由后端解析当前周期和基准周期；生成指标也只能在固定交易或退款聚合模板中选择。模型表达意图，后端验证并执行。

它尚未实现通用动态任务树、依赖图并行调度或执行中 Replan。原因是当前核心问答大多是强顺序依赖：没有意图就不能确定检索域，没有可信查询结果就不能生成数据结论。盲目并行会牺牲正确性，而且增加数据库与模型并发成本。

### 项目证据

- [Agent 原子节点拆分](../backend/app/agent/graph.py)
- [结构化查询意图与受控计划](../backend/app/intent/models.py)
- [跨业务和指标查询执行](../backend/app/services/safe_query.py)
- [跨业务查询回归](../backend/tests/integration/services/test_safe_query.py)

### 设计取舍与缺口

现状的拆分粒度适合可预测的经营问答。真正需要动态拆分的信号包括：单问题必须访问多个独立外部数据源、固定节点经常出现无关工作、或长报告任务的失败无法归因。届时应让 Planner 同时产出步骤验收标准和依赖关系，而不是只生成自然语言清单。

### 可能追问

- 追问：为什么拆得越细不一定越好？
  - 答题要点：节点越多，模型调用、序列化、状态维护和跨节点信息损失越大；应以职责单一且可独立验收为粒度。
- 追问：当前哪些步骤可以并行？
  - 答题要点：需基于 Trace 证明依赖关系后再决定；例如某些只读辅助检索理论上可并行，但主意图—查询—回答链不能强行并行。

## 6. Borough 不使用 LangChain Memory，那么短期记忆和长期记忆是怎么实现的？

**来源文章：** [8. AI Agent 的记忆机制应该如何设计？](https://xiaolinnote.com/ai/agent/8_memory.html)、[9. Agent 的长短期记忆系统怎么做的？](https://xiaolinnote.com/ai/agent/9_memory_storage.html)

**项目状态：** 已实现

### 详细解答

短期记忆和长期记忆在 Borough 中不是一个中间件概念，而是不同生命周期的数据。

短期层包含本轮 `AgentState` 和持久化会话。`AgentState` 只服务一次图执行，保存当前问题、意图、知识、查询结果、预算和质量结果；Conversation、Message 和 Answer 则保存跨请求的会话历史，支持历史列表、详情和幂等重放。当前图不会把全部历史原文重新塞给每次模型调用，因此它避免了无限增长的 messages，但连续追问的语义利用仍有限。

长期层是 `MerchantMemory`。回答完成后，后台记忆任务会读取同一商家、同一业务分类的近期历史回答，与人工补充内容一起压缩为一份分类记忆，通过 `(merchant_id, category)` 唯一约束保存。检索时人工知识库优先，只有人工库未命中才使用当前商家的记忆作为 fallback，并在 `analysis_sources` 和质量备注中如实标明。

这说明记忆能力并不依赖 LangChain。关键是清楚定义保存内容、作用域、召回条件、冲突优先级和失败降级。

### 设计取舍与缺口

已具备短期持久化和长期记忆，但还不是完整的对话状态理解系统。当前缺少把关键历史约束选择性注入意图和回答 Prompt 的统一上下文装配器，也没有显式的记忆失效、遗忘和用户纠错接口。

### 可能追问

- 追问：为什么长期记忆不直接覆盖人工知识？
  - 答题要点：自动记忆来自模型归纳，可信度低于人工维护事实；只能作为未命中时的候选背景。
- 追问：怎么避免商家 A 召回商家 B 的记忆？
  - 答题要点：身份来自已验证上下文，所有记忆读写都带 `merchant_id`，数据库唯一约束和跨商家测试共同锁定边界。

## 7. Borough 的长期记忆按什么粒度保存，如何压缩、召回和防止旧记忆污染回答？

**来源文章：** [12. Agent 记忆压缩通常有哪些方法？](https://xiaolinnote.com/ai/agent/12_memcompress.html)

**项目状态：** 部分实现

### 详细解答

Borough 选择的是“结构化分桶 + 摘要压缩”，而不是保存无限聊天原文。每个商家、每个业务分类最多维护一份长期记忆，粒度由 `(merchant_id, category)` 决定。后台任务取同一范围内的近期问答和人工补充内容，交给独立记忆整理 Prompt 归纳，并固定加上“本轮自动沉淀”标记。若 LLM 不可用，则保存可识别的确定性 fallback，而不是把失败伪装成成功压缩。

召回不是全量注入。知识检索先查人工维护的业务知识；只有目标业务域没有命中人工文档时，才加载当前商家的分类记忆。前置范围闸门也可以读取该商家的全部记忆参与相关性评分，但返回的只是范围判断，不会让记忆绕过后续意图和查询校验。

当前防污染主要依靠三层边界：商家隔离、分类隔离、人工知识优先。它尚未实现按时间衰减、事实有效期、单条重要性评分、语义向量召回或用户显式删除某条记忆。因此不能说已经完整解决“旧记忆过期”问题。

- [MerchantMemory 模型与唯一约束](../backend/app/models/knowledge.py)
- [记忆 upsert 与商家范围](../backend/app/repositories/memory.py)
- [记忆压缩和降级](../backend/app/services/memory_service.py)
- [记忆 Prompt 的人工内容优先规则](../backend/app/prompts/memory.py)
- [记忆预算回归](../backend/tests/integration/services/test_memory_agent_budget.py)

### 设计取舍与缺口

一分类一份文档实现简单、检索成本低，也与当前有限业务域匹配；代价是细粒度事实可能在反复摘要中丢失或被旧结论覆盖。后续若记忆量和个性化需求增长，应拆成原始事件、稳定事实和压缩摘要三层，并引入有效期、来源、置信度和可撤销机制，而不是只把窗口调大。

### 可能追问

- 追问：这是不是向量数据库长期记忆？
  - 答题要点：不是。当前是 PostgreSQL 中按商家和分类保存的 Markdown 记忆，并使用确定性相关性检索；不能把通用方案中的向量库说成项目现状。
- 追问：为什么压缩也要走费用防护？
  - 答题要点：它仍是真实 LLM 调用，会消耗每日预算；失败时必须记录用量并显式降级。

## 8. Borough 为什么当前采用 Single-Agent，而没有拆成 Multi-Agent？什么时候才应该拆？

**来源文章：** [11. 说说 Single-Agent 和 Multi-Agent 的设计方案？](https://xiaolinnote.com/ai/agent/11_single_multi.html)

**项目状态：** 已实现（当前选择 Single-Agent/中心化编排）

### 详细解答

当前核心问答是一个中心化 `MerchantQaGraph`，多个节点共享同一份 `AgentState`。意图识别器、回答生成器、Reviewer 和记忆整理员是不同角色或模型调用点，但不是能独立接收目标、互相通信和自治调度的多个 Agent。特别是 Reviewer 只负责质量判定，不能因为“用了第二次 LLM 调用”就称为 Multi-Agent。

选择 Single-Agent 的原因是任务域和执行链都比较清楚：商家问题最终落到知识问答、指标或明细查询，关键步骤有强依赖，权限和预算还要在一个中心统一控制。拆成多个 Agent 会增加上下文复制、状态一致性、失败协调、重复查询、Token 和 Trace 复杂度，却没有证据表明当前质量或吞吐因此受限。

真正值得拆分的触发条件应是可测量的：某类任务需要完全不同的专业上下文；单一上下文经常超限；存在多个独立子任务可安全并行；或某个节点的容量、延迟、发布节奏需要独立扩缩容。即使拆，也应优先采用中心 Orchestrator + 专职 Worker，让商家身份、预算、完成标准和最终汇总仍由中心掌控。

- [单一 MerchantQaGraph 编排](../backend/app/agent/graph.py)
- [共享 AgentState](../backend/app/agent/state.py)
- [独立 Reviewer 的有限职责](../backend/app/services/review_service.py)
- [后台记忆任务](../backend/app/services/memory_agent.py)

### 设计取舍与缺口

现状没有 Multi-Agent，也没有必要为了简历术语强行引入。若未来做跨平台竞品研究、多文件并行分析或多个数据源的独立分析，可以先把瓶颈节点拆成 Worker；不要直接采用去中心化 Agent 互聊，因为租户隔离和完成确认会更难证明。

### 可能追问

- 追问：异步 MemoryAgent 算第二个 Agent 吗？
  - 答题要点：名称上叫 Agent，但架构上更像受主流程触发的后台整理任务；它没有参与当前回答的动态协商。
- 追问：Multi-Agent 一定更快吗？
  - 答题要点：不一定。只有独立子任务并行收益大于调度、上下文和汇总开销时才会更快。

## 9. Borough 使用了 LangGraph，为什么核心逻辑仍然大量手工实现？

**来源文章：** [13. 为什么有时候选择“手搓”Agent，而不是直接用成熟框架？](https://xiaolinnote.com/ai/agent/13_handcode.html)

**项目状态：** 已实现（框架编排、核心规则手写）

### 详细解答

Borough 不是“完全不用框架”，也不是“把一切交给框架”。LangGraph 只负责图和状态流转；真正决定业务正确性的部分——结构化意图、白名单、查询模板、商家隔离、回答事实包、本地数字校验、预算记账、失败降级和幂等持久化——都由项目代码显式实现。

这种边界适合生产型 Data Agent。通用框架可以减少节点和循环的样板代码，但它不了解 Borough 的指标口径、演示身份模型、跨商家风险、查询上限和用户可见降级契约。若这些规则藏在框架默认行为里，升级或异常时很难判断到底是模型、框架还是业务代码出了问题。

手写核心逻辑也让测试可以绕开真实模型：Fake LLM 只返回固定结构，单元测试分别验证 Prompt 契约、Pydantic 解析、白名单、安全查询、质量循环和费用防护。这样框架升级的影响集中在图适配层，业务不变量仍由自己的测试锁住。

优势是链路透明、可裁剪和安全边界清楚；代价是团队要自己维护更多状态、重试和观测代码。未来可以使用成熟 tracing 或文档解析组件，但不应把租户授权、SQL 安全或完成判定委托给通用 AgentExecutor 的黑盒默认值。

## 10. Borough 如何赋予模型“规划能力”，为什么没有采用 CoT、ToT 或 GoT？

**来源文章：** [14. 如何赋予 LLM 规划能力？](https://xiaolinnote.com/ai/agent/14_planning.html)

**项目状态：** 已实现（受控结构化规划）；通用多路径规划未实现

### 详细解答

Borough 所需的规划不是让模型公开输出长篇思维链，而是把自然语言问题转成可验证的执行意图。第一阶段识别回答模式、业务域和关键词；第二阶段输出严格的 `QueryIntent`，包含指标、维度、筛选、日期、排序、数量限制、对比方式以及少量受控计划。Pydantic 禁止额外字段，白名单继续校验业务值，后端再把合法意图映射为固定查询。

这相当于“模型提出计划草案，程序验证并执行”。CoT 的内部推理过程既不是可靠审计证据，也可能增加输出 Token；ToT/GoT 需要生成、评估多条路径，会显著增加调用次数和延迟。当前任务空间本来就能用 Schema 和模板枚举，没有必要为简单指标查询探索多棵推理树。

项目还对结构化调用关闭 thinking 并请求 JSON 输出，重点是稳定拿到协议，而不是收集推理文本。对比周期、聚合公式和查询范围最终由后端计算，模型不能自行编造。

- [两阶段意图服务与有限重试](../backend/app/intent/service.py)
- [意图 Prompt 的完整 JSON 契约](../backend/app/intent/prompts.py)
- [QueryIntent 严格模型](../backend/app/intent/models.py)
- [意图白名单和范围钳制](../backend/app/intent/whitelist.py)
- [结构化调用配置](../backend/app/llm/deepseek.py)

### 设计取舍与缺口

当前规划能力适用于封闭业务域，不适用于“生成一份跨十个网站的完整市场研究”这类开放长任务。未来若需要多路径探索，应只在难题切片启用，并同时设置路径数、总 Token、总时限和可验证的选优标准。

### 可能追问

- 追问：结构合法就代表意图正确吗？
  - 答题要点：不代表。Schema 只保证形状，白名单保证允许范围，语义准确率仍要靠真实问题集评估。
- 追问：为什么禁止模型输出 SQL？
  - 答题要点：SQL 是执行细节和安全边界；模型只表达业务意图，后端模板才能确保租户、表列、日期和行数限制。

## 11. Borough 的 Reflection 和 Reviewer 怎么定义成功、失败与停止？失败后会转人工吗？

**来源文章：** [15. Agent 的反思机制为什么要用、怎么实现？](https://xiaolinnote.com/ai/agent/15_reflection.html)

**项目状态：** 部分实现（自动质量闭环已实现，正式转人工未实现）

### 详细解答

当前成功条件不是“模型觉得答案不错”，而是三项同时满足：回答草稿能解析为约定 Schema、本地确定性校验没有问题、独立 Reviewer 返回 `passed=true` 且没有 issues。只要任何一项不满足，本轮就被打回；下一轮生成会收到上一版输出和明确问题，属于有反馈的改进，而不是盲目重抽样。

停止条件也由程序控制。质量循环最多运行配置的轮数，默认两轮；如果模型或 Reviewer 不可用、单请求预算或每日预算耗尽、输出持续无法通过校验，就返回由当前查询事实生成的确定性摘要，标记 `quality_status=DEGRADED`，同时给出 attempts、notes 和 degraded_reason。纯明细或范围外问题本来不需要生成式复核，状态为 `NOT_RUN`，这不等于失败。

项目目前没有工单、客服队列、人工接管按钮或 handoff 状态机，所以不能回答“已经自动转人工”。现有“需人工确认”只用于未验证临时指标的提示，也不构成正式转人工。合理的未来边界是：涉及写操作或高风险决策、同一请求多次校验失败、事实源冲突、权限无法确定、用户明确要求人工时，创建包含会话、已查证证据、失败原因和建议动作的人工任务；在人工接管前不得声称完成。

## 12. Borough 的上下文工程怎么做？是把 System Prompt、历史、知识和数据全部塞给模型吗？

**来源文章：** [17. Agent 的上下文工程怎么设计？](https://xiaolinnote.com/ai/agent/17_context_engineering.html)

**项目状态：** 部分实现

### 详细解答

Borough 已经按任务拆分上下文，而不是给每个模型同一份超长 Prompt。分类器看到业务索引和用户问题；结构化理解器看到目标业务域、相关知识、当前业务日期、字段契约和白名单；回答生成器只看到后端整理的事实包；Reviewer 看到同一事实包与候选答案；记忆整理员看到人工补充和同商家同分类历史。每个模型只获得完成该节点所需的信息。

上下文的信任级别也不同。System Prompt 规定角色和输出协议；用户问题、知识文档和数据库文本都属于待处理数据，不能改变程序权限。商家身份不从 Prompt 推断，查询服务也不会因为检索文本写着“忽略限制”就扩大数据范围。回答阶段使用后端事实包和数字白名单，减少原始明细直接进入模型造成的泄漏与幻觉。

但项目还没有统一 Context Builder、分区 Token 配额、全链路来源元数据、Observation Masking 或细粒度历史选择。尤其 `_load_context` 当前基本只记录步骤，完整对话历史没有按相关性注入意图和回答模型。因此现状应说“节点级上下文最小化已实现，成熟的动态上下文工程仍未完成”。

- [分类与结构化理解 Prompt](../backend/app/intent/prompts.py)
- [回答事实包构造](../backend/app/services/answer_service.py)
- [Reviewer 输入边界](../backend/app/services/review_service.py)
- [本轮状态字段](../backend/app/agent/state.py)

### 设计取舍与缺口

按节点最小化上下文能直接降低 Token 和注入面，适合当前固定图。下一步如果要强化连续追问，应先引入结构化会话摘要、有效约束和证据引用，而不是简单把全部历史拼回 messages。还应为每类上下文记录注入长度和来源，便于评估到底是召回错了还是模型执行错了。

### 可能追问

- 追问：Prompt Engineering 和 Context Engineering 有什么区别？
  - 答题要点：前者设计指令怎么写；后者决定本次调用看哪些指令、状态、记忆、工具结果和证据，以及它们的优先级与预算。
- 追问：为什么检索到的知识不能当 System 指令？
  - 答题要点：知识内容可能过期或被注入，只能作为数据；权限和执行策略必须在模型外固定。

## 13. Borough 如何管理多轮状态、幂等重放和中断恢复？

**来源文章：** [18. Agent 的多轮对话状态如何管理？如何防止跑偏并支持中断恢复？](https://xiaolinnote.com/ai/agent/18_session_state.html)

**项目状态：** 部分实现

### 详细解答

Borough 把“本轮执行状态”和“跨请求持久状态”分开。本轮由 `AgentState` 管理；跨请求则由 Conversation、Message 和 Answer 落 PostgreSQL。每次聊天带 `client_request_id`，服务端在商家范围内保存请求摘要与处理状态，状态包括 `PROCESSING`、`SUCCEEDED`、`FAILED_RETRYABLE` 和 `FAILED_FINAL`。

同一请求成功后再次提交，会直接重放已保存响应，不重复跑 Agent 和消耗 Token；相同 id 但请求内容不同会冲突；正在处理中的重复请求返回处理中；可重试失败可以把同一记录置回处理态后重跑；最终失败则重放稳定错误。并发首次提交通过数据库约束和冲突回读，避免两个请求同时执行。客户端在 SSE 中断时，服务会尽力把记录落为 `FAILED_RETRYABLE`，避免永久卡在 `PROCESSING`。

这已经解决了“整轮聊天请求”的幂等和恢复，但还不是通用长任务 checkpoint。LangGraph 的每个节点结果没有独立持久化，恢复通常是重跑整轮，而不是从 `query_data` 后继续；系统也没有 `WAITING_USER`、暂停后继续或有副作用工具回执核对。因此应准确描述为“请求级恢复已实现，步骤级恢复未实现”。

  - 答题要点：自然语言历史不能可靠表达哪个动作已提交、哪个结果待确认；恢复需要结构化状态和回执。

## 14. Borough 如何测试和迭代 Agent 与 Prompt，评测体系完整吗？

**来源文章：** [19. 如何评估一个 Agent 的效果？评测集和指标怎么设计？](https://xiaolinnote.com/ai/agent/19_evaluation.html)

**项目状态：** 部分实现

### 详细解答

项目目前采用分层测试。最底层用单元测试验证 Prompt 是否声明完整字段、枚举和 JSON 示例，并把示例重新交给 Pydantic 校验；意图服务测试非法 JSON、非法枚举、重试和降级；白名单与安全查询测试跨商家、注入、日期和行数上限；Agent 图测试路由、知识来源、数据查询和质量状态；API/集成测试验证幂等、SSE、持久化与权限。自动化测试全部使用 Fake 或 Mock LLM，不产生模型费用。

Prompt 迭代并不是凭感觉改文案。历史上真实 DeepSeek 验收暴露过模型自造字段、枚举值不合法、推理 Token 挤占正文、业务问题被错误判成 CHAT 等 Fake 无法覆盖的问题。修复方式是先收集真实失败，再补输出契约、纠正提示或后端规则，并增加回归测试。真实模型只在获得费用授权后做小样本定向验收，记录调用次数、Token、耗时和结果。

不过完整 Agent 评测还没有闭环。PRD 要求确定性路由回归 100%、真实模型意图准确率至少 90%，现有证据矩阵明确标记后者尚未由完整问题集验证。当前也没有一个版本化的离线数据集，系统化记录目标意图、允许轨迹、禁止动作、外部最终状态和人工标注；线上 Chat BI 的点赞与 Reviewer 通过率也不能冒充真实准确率。

## 15. Borough 怎么防止路径震荡、重复调用和死循环？

**来源文章：** [20. Agent 为什么会出现路径震荡、重复调用和死循环？怎么检测和治理？](https://xiaolinnote.com/ai/agent/20_loop_stability.html)

**项目状态：** 已实现（针对当前固定图的有界治理）

### 详细解答

当前架构首先通过“没有开放式 ReAct 循环”降低死循环风险。LangGraph 主路径节点固定且只执行一次，前置闸门只有两个明确出口；真正会重复的地方是意图解析重试和回答质量循环，它们都有硬上限。

项目还同时设置三类预算：单请求最大 LLM 调用次数、单请求最大 Token、全局每日 Token。质量循环默认两轮，结构化意图也只有有限重试；任何一类预算耗尽都会停止模型调用并返回可见降级，而不是继续空转。`client_request_id` 防止客户端重试造成同一成功请求再次执行，后台记忆失败也只记录告警，不反向拖住主回答。

因此当前治理主要是“按结构保证有界”，尚未实现适用于自由 Agent 的进展检测，例如动作指纹、相似输出、状态差异、Agent 交接图和无新证据判定。因为当前没有动态工具环，这不是缺陷；若以后引入 ReAct 或 Multi-Agent，就必须在硬预算之前增加“是否取得进展”的软检测和换路策略。

- [有限意图重试](../backend/app/intent/service.py)
- [有限质量循环](../backend/app/services/quality_loop.py)
- [单请求预算模型](../backend/app/llm/client.py)
- [配置中的最坏调用路径](../docs/deployment.md)
- [幂等重放测试](../backend/tests/integration/services/test_chat_service.py)

### 设计取舍与缺口

最大步数只能兜底，不能证明任务在推进。若未来增加动态循环，状态中应记录标准化动作、结果摘要、完成标准差距和累计预算；临时限流可以有界退避，参数错误应直接修正，连续无进展则换工具或 Replan，预算耗尽后停止并转用户或人工处理。

### 可能追问

- 追问：相同工具调用两次一定是死循环吗？
  - 答题要点：不一定，分页或临时错误重试可能合理；关键要看是否产生新证据或让状态更接近完成。
- 追问：预算控制和循环检测有什么区别？
  - 答题要点：预算保证最终能停；循环检测要在烧完预算前识别无进展并改变策略。

## 16. 线上 Agent 变慢或 Token 突增时，Borough 现在能怎么定位？还缺什么 Trace？

**来源文章：** [21. 线上 Agent 延迟明显升高时，如何通过 Trace 定位和优化？](https://xiaolinnote.com/ai/agent/21_agent_latency_trace.html)

**项目状态：** 部分实现

### 详细解答

Borough 已有两类观测。持久层的 `llm_usage` 按业务日期记录模型、请求、商家、用途、输入/输出/总 Token、预留量、用量是否已知和成功状态；`llm_daily_budget` 给出当日累计 Token 和调用数。运行时 `OperationalMetrics` 记录限流命中、降级次数、错误码和各 Agent 节点平均耗时，管理员可通过 `/api/admin/ops/status` 查看当天 Token、剩余额度、调用数和节点均值。

排查时可以先看当日调用数与 Token 是否同步上涨，再结合节点平均耗时判断是意图、查询还是质量循环变慢，并按 `request_id` 查看具体 LLM 用量记录。若调用数上涨而单次 Token 稳定，优先排查重试或请求量；调用数稳定但 Token 上涨，检查上下文或输出；节点耗时上涨但 LLM 用量不变，则关注数据库或内部服务。

现状还不是完整分布式 Trace。运行时计数器只在单进程内存中，重启归零，多实例不聚合；只有平均值，没有 P50/P95/P99、TTFT、路由耗时输出、队列时间或每次调用的父子 Span，也没有统一 Trace ID 串联网关、检索、模型、SQL 和异步记忆。因此它能做基础状态查看，不能可靠分析长尾和关键路径。

### 项目证据

- [LLM 用量和每日预算模型](../backend/app/models/operations.py)
- [调用前预留、调用后结算](../backend/app/llm/guard.py)
- [进程内节点耗时指标](../backend/app/core/metrics.py)
- [管理员运维状态端点](../backend/app/api/routes/admin.py)
- [运维端点鉴权与响应测试](../backend/tests/api/test_admin_ops.py)

### 设计取舍与缺口

当前流量和单服务规模下，轻量指标满足基础运维；要支撑性能 SLO，应接入 OpenTelemetry 类链路，记录脱敏后的模型、Token、输入输出长度、节点、重试和错误类型，保留 Trace/Span 父子关系，并用分位数而非平均值做告警。日志不能保存完整 Prompt、密钥或完整经营结果。

### 可能追问

- 追问：为什么平均耗时不够？
  - 答题要点：少量几十秒慢请求可能被大量快请求稀释；用户体验通常由 P95/P99 长尾决定。
- 追问：看到模型 Span 最长就一定换模型吗？
  - 答题要点：不一定。还要拆分排队、TTFT、生成长度和重试，并确认它是否处于端到端关键路径。

## 17. Borough 如何避免“没有查数据却声称已经完成”的任务幻觉？

**来源文章：** [23. Agent 的“任务幻觉”是什么？如何避免没有执行工具却声称任务已经完成？](https://xiaolinnote.com/ai/agent/23_task_hallucination.html)

**项目状态：** 部分实现（当前只读分析链已防护，高风险动作闭环未建设）

### 详细解答

任务幻觉与普通事实幻觉不同：前者是把计划、尝试或未知状态说成外部动作已经完成。Borough 当前没有退款、改价、发券等写工具，主要风险是“没查到经营数据却编造已查询和数字”。

项目用程序状态约束这类声明。只有 `query_data` 实际返回 `QueryResult`，后续才会建立 `AnswerFacts`、标记数据库来源并进入生成式回答；查询服务缺失或拒绝时，响应会显示未执行查询或具体降级原因。回答生成只收到事实包，本地校验会检查日期、范围和所有数字是否来自查询结果或后端派生摘要，Reviewer 再做独立复核。纯明细正文按契约保持为空，避免模型补一句看似完成但无法证明的话。

不过这仍不等于完整“任务完成证明”。当前完成状态主要覆盖只读查询和回答持久化，没有外部写工具的执行回执、异步最终状态、部分成功、未知状态和人工审批。若未来允许有副作用动作，模型只能提出动作；调度层必须先登记 call id，用幂等键执行，再读取外部最终状态，只有 `VERIFIED` 才允许回复“已完成”。

### 项目证据

- [查询结果驱动回答与显式降级](../backend/app/agent/graph.py)
- [回答事实包和数字守卫](../backend/app/services/answer_service.py)
- [Reviewer 复核](../backend/app/services/review_service.py)
- [查询节点与回答路径测试](../backend/tests/unit/agent/test_graph_query_data.py)
- [质量循环测试](../backend/tests/unit/services/test_quality_loop.py)

### 设计取舍与缺口

当前通过不提供写能力，把高风险任务幻觉的影响面降到最低。未来每种动作都应定义“请求已受理、执行成功、最终已验证、结果未知”等不同状态，不能把 HTTP 200 或模型判断直接等同于业务完成。

### 可能追问

- 追问：让第二个 LLM 判断任务完成够不够？
  - 答题要点：不够。两个模型都只能解释文本，外部状态应由数据库查询、资源读取或测试等确定性证据证明。
- 追问：工具超时应该标失败吗？
  - 答题要点：不一定，可能已成功但响应丢失；应通过幂等键和状态查询确定，查不清就标未知。

## 18. Borough 让 Agent 查询数据库时，如何防止越权、泄密、SQL 注入和查询幻觉？

**来源文章：** [24. 大模型或 Agent 连接数据库时，如何防止越权、敏感数据泄漏和查询幻觉？](https://xiaolinnote.com/ai/agent/24_database_security.html)

**项目状态：** 已实现（应用层受控查询边界）

### 详细解答

核心原则是：Prompt 不是数据库防火墙，模型也不是数据库用户。Borough 不允许模型生成或执行任意 SQL。模型只能返回 `QueryIntent`；Pydantic 拒绝未声明字段，白名单限制指标、维度和筛选键，日期跨度与明细行数由后端钳制，排序字段也只能来自本次结果范围。真正 SQL 由 SQLAlchemy 和固定查询模板构造，值通过表达式绑定，不拼接用户输入。

租户范围来自已验证的演示 Token 映射出的 `MerchantContext`，而不是相信前端或模型传入 `merchant_id`。`SafeQueryService` 在每次调用中显式传入该上下文，Repository 的每条经营查询都把 `merchant_id` 加入 where 或 join 条件。跨业务查询也先在同一商家范围内解析订单，再查询关联退款或商品，找不到时不会跨商家探测。

结果进入模型前还会裁剪为受控事实包；日志和运维端点不返回完整 Prompt、Token 明文或完整查询结果。测试覆盖同日两商家数据不混合、筛选值注入不改变语义、伪造指标在到达 SQL 前被拒、180 天日期上限以及错误原因不泄露 SQL 细节。

需要区分“查询安全”和“查询正确”：白名单能阻止越权和危险 SQL，但指标选错仍可能得到安全却错误的结果，所以还要靠指标目录、时间解析、事实校验和真实模型评测保证语义正确。

### 设计取舍与缺口

当前应用层已经形成“可信身份—结构化意图—白名单—模板查询—结果裁剪”的纵深防御。进一步增强可以使用专用只读数据库角色、脱敏视图和 PostgreSQL RLS 作为数据库侧兜底；在真正引入写操作前，还必须增加预览、人工审批、事务、影响行数限制和审计回执。

### 可能追问

- 追问：只允许 SELECT 为什么还不够？
  - 答题要点：SELECT 仍能跨商家读敏感表、调用危险函数或发起超大查询；必须限制表、列、函数、范围和租户。
- 追问：`merchant_id` 为什么不能由前端传？
  - 答题要点：请求体是用户可控数据；租户身份必须来自验证过的令牌或服务端会话，并在每次查询中强制注入。

## 面试收束建议

介绍 Borough 时，最稳妥的一句话是：这是一个“中心化、固定 Workflow 驱动、局部使用 LLM 决策、所有数据动作由后端确定性约束”的商家 Data Agent。它的亮点不是堆叠 Agent 术语，而是把模型放在适合做概率判断的位置，同时用类型、白名单、租户隔离、预算、幂等、质量循环和可见降级控制生产风险。

当前最值得坦诚说明的三项缺口是：完整的真实模型离线评测集尚未闭环；只有轻量运维指标而没有分布式 Trace；没有正式人工接管与有副作用工具状态机。这些都是明确的演进方向，但不能描述成已经交付。
