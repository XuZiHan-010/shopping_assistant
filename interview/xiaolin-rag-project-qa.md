# 小林 Coding RAG 专题 × Borough 商家 AI 助手：项目强相关面试问答

## 使用说明

本文把小林 Coding 的 RAG 专题中与 Borough 商家 AI 助手直接相关的知识，改写为可以用于项目面试的问答。它不是泛泛介绍 RAG，而是每题都回到仓库当前实现，并严格区分：

- **已实现**：可在当前代码、测试或接口中核验；
- **部分实现**：已有相近机制，但范围或实现方式不同；
- **未实现 / 建议演进**：面试时应坦诚说明，并给出何时值得做、怎样最小化落地。

本次完整浏览了专题目录列出的 21 篇文章，但只保留与项目知识库、检索、商家记忆、上下文、质量、安全和演进直接相关的内容，整理为 18 题。这里的“RAG”应理解为广义的“检索增强生成”能力；项目当前并没有 Embedding、向量数据库、混合检索、学习式重排或 GraphRAG，不能把这些能力说成已上线。

项目证据链接均指向当前工作区；网页链接指向对应的小林文章。

## 1. 这个项目有 RAG 吗？完整链路是什么？

**来源文章：** [什么是 RAG？完整工作流程](https://xiaolinnote.com/ai/rag/1_whatisrag.html)

**项目状态：** 部分实现——具备“先检索、后把受控知识交给模型”的链路，但采用确定性关键词检索，不是向量 RAG。

### 详细解答

项目中的 RAG 不应表述成“接入了某个向量库”，更准确的说法是：它有一条受控知识增强链路。Agent 先读取索引型知识，把索引交给两阶段意图识别；随后在结构化意图确定后，按业务域和意图关键词加载知识正文。对于指标问题，正文可辅助解析指标口径；对于经营数据问题，实际事实仍来自后端安全查询；对于平台规则问题，命中的知识正文就是回答依据。

链路还包含两个重要边界：团队维护的知识库优先，只有团队知识未命中时，才读取当前商家的历史记忆；每个结果保留来源类型，响应通过 `analysis_sources` 和 `quality_notes` 说明使用了知识库、记忆或降级兜底。这样“检索”不会越过业务数据的安全查询边界。

### 项目证据

- [graph.py](../backend/app/agent/graph.py) 的节点顺序包含 `retrieve_knowledge_index`、`classify_intent`、`retrieve_knowledge_detail`、`compose_answer`。
- [retrieval.py](../backend/app/knowledge/retrieval.py) 的 `load_index()`、`load_domain()` 和 `KnowledgeResult` 实现了索引、领域正文与命中来源。
- [intent/prompts.py](../backend/app/intent/prompts.py) 将业务知识作为受控上下文传给意图理解器；[graph.py](../backend/app/agent/graph.py) 会把来源映射为 `KNOWLEDGE` 或 `MEMORY`。

### 设计取舍与缺口

小语料、固定业务域的早期阶段，规则检索具有可解释、零向量费用、可重复测试的优点。缺口是同义改写、长尾问法和跨文档关联的召回能力有限。语料规模、问题多样性和“未命中但实际上有答案”的比例上升后，再引入混合检索与重排更合理。

### 可能追问

**追问：为什么不把经营数据也放进 RAG？** 因为 RAG 适合取规则、口径和说明；GMV、订单等实时且受商家隔离约束的事实必须经后端模板化 SQL 查询，不能把知识检索当作数据查询替代品。

## 2. RAG 在这个助手里主要解决什么问题？

**来源文章：** [RAG 主要解决什么问题](https://xiaolinnote.com/ai/rag/2_rag_problems.html)

**项目状态：** 已实现基础目标。

### 详细解答

它主要解决三类问题。第一，平台规则、指标口径和运营知识会变化，不能只依赖模型预训练知识；维护知识文档后可以在不改模型参数的情况下更新回答依据。第二，回答需要尽量有依据，规则问答要让系统知道命中的是团队知识还是商家记忆，并在资料不完整或未命中时显式提示。第三，知识与商家数据职责分离：知识库提供“怎么解释”，安全数据查询提供“实际发生了什么”。

RAG 不能自动解决所有幻觉。若检索错误、知识过期或上下文塞入过多无关内容，模型仍可能答错。因此项目同时使用结构化意图、白名单查询、事实包和独立 Reviewer，而不是把“检索到了文本”误当成准确性的充分条件。

### 项目证据

- [models/knowledge.py](../backend/app/models/knowledge.py) 中 `KnowledgeDocument` 有来源、路径、状态、版本和完整度字段，支持可维护知识。
- [graph.py](../backend/app/agent/graph.py) 会在知识未命中、资料不完整或回退到记忆时写入可见的 `quality_notes`。
- [answer.py](../backend/app/prompts/answer.py) 要求回答编排器只能依据受控事实包作答。

### 设计取舍与缺口

现阶段的“来源可见”是来源类型级别，而非逐句、逐文档的 UI 引用。若面向正式商家上线规则问答，应增加文档标题、版本、生效时间和可点击片段，让商家能复核答案。

### 可能追问

**追问：知识未命中时是否应该让模型自由回答？** 不应把自由回答伪装为有依据的业务结论。应说明未命中、缩小回答到已知范围，必要时转人工或引导补充知识。

## 3. 为什么这里优先做知识检索，而不是微调模型？

**来源文章：** [RAG 与微调的优劣](https://xiaolinnote.com/ai/rag/3_rag_vs_finetune.html)

**项目状态：** 已采用 RAG 优先的架构决策。

### 详细解答

本项目的规则、指标定义和商家经营口径都具有可变性、可追溯性和权限边界。用知识库更新这些内容，比微调更合适：更新速度快，可回滚，可看到来源和版本，也不会把某个商家的内容固化进模型权重。尤其商家记忆必须按 `merchant_id` 隔离，绝不能用跨商家数据微调后再让模型“记住”。

微调并非没有价值。它更适合稳定、重复且主要影响表达风格或固定分类能力的任务，例如在有高质量标注集和脱敏流程后，提升结构化意图识别的一致性。但它不能取代实时经营数据查询，也不适合承载频繁变动的规则正文。

### 项目证据

- [models/knowledge.py](../backend/app/models/knowledge.py) 将团队知识与 `MerchantMemory` 物理分表，后者带 `merchant_id` 外键和唯一约束。
- [knowledge_admin_service.py](../backend/app/services/knowledge_admin_service.py) 支持知识文档维护及版本并发控制。
- [AGENTS.md](../AGENTS.md) R5 规定经营数据、会话、附件、记忆和反馈必须按 `merchant_id` 隔离。

### 设计取舍与缺口

当前没有微调训练流水线、标注集或模型版本治理。面试时不要声称项目“完全不需要微调”，而应说明当前问题首先是知识时效、检索质量和安全，优先投资在这些可验证环节。

### 可能追问

**追问：能否用商家历史对话微调？** 默认不能。历史对话含隐私与商家特定信息，必须先有明确授权、脱敏、隔离、删除机制和训练数据治理；当前项目采用商家级记忆兜底，不将其训练进模型权重。

## 4. 当前知识文档如何存储、按什么粒度组织？

**来源文章：** [文档存储与 Chunking 策略](https://xiaolinnote.com/ai/rag/4_chunking.html)

**项目状态：** 已实现文档级管理；未实现通用 Chunking。

### 详细解答

团队知识存储在 PostgreSQL 的 `knowledge_documents` 表中，正文、标题、业务分类、虚拟路径、来源、状态、完整度、版本和源语言均可管理。知识树把文档分为 `index/`、`业务/` 和只读的 `memory/` 三个根。当前“粒度”是业务文档粒度：先以业务域和路径筛选文档，再按关键词收窄，最多取前三篇，并把完整文档正文拼入上下文。

这种组织适合当前小规模、结构清楚的业务知识库；管理员能按业务域维护，而工程上不必维护切片 ID、向量重建和父子段关系。它不等于“没有粒度控制”：复合问法会按相关性取前三篇，其他问法仍受 24,000 字符的总结果上限约束；这些是候选收窄和拼接截断，不是语义切片。

### 项目证据

- [models/knowledge.py](../backend/app/models/knowledge.py) 定义 `KnowledgeDocument` 的路径、分类、内容、版本、状态和语言字段。
- [path_policy.py](../backend/app/knowledge/path_policy.py) 约束知识根目录和 `memory` 只读边界。
- [retrieval.py](../backend/app/knowledge/retrieval.py) 的 `_TOP_N = 3`、`_render()` 和 `MAX_KNOWLEDGE_CHARS` 实施结果收窄与字符上限。

### 设计取舍与缺口

当单篇规则文档很长时，整篇注入会带来无关上下文、token 成本和“正确段被截断”的风险。届时应按标题层级或业务条款生成稳定 chunk，并保留 `document_id`、标题路径、版本、chunk 序号和前后文关系。

### 可能追问

**追问：为什么不是按固定 500 token 切？** 固定长度简单但容易切断“适用条件—例外—处理步骤”的完整语义。该领域更适合优先按 Markdown 标题、条款编号和表格边界切，再用长度作为兜底。

## 5. 如果以后切片，怎样避免把语义切坏？

**来源文章：** [如何规避语义被切割](https://xiaolinnote.com/ai/rag/5_semantic_cuts.html)

**项目状态：** 未实现，属于明确演进项。

### 详细解答

对平台规则和指标口径来说，语义完整性比平均 chunk 长度更重要。一个可行方案是先按 Markdown 的一级、二级标题和编号条款切分：把“定义、适用范围、计算口径、例外、处理动作”作为结构单元；超过长度阈值时再按句子或列表项切。每段要携带文档标题路径、版本、前后邻接关系和原始来源，命中一段后可按需补相邻段。

对于表格，不应把一行拆到两个 chunk；对于“若……则……”规则，应让条件和结论留在同一段；对于指标，应让公式、统计范围和排除项同时出现。评估时不能只看相似度，还要检查关键例外是否仍能召回。

### 项目证据

- [retrieval.py](../backend/app/knowledge/retrieval.py) 当前直接渲染整个命中文档，证明尚无 chunk 元数据或邻接召回。
- [knowledge_admin_service.py](../backend/app/services/knowledge_admin_service.py) 已具备正文版本和 ETag 并发控制，可作为未来“文档更新触发重切片”的基础。

### 设计取舍与缺口

不要仅为了“用了 RAG 最佳实践”就提前切片。当前文档数和业务域都较小，先把文档结构、质量和更新流程管好更划算。触发条件是单篇文档明显变长、命中后上下文经常截断，或评测显示正确条款被漏召回。

### 可能追问

**追问：切片重叠要设多少？** 不应先拍一个固定百分比；先以标题和条款边界解决大部分问题。只有不得已按句子切分时，才设置小范围重叠，并通过离线召回评测调参。

## 6. Embedding 是什么？如果项目要引入，如何选模型？

**来源文章：** [Embedding 的作用与选型](https://xiaolinnote.com/ai/rag/6_embedding.html)、[Embedding 常见算法](https://xiaolinnote.com/ai/rag/7_embedding_algos.html)

**项目状态：** 未实现。

### 详细解答

Embedding 是把文本映射为向量，使“意思相近但字面不同”的查询与知识段落能在向量空间中靠近。它能补足当前关键词策略对同义词、口语化表达和跨语言表达的不足，但不是免费且不必然更准：领域缩写、指标代码、否定词和规则例外有时恰恰需要精确关键词。

若引入，选型不应只看公开榜单。要以项目语料构造中文/英文、业务术语、规则问答、指标口径和干扰项的评测集；比较 Recall@K、MRR、延迟、向量维度、批量索引成本、API 可用性与数据出境风险。模型应支持项目的中英双语，而向量维度和检索方案必须与存储能力匹配。

### 项目证据

- [domains.py](../backend/app/knowledge/domains.py) 明确说明当前不引入分词器或向量库，而是使用受控词表完成确定性匹配。
- [test_retrieval.py](../backend/tests/unit/knowledge/test_retrieval.py) 与 [test_score_question.py](../backend/tests/unit/knowledge/test_score_question.py) 覆盖了当前可重复的规则检索行为。

### 设计取舍与缺口

直接接外部 Embedding API 会增加费用、延迟和知识文本外发面；本项目没有为它配置密钥、预算、失败降级和向量更新任务。最小落地应先建立离线评测和抽象接口，再做小样本对照，而非先替换线上检索。

### 可能追问

**追问：词向量、双塔、交叉编码器分别怎么用？** 召回层通常用可预计算文档向量的双塔/bi-encoder；交叉编码器更适合对少量候选精排，成本较高；传统词向量模型表达能力有限，通常不作为现代语义检索的首选。

## 7. 为什么项目现在没有向量数据库？未来如何做选型与性能治理？

**来源文章：** [向量数据库与选型](https://xiaolinnote.com/ai/rag/8_vectordb.html)、[向量数据库实践、规模与性能](https://xiaolinnote.com/ai/rag/9_vectordb_practice.html)

**项目状态：** 未实现；当前不需要单独引入。

### 详细解答

当前知识库是有限数量、结构明确的运营文档，确定性业务域和关键词筛选足以工作，并且更容易解释和测试。因此项目没有使用 pgvector、Milvus、Elasticsearch 或托管向量服务，更没有 ANN 索引、召回延迟或向量容量的线上指标。

未来需要向量检索时，先判断规模与需求，而不是先选产品：语料是否增长到规则文档粒度难以人工维护、同义问法漏召回是否成为主要问题、检索延迟和并发目标是多少、是否需要元数据过滤。若项目仍以 PostgreSQL 为主且规模中小，可先评估 pgvector，复用事务、备份和权限体系；若向量规模、吞吐或 ANN 调优成为独立瓶颈，再评估专用向量库。无论哪种，`merchant_id` 和文档状态等过滤必须在查询层强制执行。

### 项目证据

- [AGENTS.md](../AGENTS.md) 的技术栈把 PostgreSQL 作为当前主数据库，未声明向量数据库。
- [retrieval.py](../backend/app/knowledge/retrieval.py) 全部基于路径、标题、正文和受控词的确定性评分，没有向量查询调用。

### 设计取舍与缺口

“没有向量库”是当前阶段的有意简化，不是宣称向量库没有价值。要避免两个误区：一是把数据库选型当成检索质量本身；二是忽略过滤条件，导致商家记忆跨租户召回。

### 可能追问

**追问：向量库性能怎么看？** 以端到端 P95/P99、Recall@K、索引构建耗时、写入后可见延迟、过滤后的召回质量、存储成本和故障恢复时间衡量，不能只报 QPS。

## 8. 用户提问进入当前知识增强流程后，如何组装上下文？

**来源文章：** [RAG 输入后的工作流程](https://xiaolinnote.com/ai/rag/10_online_workflow.html)

**项目状态：** 已实现基础两阶段流程。

### 详细解答

当前流程不是“一次检索后把所有知识塞给模型”。Agent 先加载索引和规则类资料，调用第一阶段意图识别；意图确定后，再按类别与关键词检索领域正文，随后做意图校验、安全数据查询或规则回答。这样索引承担路由作用，正文只在知道业务域后使用，减少无关上下文。

上下文里还分清知识与事实：规则模式可由知识正文直接回答；指标和明细模式的回答事实来自安全查询与指标目录，知识不允许替代数据库结果。实际命中的查询词会写进 `AgentState.retrieval_queries`，用于排障和测试观察，而不会覆盖用户原始问题或写回知识库。

### 项目证据

- [graph.py](../backend/app/agent/graph.py) 的 `_classify_intent()`、`_understand_intent()` 与 `_retrieve_knowledge_detail()` 展示两阶段使用知识。
- [state.py](../backend/app/agent/state.py) 保存 `knowledge_index`、`knowledge_detail` 与 `retrieval_queries`。
- [retrieval.py](../backend/app/knowledge/retrieval.py) 说明规范化查询仅用于本次匹配。

### 设计取舍与缺口

目前检索文本最大 24,000 字符，缺少基于 token 的完整上下文预算分配，也没有“证据不足则拒答”的统一阈值。未来应为系统提示、历史、知识、数据事实和输出预留预算，按优先级裁剪，而不是简单截断。

### 可能追问

**追问：为什么不把聊天历史直接和知识一起全量塞入？** 历史会挤占知识和事实窗口，也可能把过期上下文带入当前问题。应只保留当前任务所需的短期历史，并让商家级长期记忆有独立、可控的召回路径。

## 9. 关键词检索和向量检索有什么区别？本项目为什么先选关键词？

**来源文章：** [向量检索与关键词检索的区别](https://xiaolinnote.com/ai/rag/11_retrieval_types.html)

**项目状态：** 已实现关键词/规则检索；未实现向量检索。

### 详细解答

关键词检索擅长精确术语、指标代码、业务域和规则动作，优点是可解释、可预测、低成本；向量检索擅长语义相似和同义改写，但需要 Embedding、索引与评测，也可能把字面相近却规则不适用的段落召回。项目当前的知识本身带有“退款、优惠券、上架、规则”等强业务词，且分类与动作词表是受控的，所以先用关键词和路径筛选是合理的 MVP 方案。

具体地说，项目会先依据业务域别名过滤文档；复合问题再要求“业务词 + 动作/规则词”各自命中，并按标题、路径、正文的加权相关度取 Top 3。这不是 BM25，也不是语义检索，但比全量字符串搜索多了一层明确的业务约束。

### 项目证据

- [domains.py](../backend/app/knowledge/domains.py) 定义 `DOMAIN_KEYWORDS` 和 `ACTION_RULE_TERMS`。
- [retrieval.py](../backend/app/knowledge/retrieval.py) 的 `_decompose()`、`_narrow_by_keywords()` 与 `_relevance_score()` 实现了当前匹配策略。

### 设计取舍与缺口

当前策略对“退款怎么处理”和“售后退款规则”这类已登记同义词有效，对未登记的表达较弱。演进时不建议二选一，而是保留精确关键词作为一路，与向量召回融合后再重排。

### 可能追问

**追问：为什么关键词策略要区分业务词和动作词？** 只命中“商品”会把定价、上架、库存等文档都混进来；同时要求“商品 + 上架/规则”等条件能显著减少同域噪声。

## 10. 项目是否有 Query Rewrite？中英文问题如何处理？

**来源文章：** [Query Rewrite 的目的与做法](https://xiaolinnote.com/ai/rag/12_query_rewrite.html)

**项目状态：** 部分实现——仅有受限的跨语言查询规范化，不是通用 Query Rewrite。

### 详细解答

项目不会让模型随意“润色”或改写用户问题。当前只在原查询未命中、已注入本地化服务、请求语言与知识语料语言不同且语言检测一致等严格条件同时满足时，最多将问题翻译成语料语言重试一次。原始问题保留用于展示和存储，规范化译文只用于该次检索，并记录在 `retrieval_queries` 供排查。

这是成本与语义风险的控制：通用 Query Rewrite 可能丢掉时间、筛选条件、指标名或否定关系，也会增加模型调用。若未来做通用改写，应要求结构化输出，例如保留实体、时间范围、指标、否定词与原问题的映射；并在离线集上证明召回收益大于误改风险。

### 项目证据

- [retrieval.py](../backend/app/knowledge/retrieval.py) 的 `load_domain_with_cross_language_retrieval()` 明确约束最多一次翻译重试和触发条件。
- [graph.py](../backend/app/agent/graph.py) 为这次本地化检索配置了独立预算，不挤占主 Agent 调用额度。

### 设计取舍与缺口

跨语言规范化是一个很窄的 Query Rewrite 子集，不能回答成“项目做了 HyDE、多查询扩展或会话重写”。这些能力目前都没有，需要先有评测集和费用上限才值得加入。

### 可能追问

**追问：为什么翻译失败不直接报错？** 检索增强是可降级组件。翻译失败时仍保留原查询的结果，并继续按既有链路处理；不能因为一个优化步骤失败而让正常问答整体不可用。

## 11. 项目有多路召回吗？团队知识和商家记忆冲突时怎么办？

**来源文章：** [多路召回是什么](https://xiaolinnote.com/ai/rag/13_multi_retrieval.html)

**项目状态：** 部分实现——有受控的多来源检索，不是并行融合的多路召回。

### 详细解答

项目有多个知识来源：索引/规则文档、业务域团队知识、指标目录和当前商家的历史记忆。但它们不是 BM25、向量、网页搜索并行召回后做 RRF 融合；而是分阶段、带优先级的受控流程。团队知识先按业务域和关键词命中，只有它没有命中时，才使用该 `merchant_id`、该分类的记忆作为 fallback。

这条优先级表达了知识治理原则：团队维护的规则是平台事实源，商家记忆是个性化历史上下文，不能反过来覆盖规则。若两者含义冲突，回答应以团队知识为准；若只命中记忆，必须告诉用户本次是基于历史记忆，而不是伪装成平台政策。

### 项目证据

- [models/knowledge.py](../backend/app/models/knowledge.py) 注释明确团队知识永远优先、商家记忆仅在未命中时参与检索。
- [retrieval.py](../backend/app/knowledge/retrieval.py) 的 `load_domain()` 和 `_load_memory_fallback()` 实现先团队知识、后商家记忆。
- [graph.py](../backend/app/agent/graph.py) 会对记忆兜底写出用户可见说明。

### 设计取舍与缺口

当前没有并行的融合分数、来源可信度模型或时间衰减排序。若知识库扩大，可在不改变“团队知识优先”治理规则的前提下，增加关键词、向量和元数据过滤并行召回，再由重排器处理候选。

### 可能追问

**追问：多路召回为何不直接取并集？** 并集会提高召回，也会放大噪声和上下文成本。应先控制每路 Top K，再做归一化、去重、可信度和租户过滤，最后给生成模型最小充分证据。

## 12. 现有检索怎么优化？什么时候该加入混合检索和 Reranker？

**来源文章：** [RAG 检索优化策略](https://xiaolinnote.com/ai/rag/14_retrieval_opt.html)

**项目状态：** 已有确定性收窄；混合检索与重排未实现。

### 详细解答

现有优化已经包括领域过滤、复合词门槛、标题/路径/正文加权、复合问法的稳定 Top 3 排序，以及未命中的跨语言重试。这些机制适合小语料，能减少不相关文档进入上下文，也让测试结果稳定复现。

下一阶段应先用失败案例驱动优化：收集“用户问题—应命中文档—实际候选”的离线集，分别量化漏召回和错召回。如果同义改写导致漏召回，再加向量一路；如果候选多而排序差，再只对少量候选调用 cross-encoder 或轻量 LLM reranker；如果精确术语被向量吞没，则保留关键词分支。不要先上线昂贵重排器再寻找问题。

### 项目证据

- [retrieval.py](../backend/app/knowledge/retrieval.py) 对复合问法采用两类词同时命中和稳定 Top 3 排序。
- [test_retrieval.py](../backend/tests/unit/knowledge/test_retrieval.py) 与 [test_dual_library.py](../backend/tests/unit/knowledge/test_dual_library.py) 覆盖检索和双库优先级。

### 设计取舍与缺口

重排通常是提升精度而非召回的工具，应该放在“候选已召回”的后面。当前没有检索日志指标、标注集和 reranker 预算，直接加入会难以证明收益，也会增加延迟和成本。

### 可能追问

**追问：混合检索如何融合？** 可从关键词分数与向量分数各取 Top K，做去重后用 RRF 等无量纲方法融合，或交给重排器；但在此之前必须先做商家、状态、语言和业务域过滤。

## 13. 如何降低 RAG 幻觉，并让用户知道答案的依据？

**来源文章：** [规避 RAG 幻觉](https://xiaolinnote.com/ai/rag/17_hallucination.html)

**项目状态：** 部分实现。

### 详细解答

降低幻觉不能只靠一句“请不要编造”。项目采用多层约束：意图由 Pydantic 结构校验，SQL 由后端白名单模板生成，回答编排器只能使用受控事实包；规则问答则从检索结果生成。检索未命中、命中文档不完整或回退到商家记忆时，系统会在 `quality_notes` 中显式说明；组件不可用时，用 `degraded` 与 `degraded_reason` 表示降级。

但也要坦诚边界：当前对用户展示的是 `analysis_sources` 的来源类型，不是每段回答对应哪篇文档、哪一版条款的细粒度引用。未来应把 `KnowledgeHit` 的路径、标题、版本和截取片段变成可展示证据，并让“没有足够证据”成为可选的拒答或转人工条件。

### 项目证据

- [answer.py](../backend/app/prompts/answer.py) 限制模型只能依据事实包输出，并禁止自行计算未经提供的结论。
- [graph.py](../backend/app/agent/graph.py) 对未命中、不完整资料、记忆兜底和降级状态生成可见说明。
- [retrieval.py](../backend/app/knowledge/retrieval.py) 的 `KnowledgeHit` 保留来源路径与正文，具备未来实现细粒度引用的基础。

### 设计取舍与缺口

Reviewer 主要核查事实包一致性，不等于 RAG grounding 评测。规则回答在没有细粒度引用和“证据覆盖率”校验前，仍需谨慎对外承诺准确性。

### 可能追问

**追问：检索到错误知识时怎么办？** 先靠知识库审核、版本和来源治理预防；线上发现后下线或修正文档、回归评测该问题，并保留审计。不能靠模型“自己判断哪篇是真的”替代治理。

## 14. 怎样评估这个项目的 RAG 效果？

**来源文章：** [RAG 效果量化](https://xiaolinnote.com/ai/rag/18_evaluation.html)

**项目状态：** 基础单元测试已实现；端到端 RAG 评测体系未实现。

### 详细解答

评测至少拆成检索和生成两层。检索层建立带标准文档/条款的测试集，衡量 Recall@K、MRR、nDCG、无答案问题的误命中率，以及不同语言、不同业务域和不同商家记忆的隔离正确性。生成层检查答案是否忠于证据、是否覆盖关键例外、是否包含不支持的结论、是否正确展示来源和降级信息。线上再看检索未命中率、用户追问率、点赞/点踩、人工转接率、延迟和 token 成本。

当前仓库有关键词检索、双库优先级、路径安全和知识库 API 的自动化测试，这证明确定性行为可回归；但没有一个标准问答集、向量召回基准、RAGAS 类指标或线上检索仪表盘。因此面试应回答“具备测试基础，尚未形成完整 RAG 评测闭环”。

### 项目证据

- [backend/tests/unit/knowledge](../backend/tests/unit/knowledge) 覆盖评分、检索、双知识库、路径策略、版本等单元测试。
- [test_knowledge_documents.py](../backend/tests/api/test_knowledge_documents.py) 覆盖文档更新、并发版本和只读记忆边界。
- [test_knowledge_memory_compress.py](../backend/tests/api/test_knowledge_memory_compress.py) 说明记忆压缩测试使用 Fake LLM，不产生真实模型费用。

### 设计取舍与缺口

离线指标不能独自代表商家满意度，线上反馈也不能告诉我们错在召回还是生成，所以两者都需要。最小下一步是从高频规则问题和历史失败案例开始建立几十条金标集，再纳入 CI。

### 可能追问

**追问：为什么 Recall@K 很高，用户仍觉得不好用？** 因为正确材料“被召回”不代表它排在前面、被放进上下文、被模型正确引用，也不代表回答符合用户任务。需要同时看排序、grounding 与最终任务成功率。

## 15. 知识库怎样动态更新，并避免并发覆盖和过期译文？

**来源文章：** [知识库动态持续更新](https://xiaolinnote.com/ai/rag/19_dynamic_update.html)

**项目状态：** 已实现基础知识治理。

### 详细解答

项目提供管理员知识树、文档读取、创建、更新、删除和业务域管理接口。知识正文的版本由内容哈希形成 ETag，更新和删除必须带 `If-Match`，并通过条件更新避免两个管理员基于同一旧版本互相覆盖。文档路径有受控根目录，商家记忆路径是只读的，防止管理员把团队规则和自动沉淀记忆混为一谈。

国际化方面，知识文档维护源版本与人工译文的关联；源内容更新后，旧人工译文会标为 `STALE` 而非被静默当成当前版本。商家记忆在不同语言读取时可按需走本地化服务，无法翻译则安全地返回源文。这些都是“更新后内容可追溯、不会悄悄错配”的基础。

### 项目证据

- [knowledge.py](../backend/app/api/routes/knowledge.py) 暴露知识树、文档 CRUD、ETag 与 `If-Match` 接口。
- [versioning.py](../backend/app/knowledge/versioning.py) 以 SHA-256 生成文档和目录版本。
- [knowledge_admin_service.py](../backend/app/services/knowledge_admin_service.py) 管理源版本、人工译文和 `STALE` 状态。

### 设计取舍与缺口

当前无需重建向量索引，因为没有向量索引；未来引入 chunk/Embedding 后，更新流程必须成为“写入版本 → 异步切片/嵌入 → 原子切换检索版本 → 评测/告警”的流水线，不能只更新正文。

### 可能追问

**追问：为什么删除需要 If-Match？** 删除同样可能误删其他管理员刚更新的内容。条件版本让客户端先确认自己删除的是看到的那一版，而不是静默覆盖更新。

## 16. 不同来源知识冲突时，项目应该相信谁？

**来源文章：** [知识冲突时 RAG 应信谁](https://xiaolinnote.com/ai/rag/21_knowledge_conflict.html)

**项目状态：** 已实现最关键的优先级；完整冲突检测未实现。

### 详细解答

项目已明确区分两类知识：团队维护知识是平台规则、指标口径等规范事实源；商家记忆是当前商家的历史上下文。因此检索策略不是平权融合，而是“团队知识优先，未命中才使用该商家、该分类记忆”。这既减少了个性化记忆覆盖平台规则的风险，也把冲突处理变成可解释的治理规则。

更完整的冲突治理还应考虑来源权威性、发布时间/生效时间、文档版本、业务域、租户范围和人工审核状态。例如“旧规则”和“新规则”都在团队库中时，当前实现没有自动识别语义冲突；需要在知识录入层增加生效期、替代关系或归档策略，而不是把选择压力交给模型。

### 项目证据

- [models/knowledge.py](../backend/app/models/knowledge.py) 的 `MerchantMemory` 文档说明了人工知识优先、记忆仅 fallback 的双库原则。
- [retrieval.py](../backend/app/knowledge/retrieval.py) 只有团队知识无命中时才调用 `_load_memory_fallback()`。
- [graph.py](../backend/app/agent/graph.py) 在使用记忆兜底时向用户明示。

### 设计取舍与缺口

“团队知识优先”并不能处理团队文档内部冲突，也不能替代版本审计。面试时可以把它说成已解决跨来源优先级，但不能说已解决所有知识冲突。

### 可能追问

**追问：商家自定义规则能否覆盖平台规则？** 不能覆盖。它最多作为商家偏好或内部流程，并需明确标记适用范围；与平台政策冲突时应以平台规则为准并提示差异。

## 17. RAG 面临哪些安全问题？本项目已做了什么，还缺什么？

**来源文章：** [规避 RAG 幻觉](https://xiaolinnote.com/ai/rag/17_hallucination.html)、[RAG 落地最难的地方](https://xiaolinnote.com/ai/rag/20_hardest_parts.html)

**项目状态：** 部分实现。

### 详细解答

RAG 的安全面不止“模型会不会胡说”：还包括商家记忆跨租户泄露、管理员越权改知识、恶意文档的提示词注入、把知识上下文诱导成 SQL、以及来源与版本不可追溯。项目对前两类已有明确边界：记忆按 `merchant_id` 查询，团队知识和记忆物理分表；知识库写操作走管理员令牌，`memory/` 只读；经营 SQL 不由模型直接生成或执行，而要经过结构化意图与后端白名单。

需要坦诚的缺口是：业务知识正文进入意图提示词时，尚未形成一套专门的“将检索内容视为不可信数据”的通用注入防护和文档入库扫描策略。翻译提示词已明确把待翻译文本视为不可信数据，这可作为设计参照，但不能误说为整个 RAG 链路已完整防注入。未来应在入库、检索、提示词三个层面加入来源白名单、指令模式检测、数据分隔符、最小权限工具调用和安全回归集。

### 项目证据

- [AGENTS.md](../AGENTS.md) 的 R4、R5 规定 SQL 白名单和商家隔离。
- [path_policy.py](../backend/app/knowledge/path_policy.py) 禁止写入 `memory` 根；[test_knowledge_documents.py](../backend/tests/api/test_knowledge_documents.py) 覆盖该边界。
- [localization.py](../backend/app/prompts/localization.py) 明确要求把 `items[].text` 当作不可信数据，而非模型指令。

### 设计取舍与缺口

只对管理员开放知识编辑能降低风险，但不是内容安全机制。将来若支持附件、网页或商家自助上传知识，必须把注入防护、恶意文件检测、审核与回滚作为上线前置条件。

### 可能追问

**追问：检索出来一段“忽略之前指令”的文本怎么办？** 模型提示词必须明确该段是数据不是指令；应用层不能让它驱动工具或 SQL；同时记录来源并将文档下线审核。

## 18. 什么时候需要 Advanced RAG、GraphRAG？这个项目最难的 RAG 问题和演进路线是什么？

**来源文章：** [复杂 RAG 范式](https://xiaolinnote.com/ai/rag/15_advanced_paradigms.html)、[何时用图数据库增强 RAG](https://xiaolinnote.com/ai/rag/16_graph_db.html)、[RAG 落地最难的地方](https://xiaolinnote.com/ai/rag/20_hardest_parts.html)

**项目状态：** 未实现；当前不建议为了技术名词引入。

### 详细解答

Advanced RAG 包括自反思/纠错检索、查询分解、多跳检索、混合检索和重排等；GraphRAG 则适合实体关系密集、问题依赖多跳关系的场景，例如“某商品—某活动—某规则版本—某处罚记录之间的影响链”。当前项目的规则知识以业务域文档为主，经营事实由受控关系型查询提供，尚未出现需要从知识图谱做复杂多跳推理的强证据，所以不应引入图数据库或 GraphRAG 增加维护复杂度。

项目真正难点不在“有没有更酷的 RAG 架构”，而在知识正确性、更新治理、租户隔离、检索评测和成本可观测性。合理演进顺序是：先补金标评测与来源引用；再按真实漏召回问题试验关键词 + 向量的混合召回；候选排序确实成为瓶颈后加重排；只有问题长期需要跨实体、多跳关系解释时，才把实体、关系、版本和权限建模并评估 GraphRAG。

### 项目证据

- [retrieval.py](../backend/app/knowledge/retrieval.py) 当前检索是文档/记忆的确定性筛选，不含图遍历、向量召回或重排。
- [domains.py](../backend/app/knowledge/domains.py) 与 [safe_query.py](../backend/app/services/safe_query.py) 分别体现规则知识路由和经营数据受控查询的职责边界。
- [project-progress.md](../docs/project-progress.md) 记录项目已落地的知识库与商家记忆能力，可作为后续演进的基线。

### 设计取舍与缺口

复杂范式不是质量保证。每新增一层都会带来延迟、token/服务成本、可观测性和故障面。面试时最好的回答是给出触发条件、评测指标和分阶段落地路径，而不是宣称“以后一定用 GraphRAG”。

### 可能追问

**追问：什么数据证明该上 GraphRAG？** 应证明普通检索持续无法解决多跳关系问题：例如大量问题需要跨多个实体和规则版本推理，且离线集上通过图关系扩展能稳定提升任务成功率，收益超过建图、更新和权限治理成本。

## 面试回答原则

1. 先说真实实现，再说缺口与演进，绝不把“设计上可做”说成“已经上线”。
2. 把知识检索与经营数据查询分开：前者解释规则和口径，后者提供按商家隔离的实时事实。
3. 不以技术名词为目标。是否引入向量、重排或图检索，必须由漏召回、排序质量、规模、延迟、成本和安全评测共同决定。
4. RAG 的核心不是“搜到文本”，而是可维护的知识、正确的召回、受控的上下文、可核验的回答和可观测的失败。
