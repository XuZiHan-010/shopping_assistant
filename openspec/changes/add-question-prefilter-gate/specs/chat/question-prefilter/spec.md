## Purpose

在任何 LLM 调用发生之前，以确定性算法判定商家提问是否落在本平台经营问答范围内，
使范围外的提问以零 token 成本被拒绝并被引导重问，从而在对外部署下限制恶意提问对模型预算的消耗。

## ADDED Requirements

### Requirement: 范围外提问必须零 LLM 成本拒绝

系统 SHALL 在调用任何 LLM 之前判定提问是否与平台经营问答相关。判定为不相关时，
系统 MUST 直接生成拒答响应，且本轮 LLM 调用次数 MUST 为 0。

判定依据 MUST 是提问与系统已有业务语料（业务知识库、指标目录、该商家历史记忆）的
加权匹配程度，MUST NOT 依赖人工维护的无关词黑名单——无关提问无法穷举。

#### Scenario: 与经营完全无关的提问被零成本拒绝

- **WHEN** 商家在新会话首轮提问「CNN 和 RNN 的区别是什么」
- **THEN** 系统返回 `answer_mode=INVALID` 的响应
- **AND** 本轮未发生任何 LLM 调用
- **AND** 响应中包含说明范围的引导文案与推荐问题

#### Scenario: 拒答不消耗每日 token 预算

- **WHEN** 连续提交 100 条范围外提问
- **THEN** 每日 token 用量统计的增量为 0

### Requirement: 业务相关提问必须原样放行

判定为相关或无法确定时，系统 SHALL 将提问原样交给既有意图识别链路处理，
MUST NOT 改写提问文本，也 MUST NOT 预先指定回答模式或业务类目。

判定不确定时 SHALL 放行（fail open）：宁可多花一次 LLM 调用，也不误拒合法经营提问。

#### Scenario: 命中业务语料的提问进入正常链路

- **WHEN** 商家提问「最近 7 天退货量趋势」
- **THEN** 提问被放行，进入意图识别与受控查询链路
- **AND** 最终响应与未引入本能力时的行为一致

#### Scenario: 商家专有词汇因历史记忆而放行

- **WHEN** 商家历史问答中出现过某个本店铺专有的商品名，且新提问只包含该商品名
- **THEN** 提问被放行

### Requirement: 问候语必须放行并由模型自然回答

系统 SHALL 识别日常问候与寒暄，并放行交由既有 `CHAT` 模式处理，
MUST NOT 将其判定为范围外提问。

#### Scenario: 问候语不被拒绝

- **WHEN** 商家提问「你好」
- **THEN** 提问被放行
- **AND** 响应为 `answer_mode=CHAT` 的自然回答，而非拒答文案

### Requirement: 会话内追问必须放行

同一会话中已存在被放行过的历史轮次时，系统 SHALL 放行该会话的后续所有提问，
不再执行范围判定。

理由：合法追问常常不含任何业务词汇，对其执行判定会造成误拒。

#### Scenario: 无业务词的追问不被误拒

- **WHEN** 商家先提问「最近 7 天退货量」并获得正常回答，随后在同一会话提问「那上个月呢？」
- **THEN** 第二轮提问被放行，不执行范围判定

#### Scenario: 新会话首轮重新执行判定

- **WHEN** 商家开启新会话并首轮提问「CNN 和 RNN 的区别是什么」
- **THEN** 该提问被拒绝，不因其他会话存在历史而放行

### Requirement: 拒答响应必须表述为正常结果而非系统降级

拒答是设计内的正常行为。拒答响应 MUST 满足：

- `degraded` 为 `false`
- `degraded_reason` 为 `null`
- `quality_status` 为 `NOT_RUN`
- `analysis_sources` 为 `["NONE"]`

系统 MUST NOT 将拒答标记为降级——那会使商家与运营把正常的范围外拒绝误读为系统故障。

拒答 MUST NOT 引入任何 `ChatResponse` 契约之外的新字段。

#### Scenario: 拒答响应的降级字段取值

- **WHEN** 提问被判定为范围外并返回拒答
- **THEN** 响应中 `degraded=false`、`degraded_reason=null`、`quality_status=NOT_RUN`、
  `analysis_sources=["NONE"]`

#### Scenario: 拒答携带引导素材

- **WHEN** 提问被判定为范围外并返回拒答
- **THEN** 响应包含说明助手服务范围的中文文案
- **AND** 响应包含可供商家直接选用的推荐问题

### Requirement: 业务语料不可用时必须放行

范围判定所依赖的业务语料为空或不可读取时，系统 MUST 放行提问交由 LLM 处理，
MUST NOT 因语料缺失而拒绝全部提问。

#### Scenario: 知识库为空时不拒绝任何提问

- **WHEN** 业务知识库与指标目录均无可用内容，商家提交任意提问
- **THEN** 提问被放行，不返回拒答

### Requirement: 判定必须限定在已验证商家范围内

范围判定若使用商家历史记忆作为语料，其商家标识 MUST 取自服务端已验证的身份，
MUST NOT 采信请求体或查询参数中传入的商家编号。

一个商家的历史记忆 MUST NOT 影响另一个商家的判定结果。

#### Scenario: 跨商家记忆不参与判定

- **WHEN** 商家 A 的历史问答中包含某专有词汇，商家 B 在新会话提问仅含该词汇
- **THEN** 商家 B 的提问不因商家 A 的记忆而放行

### Requirement: 判定行为必须可配置且可观测

系统 SHALL 提供配置项以启用/停用范围判定，并 SHALL 提供可调的判定阈值，
两者 MUST 可通过环境变量设置而无需改动代码。

系统 SHALL 为每次拒答记录结构化日志，内容至少包含判定分数与所用阈值，
供运营发现误拒并据此补充业务语料。日志 MUST 遵循既有脱敏约束，
MUST NOT 记录隐私字段。

#### Scenario: 停用后行为回到引入本能力之前

- **WHEN** 范围判定被配置为停用
- **THEN** 所有提问均被放行，行为与未引入本能力时一致

#### Scenario: 拒答产生可供排查的日志

- **WHEN** 提问被判定为范围外并返回拒答
- **THEN** 系统记录一条包含判定分数与阈值的结构化日志

### Requirement: 判定过程必须与查询层完全隔离

范围判定 MUST NOT 生成、拼接或执行任何 SQL，MUST NOT 产出表名、列名或查询标识符，
其输出 MUST 仅为「放行 / 拒绝」的判定结果。

#### Scenario: 判定不产出查询意图

- **WHEN** 提问被判定为相关并放行
- **THEN** 判定过程未产出任何查询意图、表名或列名，查询意图仍完全由既有意图识别链路生成
