# N4 E5 RAG 混合检索对比（2026-10-02）

> **结论（2026-10-02 定稿）：采用关键词 + `BAAI/bge-small-zh-v1.5` 向量的 RRF 混合检索，关键词侧补「完整字段名精确匹配」。**
> 拒答率保持 0.90，Recall@5 0.759 → **0.907**、MRR 0.639 → **0.802**、nDCG@5 0.652 → 0.817；只看 46 条中文问题，
> Recall@5 0.761 → **0.935**。代价（Linux 容器单线程实测）：常驻内存 +170 MB、镜像模型层 +95 MB、44 块建索引 14 秒。
> 选型理由与 `embeddinggemma-300m`（质量略高、成本约 5 倍）的对照见下文；重排不保留（见文末）。
>
> **证据分层**：本文全部检索指标为**确定性评测**（本地嵌入推理，零 LLM 调用、零费用）。引用正确率与回答忠实度需要 LLM 裁判，
> 只对 2026-10-01 的关键词检索做过真实评测（`rag-baseline.md`）；**混合检索的裁判复测待授权**（R3，约 128 次调用）。
> 阈值与评测集同源（见「局限」），换语料后须重评。

### 字段名精确匹配（2026-10-02，用户同意）

分词把 `repay_status_name` 切成 repay / status / name，「status」又扩展出一串泛化状态词，含完整字段名的文档被淹没。
`search_rules` 现从问题里抽出 snake_case 字段名，正文含完整字段名的文档作为排序硬优先；英文片段改按词边界匹配，
同分时索引类文档排后。只作用于 v2 `search_documents`，v1 `load_domain` 与零 LLM 闸门不变。这是通用规则，不是按评测集调参。

| 检索方式 | 改前 R@5 / MRR | 改后 R@5 / MRR | 字段名 R@5 | 拒答率 |
| --- | --- | --- | --- | --- |
| 关键词 | 0.759 / 0.639 | **0.833 / 0.755** | 0.44 → 0.94 | 0.90 |
| 混合（bge-small-zh，τ=0.575） | 0.870 / 0.738 | **0.907 / 0.802** | 0.69 → 0.94 | 0.90 |

改后 bge 混合仍漏 4 条：R-039、R-040（口语化）、R-043、R-045（英文提问）；误命中 1 条（R-060，与关键词同）。

## 方法

- 评测集与基线同一份：`backend/app/knowledge/probes/n4_e5_rag.yaml`，64 条（可回答 54、应找不到 10）；
  语料为镜像内团队知识种子 21 篇（全部中文），见 `rag-baseline.md`。
- 混合检索走产品路径：`resolve_rule_search(query, retrieval=..., vector=...)` →
  `KnowledgeRetrieval.search_documents(tokenize(query), vector_ranking=...)` → RRF（k=60）取前 5。
  评测用 `InMemoryVectorSearch` 代替数据库查询，分块（约 400 字/块、前缀标题）与「文档取最高块相似度」的聚合与
  `VectorIndexSearch` 一致。
- 复现：`cd backend; uv run python -m app.eval.rag_e5 --embedding-model BAAI/bge-small-zh-v1.5 --min-similarity 0.575`
  （首次运行会下载模型；换 `google/embeddinggemma-300m --min-similarity 0.4` 即复现对照）。
- 资源数据：本机 Windows、ONNX Runtime 2 线程、每个模型单独进程；常驻 +RSS = 加载并预热后减去基线，
  建索引峰值取进程高水位；镜像增量为 Linux 镜像实测。

## 局限

1. **阈值与评测集同源**。τ 是在这 64 条上选出来的。二折交叉验证（按序号奇偶分层，一折选 τ、另一折评估）：
   embeddinggemma 两折测试 Recall@5 均为 0.963，召回提升稳定；但两折选出的 τ（0.35 / 0.375）在测试折上的拒答率
   为 0.4 / 1.0——每折只有 5 条「应找不到」，拒答率对阈值非常敏感。因此生产取 0.40（全量最优点为 0.375），
   往保守一侧留余量。**语料或评测集变化后须重跑本评测再定阈值**。
2. 语料只有 21 篇且多为骨架文档，规模远小于真实知识库；向量召回在大语料上的误召回会更多。
3. 资源数据来自本机与本机 Docker，不是 Railway 实测；Railway 的 CPU 可能更慢，冷启动与建索引时间会更长。
4. 引用正确率与回答忠实度（LLM 裁判，R3）尚未对混合检索重跑；关键词路径的结果见 `rag-baseline.md`。
   混合检索上线后须另行取得费用授权重跑。

## 重排（Task 5）——不保留

候选：`BAAI/bge-reranker-base`（fastembed 交叉编码器，中英，约 1.04 GB；同档的 `jina-reranker-v2-base-multilingual`
为 1.11 GB，英文专用的小模型不适用中文语料）。做法：混合检索（gemma，τ=0.40）取前 10 篇，按 (问题, 标题 + 正文前 1500 字)
打分重排后取前 5；命中判定不变。

| 方式 | Recall@5 | MRR | nDCG@5 | 拒答率 | 每次查询额外耗时 p50 / p95 | 额外常驻内存 |
| --- | --- | --- | --- | --- | --- | --- |
| 混合 | 0.935 | 0.794 | 0.819 | 0.90 | — | — |
| 混合 + 重排 | 0.935 | 0.875 | 0.884 | 0.90 | 4.0 s / 9.4 s | +1.3 GB |

（本表「混合」一行由重排脚本按同一分块离线复算，关键词侧只用名次，与正式评估器的 0.833 略有出入；比较只看同一脚本内的两行。）

判定（计划 Task 5）：nDCG@5 提升 6.4 个百分点，**超过 3 个百分点的门槛，但 p95 延迟增量不可接受**——单次规则检索多 4–9 秒，
工具循环墙钟上限 60 秒，且 backend 内存要在 gemma 之上再加 1.3 GB。延迟测量时后端全量回归在同一台机器上并行，数值偏高，
但即使减半也仍是秒级。**结论：不保留重排**。重排只在评测脚本里实现，没有进入产品代码，无需删除。
若日后语料变大、排序问题变得突出，可评估更小的中文交叉编码器或把重排挪到异步路径，届时须重新评测。
