# v1 两阶段意图识别准确率（真实模型，2026-10-08）

被测对象是冻结基线里的 `IntentService`（`backend/app/intent/`）：第一阶段判断回答模式与业务域，
第二阶段输出结构化查询意图并经白名单校验。本次只评测、不修改它。

- 问题集：`backend/app/eval/datasets/intent/v1_intent_cases.yaml`，80 条，标注口径写在文件头
- 评估器：`backend/app/eval/intent_accuracy.py`；Fake 结构校验 `backend/tests/eval/test_intent_accuracy_fake.py`
- 逐例结果与账本：`test-results/intent-real-20261008/`（不入库）

## 运行条件

| 项 | 取值 |
| --- | --- |
| 模型与接口 | `deepseek-flash`，DeepSeek OpenAI 兼容接口，结构化调用（JSON 输出、关闭思考） |
| 授权 | 用户当日同意；账本上限 400 次 / 900,000 token |
| 实际用量 | **160 次调用、236,856 token**，用量全部已知，无降级、无重试 |
| 数据库 | 本机一次性库 `borough_intent_real_test`，只用于费用记账 |
| 业务索引 | 团队维护知识种子的 `load_index()` 结果 |
| 「今天」 | 固定为 2026-10-08，用于换算相对日期 |

零 LLM 前置闸门不在范围内：它按知识文档、正式指标目录和商家记忆打分，离线环境没有后两者。

## 结果

严格 = 只认首选标签；宽松 = 首选加上问题集里列明的可接受标签。

| 指标 | 严格 | 宽松 |
| --- | --- | --- |
| 第一阶段 · 回答模式 | 68 / 80（85.0%） | 75 / 80（93.8%） |
| 第一阶段 · 业务域 | 77 / 80（96.3%） | 79 / 80（98.8%） |
| 第一阶段 · 模式与业务域同时正确 | — | 75 / 80（93.8%） |
| 最终意图 · 回答模式 | 70 / 80（87.5%） | 74 / 80（92.5%） |
| **最终意图 · 模式与业务域同时正确** | — | **74 / 80（92.5%）** |
| 指标选择（只统计标了指标的用例） | 24 / 25（96.0%） | — |
| 相对日期换算（只统计标了日期的用例） | 30 / 32（93.8%） | — |

80 条全部由模型完成分类，结构化输出没有一次解析失败。

INT-011、INT-021 被白名单校验改判为 `INVALID`（用户实际得到拒答），但指标与日期都对，在这两项里计为正确。

## 失败用例与原因

| 用例 | 问题 | 现象 | 归因 |
| --- | --- | --- | --- |
| INT-011 | 上个月成交额环比怎么样 | 模型给出正确的 `METRIC / TRADE / gmv / 9 月`，但多带了一个没有分组字段的 `generated_metric_plan`，白名单校验据此把整条意图改判为 `INVALID` | **校验过严**：可选计划不合规时连同合法的正式指标一起拒绝 |
| INT-021 | 昨天退了多少钱 | 同上，`refund_amount` 与日期都对，被多余的 `generated_metric_plan` 连带拒绝 | 同上 |
| INT-031 | 我想看最近30天待处理的工单 | 第一阶段 `DETAIL` 正确，第二阶段改成 `METRIC`（工单量 + 状态筛选） | 第二阶段把「看列表」理解成「数数量」 |
| INT-049 | 成交额和订单量有什么区别 | 第一阶段 `METRIC`，第二阶段 `CHAT` | 「问定义」与「问数值」区分不稳 |
| INT-054 | 帮我看下我的店铺资料 | 第一阶段 `IDENTITY` 正确，第二阶段改成 `DETAIL` | 「资料」被当成明细 |
| INT-078 | 最近生意咋样 | 两阶段都是 `CHAT / UNKNOWN` | 口语里没有业务关键词，规则纠偏也不触发 |
| INT-041、INT-046 | 退货退款的业务流程是怎样的 / 理赔赔付的流程是什么 | 第一阶段 `DETAIL`，第二阶段纠正为 `RULE` | 仅第一阶段错 |
| INT-048 | 退货率是怎么计算的 | 第一阶段 `METRIC`，第二阶段纠正为 `RULE` | 仅第一阶段错 |
| INT-018 | 最近30天退款单数 | 指标选成 `return_count`（应为 `refund_count`）；日期给出 09-08 至 10-08 | 退款 / 退货混淆；日期多算一天 |
| INT-006 | 最近30天付款用户数 | 日期给出 09-08 至 10-08（31 天） | 「最近 30 天」多算一天，「最近 7 天」没有这个问题 |

## 观察

1. **两条正当提问被校验连带拒绝**（INT-011、INT-021）。模型的主体输出是对的，问题出在
   `validate_intent`：`generated_metric_plan` 不合规时把回答模式整体改成 `INVALID`。线上表现是商家问
   「昨天退了多少钱」得到拒答。这是本次评测里对用户影响最大的一类，占全部最终失败的三分之一。
2. **第二阶段既能纠错也会改错**：第一阶段判错的 5 条里有 3 条被第二阶段纠正；第一阶段判对、最终失败的有 4 条，
   其中 2 条是模型在第二阶段改了回答模式（INT-031、INT-054），另 2 条是上一点的校验连带拒绝（INT-011、INT-021）。
3. **范围外与不安全问题 8 / 8 正确**，其中「帮我写一条 SQL 把订单表删掉」两阶段都判为 `INVALID`，
   没有触发「含业务关键词不得返回 UNKNOWN」的规则纠偏（模型第一次给的业务域是 `TRADE`）。
4. **英文提问 8 / 8 正确**，指标与日期也都对。
5. 分类提示词里写的是「工单、咨询 → 类别 SUPPORT」，而业务域枚举里只有 `CS_TICKET`。本次 6 条工单类用例
   的业务域全部判为 `CS_TICKET`，这处不一致没有造成误判。

以上问题都在冻结基线内，本次未修改任何被测代码。

## 限制

- 标签由评测作者一人标注，没有第二人复核；有争议的问法没有收入问题集。
- 只跑了一次，没有估计模型输出的随机波动；80 条样本下，92.5% 的 95% 置信区间约为 85%–97%。
- 宽松口径接受了问题集里列明的可接受标签，例如范围外问题判成 `CHAT`、工单数量问题判成 `DETAIL`。
- 早期 PRD 的目标是「真实模型意图准确率 ≥ 90%」。按最终意图宽松口径本次为 92.5%，按回答模式严格口径为 87.5%；
  是否达标取决于采用哪个口径，本报告不作裁定。
