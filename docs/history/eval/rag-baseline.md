# N4 E5 RAG 关键词基线（2026-10-01）

> 结论：**现有 `search_rules` 的检索 Recall@5 只有 9.3%，主因是工具写死只在「平台规则」业务域里检索**——
> 21 篇团队知识里只有 3 篇能进入候选。假设业务域选对，同样的关键词匹配 Recall@5 可到 86.1%（诊断上限，不可上线）。
> 「应当找不到」的问题只承认了 50%。这份基线是 N4-C 后续向量与混合检索的对照，未改任何检索代码。

## 方法

- 评测集：`backend/app/knowledge/probes/n4_e5_rag.yaml`（2026-10-02 由 `app/eval/datasets/rag/` 移至生产侧，兼作索引切换验证探针；内容未改），64 条（可回答 54、应找不到 10）。按正文内容标注应命中的文档，
  分七类：口径问答 12、流程与规则 12、字段与数据表 8、口语化改写 8、英文提问中文文档 8、多文档组合 6、应找不到 10。
- 语料：镜像内团队知识种子 `backend/app/knowledge/wiki_seed.json`，21 篇，全部中文（每个业务域「名词解释」+「业务流程」各一篇，另有索引 README）。
  不少文档仍是「待团队补充」的骨架。
- 检索路径与 N3 `search_rules` 工具完全一致：`tokenize(query)` → `KnowledgeRetrieval.load_domain(PLATFORM_RULE, keywords)`。
- 评估器：`backend/app/eval/rag_e5.py`（`uv run python -m app.eval.rag_e5`，零 LLM 调用）；校验 `backend/tests/eval/test_n4_rag_baseline.py`。
- 指标：Recall@3/5、MRR、nDCG@5（二值相关）只对可回答的 54 条计算；「拒答率」= 应找不到的 10 条里检索返回未命中的比例。
- 引用正确率与回答忠实度需要 LLM 裁判（R3），已于 2026-10-01 获授权完成，见文末一节。

## 发现

1. **域过滤是主要瓶颈**：`load_domain(PLATFORM_RULE, ...)` 先要求文档包含「规则 / 政策 / 平台要求 / rule」之一，
   只有索引 README 与两篇平台规则文档满足。商家问退货、优惠券、理赔、口径时，正确文档根本不在候选里。
   v1 链路按意图分类选域，不受此影响；受影响的是 N3 起的 v2 `search_rules` 工具。
2. **关键词匹配本身尚可，但不会说「找不到」**：问题按 2–4 字滑窗切词，只要任一片段出现在文档里就算命中，
   应找不到的 10 条里一半被凑出了结果（如「广告投放的出价规则」命中平台规则文档）。
3. **英文提问并非完全失效**：分词时会通过中英业务词表反查中文，诊断上限下英文问题 Recall@5 为 0.88；
   生产路径为 0 是域过滤所致。
4. **多文档组合最弱**：诊断上限只有 0.58，单域检索天然拿不全跨域答案。

## 对后续任务的含义

- 混合检索（Task 4）须与本基线对比，Recall@5 与 MRR 都要优于生产路径才可上线；诊断上限可作为「只修域路由」的参照——
  如果去掉固定域、在全部文档上做关键词检索就能接近上限，向量召回的增益要相对这个更便宜的改法来证明。
- 拒答率需要单独的阈值设计（向量相似度或融合分数下限），否则混合检索同样会凑结果。
- 语料偏小且多为骨架；索引版本质量门（Recall@5 不低于上一版本 95%）在这个规模上波动会较大，需要在 Task 2 里注意。

## 2026-10-01 改进：`search_rules` 改为全文档检索（不依赖向量）

依据上述发现 1，`search_rules` 不再固定平台规则域，改用 `KnowledgeRetrieval.search_documents`：在全部团队知识里按「标题 > 路径 > 正文」
加权打分排序，至少命中 2 个不同的**分词片段**才算候选，最多返回 5 篇。`load_domain` 与 v1 链路不变。

> **阈值的实际含义（2026-10-01 独立复审 I-3 更正）**：片段来自 `tokenize` 的 2–4 字滑窗，重叠片段分别计数，
> 所以「2 个片段」约等于「命中查询里一段至少 3 字的连续文字，或两段各 2 字」，而不是「两个独立概念」——
> 一个 3 字以上的词可以独自过关。查询本身只切出 1 个片段（如「退款」）时阈值降为 1，否则永远检索不到。
> 评测集里没有单片段查询，此修正不改变下表数字。

| 检索方式 | Recall@3 | Recall@5 | MRR | nDCG@5 | 拒答率 | 平均返回篇数 |
| --- | --- | --- | --- | --- | --- | --- |
| 原路径（固定平台规则域） | 0.093 | 0.093 | 0.074 | 0.066 | 0.50 | 1.45 |
| **当前 `search_rules`** | **0.713** | **0.759** | **0.639** | **0.652** | **0.90** | 2.59 |
| 诊断上限（假设业务域选对） | 0.750 | 0.861 | 0.646 | 0.677 | 0.50 | 2.45 |

按类别 Recall@5：口径 1.00、流程与规则 1.00、多文档 0.75、英文提问 0.75、字段 0.44、口语化 0.38。

- 「至少 2 个不同查询词」的阈值在同一评测集上比较 1/2/3 个词与最低分门槛后选定：要求 1 个时 Recall@5 0.889 但拒答率 0.30（比原路径还爱凑结果），
  要求 2 个时三项均优于原路径。**阈值与评测集同源，存在过拟合风险**，混合检索上线时应换用留出集复核。
- 剩余短板是口语化改写与字段名查询：问法用词与文档用词对不上，这是向量召回要补的部分。
- 回归：S7 后端场景、`test_merchant_chat_definitions.py`、工具与知识单测、`tests/eval` 共 373 passed。

## 2026-10-01 引用正确率与回答忠实度（真实模型，用户授权 R3）

- 入口 `backend/app/eval/rag_judge_e5.py --real`（Fake 演练 `backend/tests/eval/test_n4_rag_judge_e5.py`）；检索为当前 `search_rules`（全文档）。
- 每题：模型依据围栏后的检索文档作答并标注 `[source_path]`（1 次），再由模型当裁判输出结构化判定（1 次）。引用的文档是否在检索结果里由规则判定。
- 模型 `deepseek-flash`；**128 次调用全部成功，共 184,360 token**（作答 88,213、裁判 96,147），未调高每日预算；本地可丢弃库 `borough_e5_real_test`。

| 指标 | 结果 |
| --- | --- |
| 引用正确率（有检索结果的可回答题 47 道） | **0.979**（46/47） |
| 引用存在率（引用都在检索结果中） | 0.979 |
| 回答忠实度（裁判） | 1.000（**人工抽查见下，不宜视为满分**） |
| 如实拒答（应找不到 10 道 + 检索落空 7 道） | **1.000**（17/17） |
| 裁判输出解析失败 | 0 |

人工抽查 10 条：
- R-002（失败）：内容与文档一致，但引用写成空括号 `[]`，引用格式未遵守；
- R-051：回答「会被扣」并推断「申诉成立可撤销处罚，否则会走到保证金扣划」，文档只有流程步骤，属轻度超出文档的推断，裁判判为忠实——同模型自评偏宽；
- 其余 8 条引用准确，骨架文档会说明「待团队补充」，应找不到的题明确拒答（R-060 检索误命中一篇，模型仍如实拒答）。

结论：在当前语料与检索下，模型能遵守「只依据文档、标注来源、未覆盖时承认」的约束；忠实度应表述为「裁判 47/47，人工抽查 10 条有 1 条轻度推断」。
裁判与作答同模型，后续若要更可靠的忠实度数字，应换用不同模型或人工标注。
