# 小林 RAG 专题 × Borough 项目问答设计

## 目标

阅读小林面试笔记 RAG 专题中与 Borough 商家 AI 助手强相关的文章，把通用 RAG 知识改写为能够检验项目真实实现、明确缺口与演进取舍的面试问答。

本轮只处理 RAG 专题；它与既有 Agent 专题分文件维护，不混写，以便面试复习与事实核验。

## 产物

- 路径：`interview/xiaolin-rag-project-qa.md`
- 题数：15～20 题，目标 18 题，绝不超过 20
- 语言：中文
- 每题固定包含：来源文章、项目状态、详细解答、项目证据、设计取舍与缺口、可能追问

网页文章只支撑 RAG 通用原理；Borough 状态必须由源码、测试和项目文档证明。每题至少给出一个小林网页来源和一个本地证据。不得转载文章长段落，不得泄露密钥、完整生产 Prompt 或经营数据。

## 强相关选题范围

保留并映射以下问题：

1. Borough 的知识检索链路是否构成 RAG，以及它解决什么问题；
2. RAG 与微调的边界；
3. 知识文档的来源、分域、粒度、存储和导入；
4. 文档切分、语义连续性与当前未采用的 Chunking；
5. 当前关键词/规则检索与未采用的 Embedding、向量数据库；
6. Query Rewrite 与跨语言检索；
7. 多路召回、排序和规则收窄；
8. RAG 上下文拼装、Token 预算与检索注入；
9. RAG 幻觉、引用、来源可见性和无命中降级；
10. RAG 检索质量评测、线上反馈与缺口；
11. 知识库动态更新、版本并发控制与管理后台；
12. 团队知识、商家记忆与不同来源的冲突优先级；
13. 多语言知识召回与机器翻译边界；
14. 检索安全、提示词注入与商家隔离；
15. 何时需要 Hybrid RAG、Rerank、Graph RAG 或向量数据库；
16. RAG 在 Borough 的最大难点和演进优先级。

以下文章只作筛选背景或合并进入项目问题，不单独凑题：纯 Embedding 算法细节、在项目未采用向量库前无法基于真实经验回答的向量数据库性能题，以及没有业务实体关系需求支撑的 Graph RAG 细节。

## 项目事实边界

- 当前知识检索以 `KnowledgeRetrieval`、业务域和确定性相关性评分实现；不能说已经使用 Embedding、向量数据库、Reranker、Hybrid Retrieval 或 Graph RAG。
- 人工维护的团队知识优先；商家记忆仅在团队知识未命中时作为 fallback，并按 `merchant_id` 隔离。
- 知识库有管理员 CRUD、路径策略、版本控制、源语言/人工译文和机器翻译缓存；这些能力不等于自动化内容质量治理。
- `analysis_sources`、`quality_notes`、`degraded` 与 `degraded_reason` 必须如实表达知识来源和失败，不能以模型回答掩盖检索未命中。
- 真实 LLM 调用需要用户另行按项目 R3 授权；本次研究和文档任务不调用 DeepSeek。

## 验收与自检

完成时检查：

1. `^## [0-9]+\.` 的题数为 15～20；
2. 六个必备字段各出现题数次；
3. 小林 RAG 文章 URL 与本地相对链接都有效；
4. 无 `TODO`、`TBD`、密钥样式或不实实现声明；
5. 不把知识库/记忆说成向量库，不把机器翻译缓存说成权威业务知识，不把规划写成已实现；
6. 不执行真实模型、应用代码修改或 Git commit。
