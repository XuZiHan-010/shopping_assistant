# 小林 AI 专题 × Borough 项目问答设计

## 目标

阅读小林面试笔记 AI 专题中与 Borough 商家 AI 助手强相关的文章，把通用知识改写为能够检验本项目真实设计与实现的面试问题，并提供基于代码、测试和项目文档的详细答案。

首轮只处理 Agent 专题。后续 RAG、LLM 工具调用、大模型工程和 LangChain/LangGraph 专题沿用同一方法，但分别交付，避免一次性文档过大。

## 产物形式

首选 Markdown，而不是独立网页：

- 路径：`interview/xiaolin-agent-project-qa.md`；
- 原因：适合长篇问答、代码证据可点击、可直接在 VS Code/GitHub 阅读、便于审查差异；
- 文档结构预留五个专题，本轮只完成 Agent 部分；
- 内容稳定后如确有演示需求，再基于同一 Markdown 生成网页，避免同时维护两份事实源。

## 选题原则

1. 每个专题最多 20 题；Agent 专题目标为 15～20 题，预计 18 题。
2. 只保留能够映射到 Borough 架构、代码、安全、成本、评估或演进决策的文章。
3. 不要求项目使用文章中的同名技术。应把框架问题转换为项目问题，例如：
   - “LangChain 如何实现短期和长期记忆”转换为“Borough 如何实现短期和长期记忆，为什么没有采用 LangChain Memory”；
   - “Multi-Agent 如何协作”转换为“Borough 为什么当前选择单 Agent 工作流，何时才值得拆成 Multi-Agent”；
   - “Agent 工具调用”转换为“Borough 如何把模型意图转换为后端受控查询，而不让模型执行 SQL”。
4. 不为凑数量收录与项目弱相关的纯模型训练理论。
5. 不大段复制原文，只提炼文章知识并重新结合项目表达。

## 每道题的结构

每题统一包含：

1. **来源文章**：文章标题和原始链接；
2. **问题**：改写成针对 Borough 的面试题；
3. **详细解答**：先给可直接口述的结论，再解释原理和实现；
4. **项目现状**：明确标记“已实现 / 部分实现 / 未实现”；
5. **代码证据**：链接到关键源码、测试或设计文档；
6. **设计取舍与缺口**：说明为什么这样做、当前边界和合理演进方向；
7. **可能追问**：列出 1～3 个面试官可能继续深入的问题，并给简短答题要点。

## Agent 专题候选范围

优先研究并从中筛选约 18 题：

- Agent 与普通 LLM 调用、Workflow、Tools 的边界；
- Borough 的 Agent 组件与 LangGraph 状态流；
- ReAct、Plan-and-Execute、Reflection 与本项目实际范式；
- 复杂任务拆分和受控查询计划；
- 短期会话上下文、长期商家记忆及记忆压缩；
- 单 Agent 与 Multi-Agent 选型；
- 为什么部分能力手工实现而不是完全交给框架；
- 规划能力与结构化意图；
- Reviewer 反思机制和质量循环；
- 上下文组装、知识与经营数据隔离；
- 多轮状态、幂等、中断和失败恢复；
- Agent 评测集与线上指标；
- 重复调用、路径震荡和死循环治理；
- Trace、延迟和 Token 成本定位；
- 任务幻觉与“没有执行却声称完成”的防护；
- 数据库越权、敏感数据泄漏和查询幻觉；
- 成功、失败、显式降级和未来转人工边界。

## 研究与核验方法

1. 逐篇打开候选文章，记录其核心论点、适用条件和风险。
2. 对每个知识点检索 Borough 实际代码、测试和最新进度文档。
3. 发现文章建议与项目不一致时，解释差异，不强行宣称项目已经实现。
4. 每道题至少提供一个网页来源和一个项目证据；纯设计演进题可使用多个项目证据。
5. 完成后检查：
   - 题目总数不超过 20；
   - 没有重复问题；
   - 所有本地路径和网页链接有效；
   - “已实现/部分实现/未实现”与代码一致；
   - 不泄露密钥、完整 Prompt 或生产敏感数据；
   - 不触发真实 DeepSeek 调用。

## 非目标

- 本轮不修改 Borough 应用代码或架构；
- 不创建新的 Agent 功能；
- 不把文章内容完整转载进仓库；
- 不为了网页展示新增前端依赖；
- 不执行真实模型评估或产生项目 LLM 费用。
