## M1 产品定位与范围（已确认）

| # | 决策 | 结论 | 理由摘要 |
| --- | --- | --- | --- |
| D1 | 顾客端形态 | **店铺级顾客 Agent**：Borough 上每家店有店铺页与店铺助手，只服务本店顾客（售前咨询、加购结账交接、订单、售后） | 最大化复用蓝图购物 Agent；数据按 `merchant_id` 隔离，R5 不推翻；双端联动发生在「店与其顾客」之间 |
| D2 | 功能范围基线 | 采用 2026-09-18 对话中的功能清单（顾客端 / 商家端 / Agent 内核 / 评测运维四部分）作为新 PRD 的范围基线，并按 D3–D6 修正 | 用户未提出异议并进入细化阶段 |
| D3 | 行业范围 | 只做电商零售一个领域：蓝图零售示例改造为 Borough；旅行、电信、票务不进产品、不部署，仅作为 `vendor/` 内的原样参考，不删除 | 数据与知识库只覆盖电商；vendor 保持与上游一致便于对比 |
| D4 | 营销与促销 | 只做「定价与促销」：新建优惠券/促销数据；券型仅满减券、折扣券，可限定商品或全店；护栏含券面折扣率上限、单次调价幅度上限、促销必须有结束日期；顾客端只显示已生效的券。**不做**站外营销活动（`marketing-campaigns`） | 优惠券是站内双端闭环；站外活动的花费与归因数据只能编造，经不起追问 |
| D5 | 库存 | 做库存并形成商家端闭环：商品新增可售库存与低库存阈值，近 30 天销量由订单明细计算；商家端有低库存 / 售罄 / 滞销告警与「可售天数」计算，补货调整经商家批准后生效（按增量写入并比对当前库存）；顾客端只显示有货 / 紧张 / 售罄三档。本版**不做多规格**（一个商品一个库存数）；补货 = 登记到货后增加可售库存，不做采购单、供应商、入库质检；扣减时机在 M3 结账题裁定 | 库存是顾客端刚需；补货可展示应用时的并发校验；滞销处置可与 D4 促销联动 |
| D6 | 附件 | **本版不做附件**：商家端不支持 Excel、PDF、图片上传或附件分析；顾客退货只提交结构化原因和文字说明，不上传照片；不建设对象存储、OCR、文件解析和附件异步任务；现有规划中的附件接口、`ATTACHMENT` 回答模式及相关 P1 验收项迁入后续版本；`vendor/` 内与附件相关的示例（如有）原样保留仅作参考；DeepSeek 是否支持图片输入不影响本次取舍，未来重启附件能力时再依据当时官方 API 核实 | 把资源集中在双端零售闭环、受控写操作、Agent 内核和评测上 |

## M2 身份与权限（已确认）

| # | 决策 | 结论 | 理由摘要 |
| --- | --- | --- | --- |
| D7 | 顾客身份 | **访客 + 演示顾客身份**。<br>① 顾客身份为平台级身份；`buyer_key` 只由服务端会话解析；订单、退款、售后查询始终强制 `merchant_id` + `buyer_key` 双重过滤。<br>② 顾客端不得提交或覆盖 `buyer_key`，模型不能决定身份。<br>③ 选择演示顾客身份时，服务端创建新的高熵会话 ID；该 ID 即凭证，必须支持过期、注销与撤销；沿用蓝图 `X-Session-Id` 传递模式。<br>④ 演示身份入口只在演示模式开放；它演示的是隔离机制，不等同于真实身份认证；未来可替换为验证码 / JWT，下游业务接口不变。<br>⑤ 商家只看到店铺范围内的脱敏别名，由 `merchant_id` + `buyer_key` 派生，不同商家无法串联识别同一顾客；不得展示原始 `buyer_key`、手机号或地址。<br>⑥ 身份选定后只合并当前匿名会话的购物车，合并须一次性、事务性、幂等；已绑定顾客的购物车不得切换归属，换身份须先注销或新建访客会话。<br>⑦ 跨顾客访问返回 403 并写安全审计，响应不泄露目标订单的任何信息；**订单不存在与不属于本人返回同一个 403**（O1 已确认）；响应正文、耗时与错误结构也须保持一致，避免旁路枚举；内部日志可区分原因。 | 真实注册登录不是 Agent 能力；A 足以演示服务端身份绑定与双重过滤；身份来源抽象后可替换 |
| D8 | 商家与管理员身份 | **商家也改为会话模式**。<br>① 顾客与商家复用同一套会话基础设施，但使用不同的角色、状态模型和路由依赖，不是可互换的凭证。<br>② 商家登录时以演示 Bearer Token 换取高熵会话 ID；后续由会话解析 `merchant_id`，请求和模型均不得指定或覆盖它。<br>③ 商家会话调用顾客端点、顾客会话调用商家端点，一律 403 并写安全审计。<br>④ **来源状态不得跨对话**：来源校验按 role + principal + `merchant_id` + 对话隔离，并用版本号防止并发覆盖；新建对话或切换商家时来源状态从空开始，某次对话见过的对象不能永久获得修改资格。（O2 已确认：隔离键为**登录主体 + 店铺 + 对话 ID**；登录会话只负责身份认证，一个对话取得的对象访问资格不得扩散到其他对话）<br>⑤ **撤销须级联**：撤销演示商家 Token 时，同步失效由它换取的全部现存会话。<br>⑥ 管理员继续使用 `X-Admin-Token`，不进入 Agent 会话体系。<br>⑦ `VIEWER_TOKEN` 保持现有只读范围，写操作及敏感管理端点继续拒绝。 | 蓝图闸门依赖服务端会话状态，统一机制只需实现与测试一次；避免「登录凭证已撤销、旧会话仍可用」 |
| D9 | 审批权限 | **同店铺的商家会话可批准，且只能经审批界面**。<br>① 批准只走工作台审批接口；聊天里的「批准」不生效；批准标记只对该次应用调用有效，不遗留。<br>② 应用时按当时生效的配置重新检查护栏。<br>③ 变更账本记录起草者、批准者、批准时间与护栏检查结果。<br>④ 批准与丢弃只能由同店铺商家会话执行，改动须属于当前商家；跨店铺 403 并写审计。<br>⑤ 只有「暂存」状态可被批准；重复批准幂等，不重复生效。<br>⑥ 暂存超过约定时限（默认 7 天）自动过期，不可再批准。<br>⑦ **批准绑定草案版本**：批准针对某一具体草案版本；草案内容变更后旧批准失效，须重新批准。<br>⑧ **目标版本校验**：应用时校验目标对象的版本 / 当前值（如库存的 changeFromQuantity、商品内容的版本号），不匹配则拒绝写入并保持暂存。<br>⑨ **状态迁移原子且幂等**：暂存 → 已应用 / 已丢弃 / 已过期 的迁移在事务内完成，重复请求不产生二次副作用。 | 演示场景每店一位操作者，双人复核体验差；A 已覆盖「模型不能自批、审批不走聊天、标记一次性、应用时复检、全程留痕」；角色分工待真实账号体系时再加 |

| D10 | 顾客对话对商家的可见性 | **按单据关联摘要**。<br>① 摘要只覆盖与该单据相关的对话片段，不是整段会话；生成摘要同样走外部文本隔离，防止顾客在对话里写指令影响商家端 Agent。<br>② 摘要不出现手机号、地址、支付信息；顾客标识用店铺级脱敏别名（D7⑤）。<br>③ 顾客在店铺页可见「这段对话已随申请提交给商家」，不做暗中收集。<br>④ 商家查看行为写审计（谁、何时、查看哪个单据的摘要）。<br>⑤ **提交前预览**：顾客提交单据前可预览将要随单提交的摘要。<br>⑥ **不可变来源快照**：随单提交的对话片段与摘要生成时即固化为快照，事后对话变化不影响已提交内容。<br>⑦ **摘要失败不阻断**：摘要生成失败不影响单据提交，降级为「摘要不可用」并标明原因。<br>⑧ **商家不可回看全文**：商家只能看到摘要与快照片段，不能展开或检索完整对话。 | A 缺上下文，C 需实时会话与坐席、隐私面过宽；B 边界清楚且可平滑升级 |

## M3 顾客端（已确认）

| # | 决策 | 结论 | 理由摘要 |
| --- | --- | --- | --- |
| D11 | 商品内容 | **补齐一组精简字段**：短描述（卖点）、详细描述、开放式属性表（键值对）、可选图片地址，外加 D5 的库存与阈值；不做多图富文本、类目属性模板与 SKU 规格。<br>① **属性值三来源**：商家已填、商家在对话中明确给出、可从描述原文直接读出；模型不得按「同类通常如此」推断。<br>② **属性级来源追踪**：至少记录 `source_type`、来源引用、更新时间；从描述提取须能指向原文片段或源版本；提取后写入属性仍属商家改动，须暂存并经 D9 审批。<br>③ **完整度由后端确定性规则计算**，不交给模型：每个类目维护轻量规则（最短描述长度、必需属性键、是否期望图片），仅服务缺口检测，不是完整类目模板。<br>④ **完整度是派生结果**：描述、属性或图片变化后重算，不把可能过期的分数当事实源；据此生成内容缺口信号。<br>⑤ **图片地址受控**：本版（D6 不做上传与对象存储）只接受演示静态资源或允许名单内的 HTTPS 地址；后端不抓取任意 URL，避免 SSRF 与外部追踪。<br>⑥ **双语**：保存源语言与源版本；请求另一语言时复用现有本地化缓存；源内容更新后旧译文立即标记过期；属性键、文本型属性值、卖点与描述参与本地化，数字、单位、商品编码不翻译；翻译不可用时明确回退源文，不把机器生成内容冒充商家原文。<br>⑦ **演示目录确定性**：包含完整商品、缺关键属性、描述过短、无图片等可复现样本，并至少准备一条可演示「顾客提问 → 发现缺口 → 商家补充 → 顾客端可回答」的商品。 | 结构化属性是「不编造」规则的载体，也是商家端内容维护的前提；完整类目模板与 SKU 超出本版范围 |
| D12 | 导购 Agent 能力边界 | **蓝图顾客端 5 个 Skill 全要**（搜索发现、选购研究、目标规划、售后服务、记忆与个性化），**不加站外搜索**。<br>**可以**：基于本店商品的推荐 / 对比 / 组合方案（价格与库存档位来自工具结果）；引用本店与平台规则文档回答退换货、运费、发票等问题；加购物车、改购物车、生成结账摘要；起草退货申请交顾客确认；记住顾客偏好。<br>**不可以**：承诺规则之外的事（免运费、额外折扣、加急、特殊赔付）；编造商品信息（属性缺失即说明缺失并生成信息缺口信号）；跨店比价；下单或扣款；给医疗、用药、法律、金融等专业建议（只说明商品信息并建议咨询专业人士）；与顾客谈价（价格由商家设定，仅可告知现有优惠券）。<br>补充边界：<br>① **闭集知识来源**：回答只能来自本店商品数据、平台/店铺规则知识库、顾客本人订单与本轮对话，不引入站外搜索与模型常识补全。<br>② **购物车来源闸门**：只能加入本轮对话中工具返回过的商品 id。<br>③ **结账重校验**：结账时重新校验价格、库存、商品状态与优惠券适用性，不沿用对话中的旧值。<br>④ **售后界面确认**：售后类写操作一律由顾客在界面确认，聊天中的「确认」不生效。<br>⑤ **店铺级可控记忆**：顾客记忆按店铺范围隔离，顾客可查看、删除与关闭。 | 5 个 Skill 蓝图现成，改造成本在措辞与数据；目标规划最能体现 Agent 价值；站外搜索无法追溯验证且依赖 Claude 服务端能力 |
| D13 | 购物车、结账与库存扣减 | **Borough 自带演示结账页，流程为「提交订单并占库 → 模拟支付」**，不接真实支付，页面明确标注演示。<br>**购物车**：属于会话或顾客身份，不占库存；加购只校验在售与未售罄，真正可售性在提交订单时重新校验。<br>**结账**：后端重新计算单价、优惠券与总价，不采信前端与模型金额；Agent 的结账摘要仅为展示；库存不足 / 下架 / 券过期时明确提示不可用项，不静默调整。<br>**订单与库存**：提交订单时在**同一事务**内创建订单（待支付）并占用库存；模拟支付成功转「已支付」，占用转实扣；30 分钟未支付关闭订单并释放占用；扣减使用带条件更新，禁止超卖；`buyer_key` 取自会话身份，不接受前端传入；订单写入现有 `orders` 表。<br>补充：<br>① **库存双计数**：区分在库量与占用量，可售 = 在库 − 占用。<br>② **事务原子性**：订单创建与占库原子完成，任一失败整体回滚。<br>③ **价格快照**：下单时固化单价、优惠减免与总价到订单明细，后续改价不影响历史订单。<br>④ **幂等**：提交订单、模拟支付、关闭订单均幂等（幂等键），重复请求不产生二次副作用。<br>⑤ **支付 / 过期竞争控制**：支付与超时关闭并发时以状态机 + 条件更新裁决，只有一方生效，不出现「已支付又被关闭」或重复释放库存。 | 只有闭环才能演示「下单 → 库存变化 → 商家告警 → 补货」；真实支付涉及资金与合规，与项目目标无关 |
| D14 | 订单状态与物流 | **订单状态 + 订单事件表**。事件节点：已下单、已支付、已出库、运输中、派送中、已签收。<br>① 事件表**追加写**，不修改历史事件；订单状态由最新事件派生，不两边各写。<br>② 演示数据节点时间**确定性生成**（如支付后 6 小时出库、次日运输中、第 3 天签收），保证可复现。<br>③ 顾客只能看到本人订单的事件（D7 双重过滤）。<br>④ 本版**不做物流公司与运单号**，节点只描述状态与时间。<br>⑤ 时间存带时区时间戳，按顾客语言与时区格式化。<br>补充：<br>⑥ **状态多维分离**：支付状态、履约状态、售后状态分列，不混成单一状态字段。<br>⑦ **事件状态机**：事件须符合允许的迁移路径，非法迁移拒绝写入。<br>⑧ **单履约流**：本版一个订单只有一条履约流，不做拆单、部分发货与多包裹。<br>⑨ **事件幂等**：事件写入幂等（去重键），重复上报不产生重复节点。<br>⑩ **显式时区来源**：存储统一 UTC 并显式记录来源时区，展示按查看者时区换算，不做隐式推断。 | 签收时间是售后时效判断的依据；发货超时告警需要支付与出库节点；接真实物流与项目目标无关 |
| D15 | 售后范围与流程 | **做退货退款 + 仅退款 + 客服工单，不做换货**。<br>① 发起条件由后端按订单状态、签收时间与平台规则判定，模型只解释结论与收集原因；超时效或状态不允许时说明依据条款，不许诺特例。<br>② 退货状态机：待商家处理 → 已同意 / 已拒绝 / **待顾客补充信息** → 待顾客寄回 → 商家已收货 → 已退款 → 关闭；状态变化追加写事件，与 D14 一致。<br>③ 退款只产生记录，不接真实退款渠道，界面标注演示；金额由后端按 D13 价格快照计算，不采信模型金额；**行级退款上限**：单行累计退款不得超过该行价格快照金额。<br>④ 库存回补：**默认不回补**，仅当商家验货后明确判定为可售才回补，并写明来源为退货的库存事件。<br>⑤ **单工单入口**：每个售后事项只生成一条工单作为商家唯一处理入口，避免重复工单与两处处理。<br>⑥ **退款口径（O3 裁定）**：不把退款冲减后的值继续称为 GMV，拆成三个指标——`gross_gmv`（按支付日计入，不因退款追溯改写）、`refund_amount`（按退款发生日计入）、`net_gmv` 净成交额（当期 `gross_gmv - refund_amount`）；另提供「按原订单日归属退款」的订单队列 / 对账口径，标明数据截至时间，该口径会随后续退款回补历史结果。三个指标与对账口径均写入指标口径文档。 | 换货链路长且与退货演示价值重合，D5 不做多规格使「换规格」场景不存在；仅退款与退货退款两条路径体现 Agent 依订单状态选流程 |
| D16 | 顾客记忆 | **只做事实型记忆**（键 + 值 + 类别），不做顾客侧总结型记忆。<br>① 按**顾客 + 店铺**隔离；商家不可见，商家只看单据摘要（D10）。<br>② 只从顾客与助手的对话文字抽取，不读工具结果；**只记录顾客明确表达或确认过的事实**，助手文字仅用于理解上下文，不能仅凭助手推测写入。<br>③ 写入过滤拒绝手机号、身份证、银行卡、地址、邮箱等标识信息，以及健康、宗教、政治等敏感推断；单条长度沿用蓝图上限；同义事实更新而非堆叠。<br>④ 近期少量事实随提示词注入，其余按需检索；记忆是默认值不是命令，与本次对话冲突时以本次为准。<br>⑤ 顾客可查看全部记忆、逐条删除、一键关闭「记住我的偏好」；关闭会清空已有记忆，**执行前须明确提示顾客确认**；关闭后不再写入。<br>⑥ 保留期 **180 天**，按单条记忆的最后确认或更新时间滚动计算，**仅被读取不续期**；过期自动清理。 | 顾客场景记忆天然是短事实，易展示、易删除；顾客侧总结型画像难核对、难删除且易写入敏感推断 |

| D18 | 每日简报 | **定时预生成 + 对话可重新生成**：工作台直接读预生成结果；对话或按钮刷新**同一份**当日简报。<br>① 事实只来自本轮授权工具结果（库存告警、订单异常、顾客信号、待批准改动、指标显著变化）；昨天的简报、历史总结与记忆不得充当今日事实或数字来源，仅可影响语气与呈现格式。<br>② 正文 3–6 条，其余折叠为「另有 N 项」；每条包含问题、数字依据、可用的下一步动作；数字缺失时说明缺什么，不估算。<br>③ 排序以涉及金额为主；即将超过发货、工单等硬性时限的事项可进入最高优先级；**金额未知不自动排到末尾**。<br>④ 动作按钮只把问题填入输入框，不发送、不批准、不执行，且只能指向已有能力。<br>⑤ 「当日」按商家配置时区计算；简报展示**数据截至时间**与**生成时间**。<br>⑥ 同一商家、同一营业日只有一份当前简报；定时重试与手动重新生成均为更新 / 版本替换，不新增重复简报，并有并发锁与幂等保护。<br>⑦ 顾客信号只使用聚合或脱敏结果，顾客原始标识、地址、联系方式不得进入简报或模型上下文。<br>⑧ 生成失败时显示安全可理解的降级说明（不泄露内部异常、SQL、模型信息）并提供重新生成；旧简报可作为历史保留，但不得标为今日简报。<br>⑨ 「立即重新生成」须限流、冷却与预算熔断。<br>⑩ 开发阶段定时任务默认关闭，对话触发与立即重新生成默认使用 mock/fake LLM；任何真实 DeepSeek 调用按 R3 事先说明模型、次数与预计费用并取得授权。 | 工作台开箱即见、对话可刷新保证时效；定时任务本身可展示异步、幂等与失败处理 |
| D19 | 指标与归因 | **实时计算 + 日汇总兜底**；归因沿用五步法：确认波动 → 定位分项 → 区分结构与水平 → 验证候选原因 → 按证据分级表述。<br>**修正**：周期不完整时**不一律停止分析**，先尝试等长可比周期（如本周前三天 vs 上周前三天）；只有数据缺口、异常基期或样本不足导致无法形成有效比较时才停止归因。<br>① 数据源由**后端查询规划器**按跨度与粒度选择，模型不能指定走明细表还是汇总表。<br>② 跨越今天的长周期查询采用混合结果：已结束日期走日汇总、当天走实时明细，边界不重叠不漏算。<br>③ 响应明确返回数据截至时间、数据来源（实时 / 日汇总 / 混合）与指标定义版本。<br>④ 日汇总不永久冻结：退款、退货等迟到数据定期回补近期汇总；指标口径变更后必须重算或隔离旧版本，不得混用。<br>⑤ 一致性测试覆盖时区边界、退款跨日、订单取消、零值分母与未完整周期，不只测正常样例。<br>⑥ 「事件与波动时间吻合」最多是线索；只有存在直接机制证据或可靠实验依据时才可使用因果措辞。<br>⑦ 整体变化接近零或正负贡献互相抵消时，占比会失真，改报绝对贡献值并说明不计算比例。<br>⑧ 超出查询上限时返回明确限制并建议可用时间范围或更粗粒度，不得静默截断。<br>⑨ 指标定义唯一（指标口径表），实时与汇总共用同一定义；图表数据点由后端生成；R4 不变，模型只输出结构化查询意图。<br>**总边界**：模型只表达分析意图与组织语言；指标定义、数据源选择、SQL、计算、合并与图表数据点全部由后端确定性产生。 | 当天数据必须可见，长周期实时聚合过慢；五步法可产出可追溯、分级表述的结论 |

| Q15 | 同时限制循环轮数、工具总次数、LLM 调用次数、墙钟时间与 token，不只设固定轮数；**只有互不依赖的只读工具可并行**；身份、权限、安全拦截属**致命错误必须终止**，不得包装成普通工具错误继续 |
| Q16 | **LangGraph 冻结为只读评测基线（O4 裁定）**：不立即退役，但不再实现新 Skill、新工具与写操作；只与新循环比较**双方共有的旧能力**，不要求新功能实现两遍；固定其依赖、测试数据与评测集；**基线不部署生产**。Reviewer 保留，但**确定性校验必须先于 LLM Reviewer，安全不依赖 Reviewer** |

| Q18 | 索引 + 按需加载；Skill 必须是可信、版本化、只读的白名单资源，限制长度与单次加载数量；**加载器不能访问任意路径**；测试覆盖正确触发、误触发、多 Skill 冲突与更新后回归 |
| Q19 | 两种策略都实现用于对比，但**生产选定一种确定策略**；压缩后必须保留工具来源、数据截至时间与草稿版本；旧对话摘要是模型生成内容，**不得升级为事实来源**；身份保存在服务端可信上下文，不反复塞进提示词 |
| Q20 | 回合结束后异步抽取，只读对话文字，失败不影响主回答；需幂等任务、租户隔离、重试上限、单独预算、写入前后双重过滤；**不预设更便宜模型足够**，须经敏感信息误写率与事实准确率评测后选择；真实调用遵守 R3 |
| Q21 | 混合召回 + pgvector；**不锁死 bge-m3**，先建关键词基线，再选较小的多语种嵌入模型并实测部署内存与镜像成本；重排须证明收益；指标至少含 Recall@k、MRR / nDCG、引用正确率与回答忠实度 |
| Q22 | 只暴露只读工具子集；远程传输用 Streamable HTTP；使用**独立、短期、可撤销、限定商家与 scope 的凭证**，不把浏览器会话 ID 交给第三方客户端；正式兼容外部客户端时按 MCP 授权规范实现 |
| Q23 | 稳定前缀方向不变，但**缓存是 best-effort，不作为正确性依赖**；工具与 Skill 索引稳定排序、确定性序列化；记录缓存命中 token 验证收益；语言指令可动态后置，**安全规则必须在高优先级静态部分** |
| Q24 | 保留 R7 字段并迁入新契约；实现时**区分整轮降级与单个来源 / 工具降级**，避免非关键工具失败让整轮结果显得完全不可用 |
