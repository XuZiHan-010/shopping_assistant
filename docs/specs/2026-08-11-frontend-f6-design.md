# F6「Railway 部署就绪」设计说明

**日期：** 2026-08-11
**状态：** 待用户审阅
**对应实施计划：** `plans/2026-08-11-frontend-f6-railway-mvp-closeout.md`

## 目标与边界

F6 的目标是让 Borough 商家助手具备 Railway 部署和两轮线上验收的条件，而不是宣告 MVP 完成。
本阶段先完成可在本地验证的 F6-0 与 F6-A；F6-B 中创建 Railway 服务、配置变量和线上验收由用户在控制台执行，编码工作仅提供配置和操作手册。

F6-0、F6-A 和 F6-B 第一轮均不配置或调用 DeepSeek，模型网络请求和费用均为零。第二轮真实模型验收必须在执行前另行获得用户明确同意。

## 方案选择

采用「后端前置切片 → 前端构建门禁 → 用户部署验收」的顺序：

1. F6-0 先修复生产演示身份通路与未配置 LLM 时的预算预扣，避免无 Key 的线上验收既不能选择商家又污染运维计数。
2. F6-A 再通过真实浏览器网络断言和构建期机械检查，保证 ECharts 不进入首屏网络路径、Mock 不能进入生产镜像、构建产物不含密钥，并补齐前端 Railway 配置。
3. F6-B 由用户完成 Railway 控制台配置，先进行零模型调用验收；只有用户批准后才进行两次聊天请求、最多 12 次 DeepSeek 调用的真实模型验收。

仅完成前端 F6-A 会遗留生产演示身份和用量计数缺陷，因此不采用。

## 组件与数据流

### F6-0：生产配置与用量完整性

`Settings` 新增默认关闭的 `demo_deployment_mode`。生产环境只在该显式开关为真时开放既有演示商家端点；其余生产安全校验保持不变。运维状态端点只返回该布尔状态，不返回商家数据或敏感配置。

`LlmCostGuard.complete()` 在任何 token 估算和预算预扣前检查底层客户端是否已配置。未配置时立即抛出既有不可用错误，从而不调用预算仓储、不递增 `call_count`；已配置场景的预扣与回填语义不变。

### F6-A：首屏、构建与部署配置

图表面板使用异步组件，但只在浏览器空闲或收到带图表的回答时通过 `v-if` 挂载。首屏保留可访问的静态占位，避免仅异步导入却在首帧触发 loader。Playwright 监听首屏网络请求，静态脚本检查构建 HTML，二者共同防止 ECharts chunk 回到首屏。

Docker 构建显式接收 `VITE_USE_MOCK` 并在真值时失败。密钥扫描仅检查构建产物；变异验证会临时注入伪密钥，确认门禁可检测后立即清除。前端 `railway.json` 随 Service Root 放置，Caddy 继续明确拒绝 `/api`，不引入反向代理。

### 文档与状态

`docs/deployment.md` 说明 Railway 的 Root Directory、独立 Config File Path、构建期前端变量、演示部署模式及前后端部署顺序。项目索引、前端计划和进度快照只在拿到实际门禁数据后更新。F6-B 结束时才编制证据矩阵；其状态必须如实保留未验证项。

## 错误处理与安全不变量

- 生产默认关闭演示端点，只有 `DEMO_DEPLOYMENT_MODE=true` 才开放；商家范围仍由可信 Token 映射并由后端强制注入。
- 未配置 LLM 仅走可见降级，不产生预算预扣、调用计数、DeepSeek 请求或费用。
- 生产镜像拒绝 Mock，构建产物出现疑似密钥即失败。
- 前端静态服务不代理 API；缺少 API 基地址必须显式失败。
- 不修改只读参考项目，不执行 Git 发布操作，并保留现有 F5 未提交改动。

## 测试与验收

每项行为先新增失败测试，再作最小实现，并对两个关键修复进行变异验证。完成后运行前端 11 条门禁与后端静态检查、真实 PostgreSQL 回归；不执行聊天接口或任何会触发真实 LLM 的测试。通过数不得低于计划基线，文档卫生检查必须符合计划规定。

## 实施顺序

1. Task 1–2：F6-0 的配置、运维可见性、预算守卫及后端回归。
2. Task 3–6：首屏网络证据、异步挂载、Mock/密钥门禁、前端 Railway 配置与变异验证。
3. Task 7：全量门禁和文档同步。
4. Task 8–12：编写部署手册并交接给用户执行 Railway 控制台步骤；线上结果和证据矩阵按实际结果记录。
