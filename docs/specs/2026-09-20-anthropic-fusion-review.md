| Q18 Skill 加载 | 修改后同意 | 索引加按需加载方向正确。Skill 必须是可信、版本化、只读的白名单资源，限制长度和一次加载数量；加载器不能访问任意路径。还要测试正确触发、误触发、多个 Skill 冲突以及 Skill 更新后的回归。 |
| Q19 上下文压缩 | 修改后同意 | 可以实现两种策略做对比，但生产中应选择一个确定策略，不应同时随意执行。压缩后必须保留工具来源、数据截至时间和草稿版本；旧对话摘要是模型生成内容，不能升级为事实来源。身份应保存在服务端可信上下文中，而不是反复塞入模型提示词。 |
| Q20 记忆抽取 | 修改后同意 | 异步、失败不影响主回答正确。还需幂等任务、租户隔离、重试上限、单独预算和写入前后双重过滤。不要先假定更便宜模型足够，应通过敏感信息误写率和事实准确率评测后再选择。真实调用仍遵守 R3。 |

| Q22 MCP | 修改后同意 | 只读子集正确；不同意“复用商家网页会话或专用 Token 二选一”的含糊设计。远程 MCP 应使用 Streamable HTTP，并采用独立、短期、可撤销、限定商家与 scope 的凭证；正式兼容外部客户端时按 MCP OAuth 规范实现，不把浏览器会话 ID 交给第三方客户端。 |
| Q23 提示词与缓存 | 修改后同意 | 稳定前缀方向正确，但缓存是 best-effort，不能成为正确性依赖。工具与 Skill 索引要稳定排序和确定性序列化，并记录 prompt_cache_hit_tokens 验证实际收益。语言指令可动态放在后段，但安全规则仍必须位于高优先级静态部分。 |
| Q24 降级可见性 | **同意** | 保留 R7 字段是正确决定。实现时再区分整轮降级和单个来源/工具降级，避免一个非关键工具失败让整轮结果看起来完全不可用。 |

## 八、建议的总体融合原则

Claude 的蓝图融合方向大体正确，但总体策略应从“按蓝图替换现有系统”调整为：

1. 保留 Borough 已验证的领域逻辑、安全边界、测试资产和生产契约。
2. 将蓝图能力通过适配器和版本化接口接入，而不是让上游结构反向主导 Borough 领域模型。
3. 对 Agent 循环、前端技术栈和 SSE 契约等重大替换，先建立并行实现和对照评测，再决定迁移。
4. vendor 与历史参考项目都保持只读；自主实现放在 Borough 自有目录。
5. 评测、安全门禁和回滚能力从第一阶段开始建设，而不是在功能开发结束后补做。
