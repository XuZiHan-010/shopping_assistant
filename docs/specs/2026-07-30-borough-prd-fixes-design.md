## 1. 决策明细

### C1 · MVP 商家认证机制

**问题**：PRD 全文零次提到登录、auth、token。§10.2 Merchant Context 要求"从认证信息确定商家"，但认证信息的来源从未定义；MVP API 表没有任何认证接口；P1 只有"管理员认证"，P2 才有 SSO——**商家自己的认证不在任何阶段里**。而验收 #11「不同商家无法互相查询数据」是 MVP 必过项。

**决定**：演示 Token 白名单。

- Railway Variables 预置 3 个演示商家的静态 token
- 前端顶部提供商家切换器，切换即更换请求携带的 token
- 所有请求带 `Authorization: Bearer <token>`
- 后端从 token 解析出可信 `merchant_id`，**永不接受请求体或查询参数里的 merchant_id**
- 不建用户表、不做密码、不做登录页

**理由**：

1. 让验收 #11 真正可验证。没有第二个可切换的身份，"隔离"无法被证明，这条验收就是空转。
2. 保住验收 #2「1:1 还原 Prototype」。Prototype 是单页对话界面，没有登录页；引入登录会让视觉基准对不上。
3. token → merchant_id 这层间接正好是后续换 JWT 的接缝，只需改解析逻辑一处。

**代价（已接受）**：token 静态、不会过期，仅适用于演示环境。上生产前必须替换。

**落地时补充的两项判断**（改 PRD 过程中发现方案有缺口，按以下方式补齐）：

1. **切换器需要知道有哪些演示商家。** 若把 Token 放进前端构建变量，会与验收「密钥未进入构建产物」冲突。因此新增 `GET /api/demo/merchants` 返回演示商家列表与对应 Token，该端点**必须可配置关闭且生产环境禁用**。
2. **"密钥"的范围需要界定。** 演示 Token 只授予对演示数据的访问权，不属于验收条目所指的密钥；LLM 密钥和数据库连接串等真实密钥仍只保存在 Railway Variables。验收条目已据此改写为"LLM 密钥和数据库连接串未进入代码和构建产物"。§18 另增一行"演示 Token 被带入生产"的风险与缓解。

**连带的新待决项（已在 D4 定稿）**：商家切换器**在 Prototype 里不存在**——Prototype 顶栏只有 logo、标题、知识库和新会话按钮，因为它是单商家界面。所以这个控件是本决策新增的界面元素，不属于"1:1 还原 Prototype"的范围，验收 #2 不受影响。但它会挤占要被 1:1 还原的顶栏布局，位置与形态见 [D4](#d4--商家切换器按-560px-断点切换形态)。

**被否定的备选**：

- *最小 JWT 登录*（users 表 + 密码哈希 + `/api/auth/login` + 登录页）：最接近生产形态，但 MVP 要多出用户表、密码存储、token 刷新和一个 Prototype 里不存在的登录页，与"1:1 还原界面"冲突，且认证不是本项目要验证的核心价值。
- *单商家固定 + 只靠测试证明隔离*：工作量最小，但演示时无法现场展示跨商家取不到数据，安全性只能靠测试报告背书。

### C2 · 降级与 Reviewer 重试的阶段归属

**问题**：文档自相矛盾。§3.2 把"显式降级"放进内部可用版（P1），但验收 #13 和 MVP 必备响应字段都要求 MVP 就有降级。另外 §14.3「Reviewer 不得无限循环」是无条件要求，所以只要 P0 有 Reviewer，重试上限就不可能推到 P1。

**决定**：Reviewer（含固定重试上限）和显式降级**都进 P0**。P1 只保留"重试策略优化"。

**理由**：

1. PRD 自己的验收标准（#9 展示质量状态、#13 显示降级或错误）和 MVP 必备响应字段已经把两者写进 MVP，把它们标 P1 是文档错误而非范围选择。
2. 防编造数字是这个产品的核心差异化，砍掉 Reviewer 就砍掉了卖点，验收 #9 也会空转。
3. Railway 上 LLM 和数据库抖动很常见。没有降级路径，用户看到的是 500。

**代价（已接受）**：每轮问答多一次 LLM 调用。仅在人工演示时产生费用——自动化测试用 Fake LLM，不花钱。

**被否定的备选**：

- *只降级进 P0，Reviewer 推 P1*：省一次 LLM 调用，但质量状态恒为 `NOT_RUN`，验收 #9 失去意义。
- *只 Reviewer 进 P0，降级推 P1*：语义最干净，但 LLM 不可用时整个产品不可用，演示环境风险高。

### C3 · Chat Response 的字段契约

**问题**：§11.3 把 14 项都列成"最低字段"，但图表定义、至少两条建议、指标口径、数据行、导出信息这几项在 `RULE`/`CHAT`/`INVALID` 模式下按 §8 根本不存在。照此实现，Pydantic 会把它们设成必填，用户说句"你好"就校验失败。

**决定**：保持单一扁平响应类型，但 PRD 里把字段拆成"始终必填 / 按模式必填"两组并注明适用模式。完整分组见 [附录 A](#附录-a-chat-response-字段分组)。

**理由**：

1. 直接映射到 Pydantic 的 required vs Optional，实现时无需再推断。
2. 与 §8 模式表对齐，两处不会再打架。
3. 前端计划已经假设了扁平响应类型（`status`、`analysisSource` 都在同一层），不需要回头改前端契约。

**被否定的备选**：

- *全部字段可选*：最简单，但契约变松，后端漏字段测试不报错；"有数据的分析回答 100% 包含至少两条建议"这条产品指标就无法用类型系统保障。
- *按模式拆独立子类型（discriminated union）*：类型最精确，但 7 个 schema 的维护成本高，改一个公共字段要改 7 处，前端处处要 narrow，且要回头改前端计划里已有的扁平类型。

### C4 · Milestone 顺序与阶段映射

**问题**：M0–M5 从未说明哪些构成 MVP。反推出来是矛盾的：M4「内部可用功能」是 P1 内容，M5「Railway 上线」是 P0 内容，**P1 排在 P0 前面**。另外 M2 承诺交付"建议"，但产出建议的 Answer Composition 在 M3。

**决定**：重排为 M0 → M1 → M2 → M3 → **M4 Railway 上线（MVP 完成）** → M5 内部可用功能（P1）。"建议"从 M2 移到 M3。完整映射见 [附录 C](#附录-c-milestone-与阶段映射)。

**理由**：

1. MVP 边界变成"M0–M4 全部完成"，一句话可判定。
2. 部署是本项目明确的立项痛点（Problem Statement 里"原系统部署组件偏多"和"Railway 文件系统不可靠"两条），越早上线越早暴露问题。
3. 修掉 M2/M3 的依赖倒置：没有 Answer Composition 就产不出建议。

**被否定的备选**：

- *保留编号，上线拆两次*：文档改动最小，但"上线"在时间线上出现两次，沟通时容易指不清；milestone 变成 7 个。
- *Railway 部署整体移出 MVP*：交付最快，但与立项动机相背，部署风险推到后期才暴露。

### I1 · `INVALID` 与 `ATTACHMENT` 的阶段归属

**问题**：§8 定义 7 个模式，P0 只列 5 个。`ATTACHMENT` 能推断是 P1；`INVALID` 从未出现在任何阶段清单里，可它承载越权和危险请求的拦截，而验收 #11、#12 是 MVP 必过。没有它，越权请求会掉进 `CHAT` 或直接 500。

附带问题：`INVALID` 把越权、危险、无法处理三类混在一个模式里。

**决定**：

- `INVALID` 进 P0，并拆成两条路径：
  - **越权请求** → HTTP 403 + 审计日志，**不进 mode 枚举**
  - **危险请求和无法处理的问题** → 正常 200 响应 + `mode=INVALID`
- `ATTACHMENT` 明确标 P1

**理由**：

1. 越权是安全事件，应该有独立的 HTTP 语义和可告警的日志路径。混在 200 响应里，后续做审计和告警时拆不出来。
2. "这个问题我暂时答不了"不是错误，是正常业务回答，应该进会话历史、能参与反馈和质量统计，所以必须是 200。
3. 前端因此能区分"你没权限"和"换个问法"两种提示。
4. `ATTACHMENT` 在 P0 没有输入来源（附件功能在 P1），标 P0 只会得到一个空实现。

**被否定的备选**：

- *进 P0 但保持三合一*：改动最小，但前端拿到 `INVALID` 无法判断该显示哪种提示，越权事件也拆不出来。
- *取消 `INVALID` 模式，全走 HTTP 错误码*：模式表最干净，但"答不了"用 4xx 语义不对，也存不进会话历史，且这类回答无法参与反馈统计。

### I2 / I3 · MVP API 表里的阶段错位

**问题**：`GET /api/reports/daily` 在 MVP 表，但日报功能在 §3.2 和 §7.2 都是 P1，验收里也没有。`DELETE /api/conversations/{id}` 在 MVP 表，但 §7.3 把"用户删除"放在 P2。

**决定**：

- `GET /api/reports/daily` 从 MVP 表移到 P1 表
- `DELETE /api/conversations/{id}` 留在 MVP，验收标准补一条
- §7.3 那条改写为"商家记忆清理、审计留存与数据保留策略"

**理由**：

1. 日报是一整套功能（定时任务、聚合、摘要生成），整体属于 P1；只留一个接口在 MVP 表会误导实现。
2. 删除会话很便宜（一个软删除），story 4「开始新会话」的体验需要它。演示一段时间后侧边栏会堆满无用会话。
3. P2 那条说的是重量级合规删除（记忆清理、审计留存），和删单个会话不是一回事，措辞需要澄清。

**被否定的备选**：

- *两者都移出 MVP*：MVP 表面最小，但会话只能累积不能清理。
- *两者都留在 MVP*：首屏日报卡片是 Prototype 里已有的视觉元素，做了才算真"1:1 还原"；但 MVP 要多出聚合和摘要生成，M4 上线时间往后推。

### I4 · 业务时区

**问题**：§12.2 写"时间字段统一保存为带时区**或**明确约定 UTC"——一个"或"把选择权丢给了实现；同节说"API 按业务时区返回日期"，但全文再没有第三处提到时区，**业务时区是哪个从未定义**。而"昨天的 GMV"、"最近 7 天趋势"、日报统计区间全都依赖这个边界。

**决定**：

- 数据库统一 `timestamptz` 存 UTC
- 业务时区钉死 `Asia/Shanghai`
- 所有"昨天 / 最近 N 天 / 日报区间"按 `Asia/Shanghai` 计算日界后转 UTC 查询
- 时钟可注入，用于测试跨零点边界
- 删掉 §12.2 里的"或"，只留一种写法

**理由**：

1. 不定时区，前后端会各自假设，跨零点的订单归属必然错，而这类 bug 在演示数据上很难被发现。
2. §15.1 已经要求时间可注入或冻结，测试跨零点边界不需要把时区做成配置项。
3. MVP 只服务一个虚构平台，配置化属于 YAGNI。

**被否定的备选**：

- *时区做成 `BUSINESS_TIMEZONE` 环境变量*：后续做其他区域演示不用改代码，但多一个配置项和一条"配错了会怎样"的失败路径，当前没有需求支撑。
- *直接存 `Asia/Shanghai` 本地时间*：心智负担最低，但与"带时区"的原意相背，日后接外部数据源或对接 Doris 时无法判断已存数据的真实时刻，迁移代价高。

### I5 · 用户故事的阶段标记

**问题**：66 条用户故事全部没有阶段标记，混着 P1 内容（story 20 优惠券明细、39–44 附件、53 知识库管理员、56–60 日报和记忆）。以 story 驱动开发的 coding agent 会直接做超范围。

**决定**：保留现有 12 个主题分组，在每条故事句首加 `[P0]` / `[P1]` / `[P2]` 标记。

**落地时的两处调整**：

1. **新增 story 53**「作为演示环境验收人员，我希望可以在预置商家之间切换，以便现场验证数据隔离确实生效」[P0]。C1 引入了一个面向用户的能力，原来 66 条里没有任何故事覆盖它。插入后 6.10 之后的编号顺延，总数变为 **67 条**。
2. **三条跨阶段故事收敛到 P0 范围**：story 20 去掉优惠券明细、story 26 去掉优惠券和赔付规则、原 story 55（现 56）收敛为"所有导出下载都经过权限校验"。超出部分由 §7.2「优惠券、赔付、供应链等更多业务域」和 story 42（附件访问权限）承接，避免一条故事挂两个阶段标记。原 story 60「删除会话和记忆」同理拆分为 story 61「删除会话」[P0]，记忆删除随 P1 商家记忆提供。

**理由**：

1. 12 个主题分组恰好对应 Deep Modules（指标、口径、明细、知识、附件……），开发时按模块查故事很有用，不能打散。
2. coding agent 读到任何一条都能立即判断该不该做，不必回查 §7。

**代价（已接受）**：66 处改动；以后调范围要同时维护 §6 标记和 §7 清单两处。

**被否定的备选**：

- *按阶段重组 §6*：阶段边界最直观，但打散主题分组，按模块查故事变麻烦。
- *只在 §6 开头加一句声明*：改动最小，但防护只靠一句话，agent 仍可能被具体故事带跑。

### I6 · 指标标识

**问题**：`GET /api/metrics/{name}` 用指标名作 path 参数。参考项目里指标名是自由文本字段（`metrics_name string COMMENT '指标名'`），实际值是中文。中文和空格需要编码，含 `/` 的指标名会直接破坏路由。

更深一层：§10.2 的 Intent Contract 靠严格枚举和白名单约束模型输出。白名单键如果是中文自由文本，模型产出的变体（空格、简繁、同义词）会被判成不同指标，命中率会莫名下降。

**决定**：

- 指标资产增加一列稳定的英文 slug `metric_code`（如 `paid_gmv`、`refund_rate`）
- 接口改为 `GET /api/metrics/{code}`
- Intent Contract 的白名单枚举使用 `metric_code`
- 中文名作为 `display_name` 只用于展示

**理由**：

1. 一并解决 URL 编码和白名单健壮性两个问题。
2. 英文 code 做枚举对 LLM 结构化输出稳定得多。
3. URL 干净、可缓存、日志可读。

**代价（已接受）**：演示指标（约 10–20 个）要逐个定 code 并维护 code ↔ 中文名映射。

**被否定的备选**：

- *改成 query 参数 `?name=`*：改动最小，但没解决白名单用中文自由文本做键的问题。
- *不改，前端负责编码*：零改动，但含斜杠的指标名仍会破坏路由，编码后的中文路径在日志和网关里基本不可读。

### I7 · 产品指标的可测量性

**问题**：§4.1「测试问题中至少 90% 能路由到正确回答模式」没有定义测试集规模、构成、维护人和执行时机。这条现在无法被证伪，等于没有约束力，而它是 MVP 是否达标的判据之一。

**决定**：建立版本化的固定回归问题集。

- 40–60 条问题，纳入仓库并版本管理
- 每条标注期望回答模式和期望业务域
- 用 Fake LLM 执行，不产生费用
- 路由准确率作为 CI 断言

**理由**：

1. 指标从"愿望"变成自动化断言，回归能被拦住。
2. 与 §4.2「所有自动化测试不产生真实 LLM 费用」一致。
3. 日后改 prompt 或换模型时有基准可对比。

**代价（已接受）**：需人工标注几十条期望值；模式或业务域调整时要同步维护。

**被否定的备选**：

- *改成定性验收条目*：文档诚实，但失去对意图识别整体质量的计量，换模型时没有基准。
- *标为上线后观测指标，不入验收*：不增加 MVP 工作量，但上线前完全不知道路由准不准。

### A1 · 推荐问题由预置配置提供（追加决策）

**来源**：评审后追加。审阅附录 A 时先确认了"`CHAT` 模式也要给推荐问题"，随后进一步确认推荐问题可以全部预置。

**决定**：`suggested_questions[]` 全部来自服务端预置配置，**Answer Composition 不生成推荐问题**。

- 服务端维护一份按业务域分组的推荐问题配置，每个业务域下有多组候选
- 响应返回当前业务域对应的一组，同时把该业务域的其余候选组一并带回
- 前端"换一换"在已返回的候选组之间本地轮换，不发额外请求
- `CHAT` 模式返回入门问题组（能力发现型），让新用户知道助手能做什么——这是 story 6 的主要落地场景

**理由**：

1. Prototype 本来就是这么做的：`followupPools` 是三组硬编码问题，配合"换一换"轮换，每个场景另有自己的预置 `suggestions`，完全没有生成逻辑。照此实现才是真"1:1 还原"。
2. 缩小 LLM 的结构化输出。少一个数组就少一处解析失败和格式漂移的来源，Answer Composition 只需专注结论、证据和建议。
3. 推荐问题必须是系统真正答得上来的问题。LLM 生成的推荐很可能落在白名单之外，用户一点就撞 `INVALID`——预置池天然不会越界。
4. 配置放服务端，运营改推荐问题不需要发前端版本。
5. "换一换"零延迟。

**代价（已接受）**：推荐问题不随本轮数据结果变化，只按业务域分组。story 34「点击建议问题继续分析」仍然成立（预置问题按业务域相关），但相关度不如实时生成。

**注意区分**：本决策只涉及"猜你想问"（`suggested_questions[]`）。**经营建议（`recommendations[]`，至少两条）仍由 LLM 基于查询结果生成**，并受 Reviewer 校验——那是产品的核心价值，不可预置。

**影响的 Deep Module**：§10.2 Answer Composition 的职责描述要去掉"追问"的生成责任，改为由配置提供。

## 2.5 后端计划评审追加的三项决策

PRD 定稿后评审 `docs/backend-development-plan.md`，发现 3 个 Critical、11 个 Important 和 18 处与新 PRD 不一致。其中三项需要产品决策，记录如下。

### D1 · 聊天进度用 SSE 流式推送

**问题**：`thinking_steps` 是响应体字段，要等整个请求结束才能拿到，而真实链路（分类 → 理解 → 校验 → 查询 → 组织 → 本地校验 → Reviewer 最多 2 轮）超过 10 秒。PRD §14.2「1 秒内进入可见处理状态」和 §13「加载阶段显示当前动作」都无法满足，而原计划全程同步、没有任何流式或异步机制。

**决定**：`POST /api/chat` 以 SSE 推送 `step` / `done` / `error` 三类事件。`done` 载荷与非流式响应完全一致；`Accept: application/json` 走非流式路径供 API 测试使用。

**理由**：多步 Agent 是这个产品的核心差异化，把真实阶段展示出来既满足非功能要求，也让价值可见。共用同一载荷让前端只写一处解析逻辑，同一端点提供非流式路径避免为流式解析搭一套测试基础设施。

**代价（已接受）**：流中断的错误语义要单独设计；流式接口的测试比普通请求麻烦。

**被否定的备选**：*前端本地假进度*——后端零改动、Prototype 本来如此，但显示的阶段与真实阶段不同步，后端卡住时进度条仍在前进，且要改写 PRD 两处措辞。*异步 + 轮询*——代理友好且为 P1 Worker 铺路，但 MVP 没有 Redis/Worker，得用 asyncio 后台任务，Railway 多实例或重启会丢掉执行中的请求。

### D2 · MVP 没有 user 概念

**问题**：C1 定了"不建用户表"，但后端计划有 `users`、`user_merchant_roles` 两张表，`MerchantContext` 有 `user_id`，B1 还要"Seed 演示用户"。

**决定**：删掉两张表，`MerchantContext` 只保留 `merchant_id` 和 `is_admin`，Token 直接映射到商家，会话与反馈归属商家。P1 管理员用 `ADMIN_TOKEN` 判定，真实用户体系留到 P2 的 SSO。

**理由**：演示环境 3 个商家，多人协作不是 MVP 场景。不建用不上的表；P1 需要加 `user_id` 时，Alembic 加一列只是几行。

**被否定的备选**：*保留 user 表*（会话天然归属到人，但 MVP 多两张空表）；*预留可空 user_id 列*（避免日后加列，但留下一个永远为 null 的列让读代码的人困惑）。

### D3 · LLM 费用做三层限制

**问题**：把几条决策串起来看是一条完整的暴露链——验收 #1 要求**公开的 Railway 地址**，`/api/demo/merchants` 是**免鉴权**端点，环境变量里配着**真实 LLM key**，而 `RATE_LIMITED` 错误码存在但没有任何任务实现限流（PRD 把限流放在 P2）。任何人扫到地址就能取 Token 并无限调用聊天接口。

**决定**：三层防护，在 B9 部署加固阶段落地。单请求限制最大 LLM 调用次数与 token；用量写入 `llm_usage` 按日聚合，超每日预算后全局转显式降级（复用 C2 已有的降级路径）；按 Token 与来源 IP 做基础限流，命中返回 `RATE_LIMITED`。新增错误码 `LLM_BUDGET_EXCEEDED`。

**理由**：公开 URL 被爬虫和脚本扫到是常态，不是理论风险。原计划只有"用量记录"——记录不等于限制。降级路径已经要做，复用成本很低。

**代价（已接受）**：多一张用量表和一层中间件；MVP 无 Redis，限流用进程内计数器，多实例下是近似限制，需在文档中说明。

**被否定的备选**：*只做每日预算熔断*（能硬性封顶，但没有频次限制，被刷时很快撞到日上限，之后整天演示环境都是降级状态，反而展示不了）；*保持现状*（零工作量，但发现被刷之前费用已经产生，且靠人工看账单）。

### D4 · 商家切换器按 560px 断点切换形态

**问题**：C1 引入的商家切换器在 Prototype 里不存在，而顶栏是要 1:1 还原的区域，位置与形态必须先定。评估时做了五个方案的可交互 mockup，用 Prototype 原始样式渲染。

**判断标准**：这个控件**唯一的用途**是让人当场确认"我现在是这个商家，取不到其他商家的数据"。因此**当前商家名必须在任何视口下都常驻可见**——这一条直接决定了取舍。

**决定**：按 Prototype 现有的 560px 断点切换形态。

| 视口 | 位置 | 形态 |
| --- | --- | --- |
| > 560px | 顶栏右侧操作区最左 | 独立按钮，高 36px、圆角 10px，与知识库/新会话同族；品牌区与产品说明不动 |
| ≤ 560px | 品牌标题下方副行 | 行内按钮，12px 字号 |

**理由**：

1. 唯一在桌面和移动都保住商家名可见的方案。
2. **窄屏那块位置本来就是空的。** Prototype 自己的 `@media (max-width: 560px)` 里写着 `.brand-title p { display: none }`——产品说明在该断点已被隐藏。副行形态搬进去不占用新空间、不改动任何还原规则，纯副行方案"牺牲产品说明"的代价在这里自动消失。
3. 不引入新断点。560px 是现成的，同一档里 `.new-chat-button` 也收成图标，形态切换与既有响应式行为同步。

**代价（已接受）**：一个控件两种 DOM 位置，需要条件渲染，组件测试要覆盖两种形态并验证跨断点状态不丢；拖动窗口跨过 560px 时控件会跳位置。已知最紧的一点是 **560px 刚上方**——此时新会话仍是带文字的全宽按钮、切换器也还在操作区，需实测不换行不溢出，已加入 Playwright 的 570×900 视口。

**被否定的备选**：

- *纯右侧按钮*：实现最简单、品牌区不动，但窄屏要把商家名折叠成图标，违反常驻可见。
- *纯品牌副行*：空间效率最好，但宽屏要拿掉产品说明，动的是要 1:1 比对的区域。
- *左侧商家胶囊*：身份最显眼，但 1280px 以下就截断品牌名，代价最大。
- *右上角头像菜单*：形态最规范、占位最小，但收起时只显示首字母，看不到商家名——与控件自身用途直接矛盾，最先排除。
