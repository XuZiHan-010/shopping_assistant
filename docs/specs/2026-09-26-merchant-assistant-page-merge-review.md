# v1 分析助手与 v2 运营助手两页合并评审

> 本文件是评审结论，**不执行合并**。裁定合并时另立实施计划，并先按 `AGENTS.md`
> §五的顺序改 PRD → 契约 → 前后端计划 → 索引文件（PRD §15 N2：「两页是否合并在
> N3 商家 Skill 迁完后另行评审」，本次即该评审）。

## 一、评审背景

商家端目前并存两条独立入口：

| 页面 | 路由 | 技术路径 | 引入阶段 |
| --- | --- | --- | --- |
| v1 分析助手 | `/`（`AssistantView.vue`） | v1 `POST /api/chat` + Chat BI REST（`analyticsStore`） | 历史基线，已冻结不再承接新能力 |
| v2 运营助手 | `/ops-assistant`（`OpsAssistantView.vue`） | v2 `POST /api/v2/merchant/chat` + 工具循环 | N2 起新建，N3 阶段 C 本次会话持续扩展 |

N2 裁定新增独立 v2 页面并存、v1 不改，是因为当时 v2 商家工具只有库存告警与补货
草稿两项，直接替换会让指标/明细/规则/图表/导出在 N3 前整体退化。**现在 N3 阶段 C
的 6 个商家 Skill（业绩洞察、库存运营、商品内容、定价促销、明细导出、规则口径）
已经全部落地**，是重新评估这条并存约束是否还有必要的时机。

## 二、逐项能力对照

| v1 分析助手能力 | v1 实现 | v2 是否已有等价证据 | 说明 |
| --- | --- | --- | --- |
| **指标查询与趋势** | `NorthStarCards.vue` + `TrendChart.vue`（ECharts），读 Chat BI REST（`GET /admin/analytics/chatbi/overview`） | **部分**：`query_metrics`/`attribute_change` 工具已支持指标查询与归因（Task 1），但**只能通过对话文字应答**，没有独立图表组件把数据点渲染成 ECharts | v2 侧的"图表"目前是聊天回答里的文字/表格描述，不是可视化折线图。这是本次评审发现的**唯一功能性缺口**，见下方「差距」 |
| **分类下钻** | `CategoryTable.vue`，读 `GET /admin/analytics/chatbi/categories` | 无独立组件，理论上可以通过对话问"哪个类目卖得最好"经 `query_metrics` 的维度参数取得，未验证有对应工具参数支持类目维度 | 需要下一步核实 `query_metrics` 的 `QueryIntent` 是否支持按类目分组 |
| **明细与导出** | 无（v1 从未做过明细导出，`GET /api/exports/{export_id}` 是 v1 兼容层但从未被 `AssistantView` 触发） | **已有且更完整**：`create_export` 工具（Task 5），明细行不进对话上下文，只给下载链接，比 v1 更严格地遵守"明细不进对话"的设计原则 | v2 在这项上**已经超过** v1（v1 本来就没做） |
| **规则问答** | 走 v1 冻结基线的 `RULE` 回答模式 | **已有**：`get_metric_definition`/`search_rules` 工具（Task 6），零 LLM 调用即可读受控知识资产 | 对等，且 v2 路径更明确写清了"不自拟公式"边界 |
| **猜你想问** | `quickQuestions()` 常量表，按语言给出预置问题按钮 | **缺失**：v2 运营助手没有等价的预置问题入口 | 功能性缺口，但严格来说是"辅助易用性"而非核心能力——今日简报页的 `next_action_prompt` 部分承担了类似作用（针对特定告警场景给出建议问题） |
| **反馈（采纳/赞踩）** | 走 v1 冻结基线，商家端历史反馈接口 | **已有且更完整**：`POST /answers/{id}/feedback`（N2 落地），带采纳、赞踩、可选原因，历史会话按商家/对话范围恢复 | v2 在这项上已经超过 v1 |
| **今日简报** | 无（v1 从未做过简报能力） | **已有且更完整**：完整每日简报（本次 Task 2），四源（库存告警/待批草稿/顾客信号，`METRIC_CHANGE` 待补）汇总、排序、版本化存储、限流重新生成 | v2 独有能力 |
| **草稿审批** | 无 | **已有且更完整**：按 `batch_id` 分组勾选批准（本次 Task 8）、审批证据一次性签发 | v2 独有能力 |
| **知识库后台** | 不进普通商家工作台（M1 明确排除），独立 `/knowledge-base` 页面，两端共享 | 同上，不受本次评审影响 | 两页都不含知识库，非评审范围 |

## 三、结论：唯一实质性差距是「ECharts 可视化图表」

对照结果显示：**v2 在导出、反馈、简报、审批四项上已经超过或等于 v1，规则问答对等，
分类下钻需要一次核实但很可能只是参数传递问题不是能力缺失**。唯一明确的、需要新写
代码才能补上的差距是——**v2 运营助手没有把 `query_metrics`/`attribute_change` 的
数值结果渲染成 ECharts 折线图/柱图，只能以文字/表格形式在对话里出现**。

"猜你想问"是次要的易用性差距，`next_action_prompt`（简报条目自带的建议问题）已经
覆盖了其中最高频的场景（针对具体告警/信号给出下一步问题），不构成阻塞合并的理由。

## 四、给用户的建议（三个选项，需要用户裁定）

### 选项 A：现在合并，直接替换 v1 入口为 v2

**做法**：`/` 路由指向 `OpsAssistantView`（或将其挂载到根路径），下线
`OpsDashboardView`/`AssistantView`/v1 Chat BI 组件。

**前提缺口**：需要先给 v2 补一个 ECharts 图表组件（读 `query_metrics`/
`attribute_change` 工具结果渲染），否则商家会立即感知到"看不到趋势图了"的体验
倒退。**这不是小工作量**——需要设计"工具结果如何转换成图表数据"这层适配（保持
R4 底线：图表数据点仍必须来自后端确定性计算，前端不得对工具返回的数字做二次
统计运算）。

**代价**：如果合并后发现 v2 工具循环在展示图表这件事上比不过 v1 直接查
REST API 的响应速度或稳定性，用户体验会短期倒退，需要准备回退方案。

### 选项 B：现在合并，但先接受"暂无独立图表"的过渡状态

**做法**：同选项 A 替换入口，但明确告知商家"趋势图暂时以文字形式呈现，图表
可视化随后补上"。

**代价**：过渡期内商家确实会失去可视化趋势图这个具体能力，但换来的是不再维护
两套并行入口、两套 Chat 协议的长期成本。是否可接受取决于产品对这条能力缺失的
容忍度。

### 选项 C：暂不合并，先补齐图表能力，下次评审再决定

**做法**：维持现状（两页并存），先在 v2 侧补一个 ECharts 组件把
`query_metrics`/`attribute_change` 结果可视化，做完后再重新评审是否合并。

**代价**：继续维护两套入口的成本；但避免了在缺口未补齐前就做出"合并"的不可逆
决定（决定本身可逆，但商家的使用习惯迁移成本是真实的）。

## 五、本次评审明确不做的事

- 不执行任何合并操作、不下线任何现有页面或路由；
- 不新建 ECharts 图表组件（那是选项 A/B 被采纳后的后续实施工作，需要先改 PRD
  §15 N2 的既有裁定并同步契约，不在本次评审范围内直接写代码）；
- 不裁定"分类下钻"参数是否已支持——只标记为需要核实的开放问题，留给采纳选项后
  的实施阶段处理。

## 六、推荐

若必须给出一个默认建议：**选项 C**——图表可视化是唯一明确的实质性差距，且
`AGENTS.md` R4 对"图表数据点必须来自后端确定性代码"这条约束意味着新图表组件
不是简单的前端渲染工作，需要认真设计数据契约。在这个缺口补齐之前先合并，
是拿"少维护一套入口"换"商家立即感知到趋势图消失"，这笔账在没有更多产品侧
输入（例如实际有多少商家真的在用 v1 的趋势图）之前不该由实施方单方面拍板。
