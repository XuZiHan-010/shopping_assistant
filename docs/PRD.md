# Borough 商家 AI 助手重构版 PRD

> 文档状态：Draft v1  
> 产品名称：Borough 商家 AI 助手（Borough 为本项目虚构的电商平台 IP）  
> 目标版本：MVP → 内部可用版 → 生产版  
> 技术方向：Python + TypeScript  
> 部署平台：Railway  
> 视觉基准：`yshopping-prototype`  
> 业务基准：原 Java + Vue yshopping 项目

---

## 1. Problem Statement

现有 yshopping 项目已经验证了商家 Data Agent 的产品形态，但当前实现包含 Java 后端、JavaScript 前端、Doris、MySQL、自研 Agent 编排和本地知识文件等多套组件，重新理解、开发和部署的门槛较高。

我们需要从 0 到 1 重构一套更容易开发、测试和上线的版本，使商家能够通过自然语言完成经营数据查询、业务规则查询、明细查看、附件分析和行动建议获取，同时让 coding agent 可以依据明确的模块、协议和验收标准持续开发。

新版本需要解决以下问题：

- 用户不知道经营数据分布在哪些表、指标如何计算；
- 普通商家不能直接编写 SQL，也不应该接触数据库细节；
- 指标回答往往只有数字，缺少口径、趋势解释和行动建议；
- 订单、退款、商品、工单等数据分散，跨业务分析成本高；
- 业务规则和指标口径容易分散在文档或个人经验中；
- LLM 回答存在误解问题、编造字段、计算错误和越权查询风险；
- 原系统的数据库与部署组件偏多，不适合快速复刻和早期迭代；
- Railway 上的容器文件系统不能作为可靠的长期附件或知识存储。

---

## 2. Solution

建设一个基于 Vue 3 + TypeScript 和 Python FastAPI 的 Borough 商家 AI 助手。

用户通过对话输入问题或上传文件，系统识别商家身份和业务意图，检索指标口径与业务知识，将问题转为受控的结构化查询计划，再由后端安全模板查询 PostgreSQL 中的经营数据。系统根据数据生成结论、图表和至少两条行动建议，并通过独立 Reviewer 检查回答是否与数据一致。

第一阶段只使用 PostgreSQL 作为主数据库，不引入 Doris 和 MySQL。Redis、异步 Worker、对象存储和 Doris 按真实业务需求逐步增加。

产品保留原项目的三栏交互：

- 左侧：指标口径和指标图表；
- 中间：对话、日报、明细和附件；
- 右侧：经营建议和“猜你想问”；
- 移动端：调整为对话优先的单列布局。

## 3. Product Goals

### 3.1 MVP 目标

- 1:1 还原 Prototype 的核心界面；
- 支持指标、明细、规则、身份、普通对话和无效请求六类问题；
- 支持至少交易、退货、商品和客服工单四个业务域；
- 使用演示 Token 白名单确定可信商家身份，并可切换商家验证数据隔离；
- 使用 PostgreSQL 完成演示经营数据查询；
- 展示指标口径、图表、建议和质量状态；
- 提供独立 Reviewer 校验（最多 2 次尝试）和显式降级；
- 支持会话记录、会话删除、反馈和 CSV 导出；
- **具备进程内基础限流、单请求 LLM 调用与 token 上限、每日 token 预算熔断**；
- 记录越权访问等安全审计事件；
- 完成 Docker 化并部署到 Railway；
- 自动化测试不调用真实 LLM。

### 3.2 内部可用版目标

- 接入真实或准真实经营数据；
- 支持图片、PDF、Excel 和 CSV；
- 提供知识库维护后台；
- 增加管理员权限（`ADMIN_TOKEN`，不引入用户体系）；
- 增加商家记忆及记忆删除；
- 优化 Reviewer 重试策略；
- 使用对象存储保存附件；
- 支持每日经营报告；
- 增加 Redis、Worker 和任务重试。

### 3.3 生产版目标

- 引入真实用户体系或企业认证，替换演示 Token；
- 将限流升级为 Redis 分布式限流和多实例精确配额；
- 增加监控、告警、完整审计系统和数据保留策略；
- 根据真实数据量评估是否接入 Doris；
- 支持无中断或低风险数据库迁移和 Railway 发布。

各阶段的能力清单以 §7 Functional Scope 为准。本节是目标概述，出现分歧时以 §7 为准。

## 4. Success Metrics

### 4.1 产品指标

以下指标通过**固定回归问题集**测量。该问题集包含 40–60 条问题，纳入仓库并版本管理，每条标注期望回答模式和期望业务域。

**路由准确率拆成两项，不要混为一谈。** Fake LLM 为每条问题返回预置意图，因此它只能证明夹具配置正确、Agent 路由没有回归、Pydantic 契约可解析，**证明不了真实模型能理解自然语言**：

| 指标 | 执行方式 | 目标 | 性质 |
| --- | --- | --- | --- |
| 确定性路由回归通过率 | Fake LLM，进入 CI | **100%** | CI 断言，任何一条不通过即阻断合并 |
| 真实模型意图准确率 | 真实模型跑同一问题集，离线执行 | **≥ 90%** | **人工验收项，不是 CI 断言** |

真实模型评估执行前必须遵守 `AGENTS.md` R3：说明模型、调用次数和预计费用并获得同意。它在 M4 上线前执行一次，结果记入验收记录；MVP 的 CI 不包含这一项。

其余产品指标：

- 指标和明细问题的商家隔离通过率为 100%；
- 有数据的分析回答 100% 包含至少两条经营建议；
- 有指标的回答 100% 返回指标口径或明确的“口径待核验”状态；
- 规则回答能够返回知识来源或明确的降级说明；
- 用户可以在一次会话中完成提问、追问、反馈和导出。

### 4.2 工程指标

- 所有自动化测试不产生真实 LLM 费用；
- 后端关键模块具备单元测试；
- 前端核心流程具备组件测试和 Playwright 测试；
- Railway 健康检查不依赖 LLM；
- 浏览器控制台无未处理异常；
- 360px 宽度下无页面级横向滚动；
- 所有数据库查询都经过参数绑定和商家范围限制。

## 5. Personas

### 5.1 商家经营人员

关注 GMV、订单、商品、退款、客服和履约，希望快速获得数字、原因和行动建议。

### 5.2 商家负责人

关注整体趋势和异常，希望通过日报和追问快速判断业务风险。

### 5.3 平台运营人员

维护业务规则、指标口径和知识文档，关注回答是否准确、统一和可追溯。

### 5.4 系统管理员

维护商家、权限、数据连接、密钥、部署和运行状态。

### 5.5 开发人员或 Coding Agent

根据稳定的 API、模块边界、测试和目录索引持续实现功能。

## 6. User Stories

每条故事标注交付阶段：**[P0]** 属于 MVP，**[P1]** 属于内部可用版，**[P2]** 属于生产增强。阶段权威定义见 §7 Functional Scope；两处不一致时以 §7 为准。

### 6.1 会话与基础体验

1. [P0] 作为商家经营人员，我希望通过自然语言提问，以便不需要了解数据库和 SQL。
2. [P0] 作为商家经营人员，我希望看到助手正在识别、查询和整理的状态，以便知道系统没有卡住。
3. [P0] 作为商家经营人员，我希望在同一会话中连续追问，以便不用重复说明日期、指标和筛选条件。
4. [P0] 作为商家经营人员，我希望可以开始新会话，以便切换到新的分析主题。
5. [P0] 作为商家经营人员，我希望通过对话目录跳转到历史轮次，以便快速回顾之前的结论。
6. [P0] 作为商家经营人员，我希望看到建议问题，以便了解助手可以做什么。
7. [P0] 作为移动端用户，我希望对话区优先展示且不横向溢出，以便在手机上完成查询。

### 6.2 指标查询

8. [P0] 作为商家经营人员，我希望查询昨天的 GMV，以便了解最新成交表现。
9. [P0] 作为商家经营人员，我希望查询最近 7 天的订单、退款或退货趋势，以便发现变化。
10. [P0] 作为商家经营人员，我希望按商品、类目或状态拆分指标，以便定位主要贡献因素。
11. [P0] 作为商家经营人员，我希望系统理解“昨天”“最近一周”等日期表达，以便自然提问。
12. [P0] 作为商家经营人员，我希望看到周期合计、最新值和变化描述，以便快速理解图表。
13. [P0] 作为商家经营人员，我希望知道指标单位，以免混淆金额、人数和订单数。
14. [P0] 作为平台运营人员，我希望系统限制最大查询日期范围，以避免无意的大范围扫描。

### 6.3 指标口径

15. [P0] 作为商家经营人员，我希望看到指标的业务口径，以便理解数字代表什么。
16. [P0] 作为数据人员，我希望看到受控的 SQL 口径说明，以便核对计算方式。
17. [P0] 作为平台运营人员，我希望看到指标来源和负责人，以便发现问题时找到维护方。
18. [P0] 作为商家经营人员，我希望未命中指标资产时看到“待核验”提示，以免把生成口径当成正式标准。
19. [P0] 作为数据人员，我希望看到指标的来源库表，以便回到数仓核对原始数据。
20. [P1] 作为数据人员，我希望看到指标涉及的维度集合，以便判断这个指标能按什么口径拆分。
21. [P1] 作为商家经营人员，我希望在有关联报表时能一键跳转，以便查看更完整的看板。

**业务口径与 SQL 口径是两个并列字段，不是一个。** 参考项目的指标平台元数据表把它们分列为
`metrics_biz_meaning` 与 `metrics_sql_meaning`，面向的读者不同：业务口径回答“这个数是什么意思”，
SQL 口径回答“这个数怎么算出来的”。契约层不得把两者合并成单个 `definition` 字段——合并后
数据人员的核对需求（故事 16）就没有承载字段，只能落空。

业务口径在 `METRIC` 模式下必填；SQL 口径、维度、来源库表与关联报表允许缺失，缺失时
前端隐藏对应分区而不是渲染空白占位。

### 6.4 明细查询与导出

22. [P0] 作为商家经营人员，我希望查询最近订单明细，以便查看具体订单。
23. [P0] 作为商家经营人员，我希望查询退款、商品和工单明细，以便处理具体业务。（优惠券等更多业务域见 §7.2）
24. [P0] 作为商家经营人员，我希望表格展示友好的中文列名，以便无需理解数据库字段。
25. [P0] 作为商家经营人员，我希望看到总行数和当前展示数量，以便知道结果是否被截断。
26. [P0] 作为商家经营人员，我希望下载完整 CSV，以便进一步处理。
27. [P0] 作为系统管理员，我希望导出链接有有效期和权限校验，以避免数据泄露。

纯明细与明细分析必须区分：用户只要求查看明细时，回答正文必须为空，仅展示表格及其元数据；只有明确要求分析、建议、原因、诊断、优化、解读或复盘时，才生成分析正文和建议。对任一轮次都不得用“可选空正文”替代这个约束。

商家可按一笔子订单查询关联退款或商品；该能力只允许三种预定义关系，且始终按已验证的商家范围执行。后端先在该商家范围内解析订单，再以固定关系查询关联数据；不得区分订单不存在与属于其他商家。若模型给出的关系计划缺少安全路由参数，或订单无法在当前商家范围内解析，系统拒绝关联计划、回退基础查询，并向用户显示说明，不能把它伪装成无结果。

商家也可请求按商品或城市的受控临时分组指标。分组与筛选均使用后端白名单和固定聚合模板；不合法维度会明确拒绝查询。此类结果若超过展示上限，允许提供受保护的完整 CSV。

### 6.5 规则与知识问答

28. [P0] 作为商家经营人员，我希望查询商品上架和审核规则，以便减少审核失败。
29. [P0] 作为商家经营人员，我希望查询交易、退货和客服规则，以便正确处理业务。（优惠券、赔付等更多业务域见 §7.2）
30. [P1] 作为平台运营人员，我希望维护业务流程、名词、表结构和指标文档，以便统一知识来源。
31. [P1] 作为平台运营人员，我希望知识修改具有版本信息，以便避免覆盖其他人的编辑。
32. [P0] 作为商家经营人员，我希望规则回答显示知识来源或更新时间，以便判断可信程度。

### 6.6 数据分析和行动建议

33. [P0] 作为商家负责人，我希望助手总结数据中的增长、下降和异常，以便快速判断问题。
34. [P0] 作为商家负责人，我希望每次分析至少得到两条建议，以便知道下一步做什么。
35. [P0] 作为商家负责人，我希望建议包含数据依据，以便判断建议是否合理。
36. [P0] 作为商家经营人员，我希望建议包含明确行动，以便直接执行。
37. [P0] 作为商家经营人员，我希望点击建议问题继续分析，以便形成连续决策链路。

### 6.7 图表

38. [P0] 作为商家经营人员，我希望趋势指标显示折线图，以便观察时间变化。
39. [P0] 作为商家经营人员，我希望分类指标显示柱状图或饼图，以便比较构成。
40. [P0] 作为商家经营人员，我希望在允许的图表类型之间切换，以便选择合适的视图。
41. [P0] 作为数据人员，我希望图表只能引用查询结果中的安全字段，以避免模型编造图表数据。

### 6.8 附件分析

### 6.9 质量、反馈和降级

## 7. Functional Scope

## 8. Answer Modes

| 模式 | 阶段 | 说明 | 数据查询 | 图表 | 建议 |
| --- | --- | --- | ---: | ---: | ---: |
| `METRIC` | P0 | 指标、趋势、聚合分析 | 是 | 通常有 | 至少两条 |
| `DETAIL` | P0 | 业务明细和导出；纯明细正文必须为空，要求分析时才给建议 | 是 | 可选 | 仅要求分析时至少两条 |
| `RULE` | P0 | 业务规则与知识问答 | 否 | 否 | 可有 |
| `IDENTITY` | P0 | 商家资料 | 是 | 否 | 可选 |
| `CHAT` | P0 | 问候和普通交流 | 否 | 否 | 否 |
| `INVALID` | P0 | 危险请求或无法处理的问题 | 否 | 否 | 否 |
| `ATTACHMENT` | P1 | 附件分析 | 按需 | 可选 | 至少两条 |

**越权请求不进入本枚举。** 请求越权访问其他商家数据时返回 HTTP `403` 并写审计日志，因为它是安全事件，需要独立的响应语义和可告警的日志路径。

**限流与预算熔断同样不进入本枚举**，它们是传输层保护而非回答：超出限流返回 `429` 与 `RATE_LIMITED`；超出每日预算时，若已有可用数据则返回 `200` 加显式降级回答，若无法作答则返回 `503` 与 `LLM_BUDGET_EXCEEDED`。

`INVALID` 只覆盖两类情况，均返回正常 `200` 响应：

- **危险请求**：要求修改订单、商品、优惠券或资金数据等本系统不执行的操作；
- **无法处理**：超出能力范围或无法映射到受控查询计划的问题。

这两类是正常业务回答而非错误，需要进入会话历史，并可参与反馈和质量统计。

## 9. Core User Flows

### 9.1 指标问答 [P0]

```text
提问
→ 验证 Token 与会话
→ 识别 METRIC 意图
→ 检索指标口径
→ 校验指标、维度和日期
→ 安全查询
→ 生成回答、图表和建议
→ Reviewer 对比数据和结论
→ 返回并保存
```

### 9.2 明细问答 [P0]

```text
提问
→ 识别 DETAIL 意图
→ 路由到业务域
→ 强制商家过滤和行数限制
→ 返回预览
→ 需要时生成完整 CSV
→ 返回导出地址
```

### 9.3 规则问答 [P0]

```text
提问
→ 识别 RULE 意图
→ 检索团队知识
→ 必要时检索商家记忆（P1）
→ 组织有来源的回答
→ 知识缺失时显式说明
```

### 9.4 附件问答 [P1]

```text
上传
→ 类型、大小、数量和权限检查
→ 保存对象存储
→ 提取不可信正文
→ 发送问题时引用附件 ID
→ 结合附件和经营数据分析
```

## 10. Implementation Decisions

### 10.1 总体架构

- 前端采用 Vue 3 + TypeScript + Vite；
- 后端采用 Python 3.12 + FastAPI；
- 第一阶段主数据库采用 PostgreSQL；
- 前后端保存在同一 Monorepo，但作为 Railway 独立服务部署；
- Redis、Worker、对象存储和 Doris 均按阶段引入；
- 前端 API 类型优先从 FastAPI OpenAPI 生成；
- 前端不直接持有数据库或 LLM 凭证；
- MVP 商家认证采用**演示 Token 白名单**：Railway Variables 预置演示商家的 Token，请求通过 `Authorization: Bearer <token>` 携带，服务端解析出可信商家身份。不建用户表、不做密码登录。该方案仅适用于演示环境，上生产前必须替换为签名令牌或企业认证。

### 10.1.1 LLM 提供商与模型

- 云端 LLM 统一使用 DeepSeek 的 OpenAI 兼容 Chat Completions API，`LLM_BASE_URL` 固定为 `https://api.deepseek.com`；
- MVP 默认模型是 `deepseek-v4-flash`，用于意图识别、回答组织与 Reviewer。它满足本项目以结构化查询结果为依据的 Agent 流程，并优先保障首个 SSE `step` 的响应速度与成本边界；
- `deepseek-v4-pro` 可在完成费用评估、真实模型离线验收和配置复核后，通过 `LLM_MODEL` 替换为升级选项；MVP 不引入双模型路由；
- 不得配置已于 2026-07-24 弃用的 `deepseek-chat`、`deepseek-reasoner`；模型可用性和价格以 [DeepSeek 官方模型与价格页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/) 为准；
- `LLM_API_KEY` 是 DeepSeek API Key，仍只能由环境变量或 Railway Variables 提供；任何真实调用仍须遵守本 PRD 与 `AGENTS.md` 的费用确认、限流、单请求上限和每日预算熔断要求。

### 10.2 Deep Modules

以下模块应保持稳定、接口简单并可独立测试：

1. **Merchant Context**
   - 从请求的 `Authorization` Bearer Token 解析可信商家身份；
   - **Token 到 `merchant_id` 的解析、授权映射和有效性校验完全由服务端控制，前端不能通过传递 `merchant_id` 改变身份。演示环境前端可以从受控的 `/api/demo/merchants` 取得权限受限的演示 Token，但不能自行构造其他有效 Token**；
   - 为所有数据库请求提供可信 `merchant_id`；
   - **永不接受请求体、查询参数或请求头中由前端指定的 `merchant_id`**；
   - 商家切换只能通过更换 Token 实现，切换结果仍由服务端解析决定。

   演示 Token 的边界（缺一不可）：

   - 演示接口必须可以通过配置关闭；
   - 生产环境必须关闭；
   - 演示 Token 只能访问演示数据，不授予任何管理或跨商家权限；
   - 真实商家认证上线前必须替换为签名令牌或企业认证。

   注意区分两件事：**"前端不能控制授权映射"是安全要求，"前端不能看到凭证"不是**。演示 Token 在演示环境本来就要下发到浏览器，安全性来自它的权限范围有限且可随时关闭，不来自它不可见。

2. **Intent Contract**
   - 定义模型允许输出的模式、指标、维度、筛选和日期；
   - 使用严格枚举、白名单和 Pydantic 校验；
   - 指标白名单使用英文 `metric_code` 枚举，不使用中文指标名，以避免模型输出的中文变体造成漏命中；
   - 非法输出不进入查询层。

3. **Safe Analytics Query**
   - 接收经过校验的查询计划；
   - 使用固定模板、绑定参数和商家过滤；
   - 返回统一的列、行、总数和截断状态；
   - 不暴露任意 SQL 接口。

4. **Metric Catalog**
   - 每个指标具有稳定的英文标识 `metric_code`，中文名仅作展示字段 `display_name`；
   - 按正式指标资产、数据库注释、生成口径的优先级三级检索，前一级未命中才降到下一级；
   - 每一级都必须同时产出**业务口径**与 **SQL 口径**两项；
   - 明确来源、负责人、状态和待核验提示；
   - 不把生成口径标记为正式口径。

   三级检索的口径来源与降级语义（对齐参考项目 `MetricDefinitionService.resolve`）：

   | 级别 | 命中条件 | 业务口径来自 | SQL 口径来自 | `source` | `generated` |
   | --- | --- | --- | --- | --- | --- |
   | 一级 · 正式指标目录 | `metric_code` 命中目录 | 目录字段 | 目录字段 | `METRIC_CATALOG` | `false` |
   | 二级 · 受控字段注释 | 目录未命中但字段注释白名单存在 | 字段注释原文 | **后端按模板拼装**的说明句 | `FIELD_COMMENT` | `false` |
   | 三级 · 模型生成 | 前两级均未命中 | 模型输出 | 模型输出 | `AI_GENERATED` | `true` |

   二级的 SQL 口径由后端确定性拼装（例如「按商家和业务日期过滤后，对 `X` 求和」），
   **不交给模型**；三级交给模型时，提示词必须约束「不得声称这是正式口径，不得编造表字段」，
   且模型输出的是自然语言计算逻辑说明，**不是可执行 SQL**——这与 R4 一致，口径面板是给人
   阅读的解释文本，不构成查询入口。三级还必须有硬编码兜底文案，模型不可用时口径不为空。

   `generated` 为 `true` 时必须同时返回待核验提示文案（`notice`），由前端渲染为醒目告警。
   `generated` 是独立布尔字段，不得让前端从 `status` 或 `source` 的字符串里反推。

5. **Knowledge Retrieval**
   - 团队知识优先，商家记忆其次；
   - 团队知识只允许管理员写入；
   - 记忆必须按商家隔离。

6. **Answer Composition**
   - 接收结构化查询结果和知识；
   - 输出回答、经营建议和图表描述；
   - **不生成推荐问题**："猜你想问"由服务端预置配置提供，见 §11.3；
   - 非加和指标禁止错误求和。

7. **Answer Review**
   - 独立比较问题、数据和候选回答；
   - 只返回是否通过和问题列表；
   - 最大重试次数固定；
   - 无法校验时显式降级。

8. **Attachment Extraction**
   - 统一图片、PDF、Excel 和 CSV；
   - 输出规范化文本、表格摘要和安全提示；
   - 附件正文永远视为不可信数据。

### 10.3 数据库

- PostgreSQL 同时承担业务记录、会话、知识和 MVP 分析数据；
- ORM 模型与外部 API Schema 分开；
- 所有表使用迁移管理；
- 经营大表预留按日期和商家分区能力；
- Doris 不属于 MVP，只有容量和性能数据证明需要时才接入；
- MySQL 不作为新系统主数据库。

### 10.4 LLM 安全

- DeepSeek Adapter 只通过 `https://api.deepseek.com` 调用已配置的 `LLM_MODEL`，不得把 Key、完整提示词或完整经营数据写入日志；
- 模型不直接执行 SQL；
- 模型不决定可信商家身份；
- Prompt 中明确附件内容不具备指令优先级；
- 结构化输出失败时有限重试；
- 自动化测试使用确定性 Fake LLM；
- 降级结果不得伪装成真实模型理解。

### 10.5 前端交互

- 桌面端保持左中右三栏；
- 当前选中回答驱动左右侧栏；
- URL 路由区分助手与知识库；
- 图表只消费后端提供的结构化数据；
- 附件先上传获得 ID，再随聊天请求发送；
- 错误、降级和质量状态必须可见；
- Prototype 是视觉基准，不直接作为生产代码使用。

### 10.6 Railway

- Frontend、Backend、PostgreSQL 分别为独立服务；
- Worker 和 Redis 在 P1 增加；
- Backend 提供轻量健康检查；
- 普通容器文件系统不保存长期文件；
- 数据库迁移只由单一发布步骤执行；
- 所有服务通过 Railway Variables 配置。

## 11. API Contract Summary

### 11.1 MVP API

本节的路径是**唯一权威来源**。`AGENTS.md` §十和前后端开发计划都必须与本表逐项一致，任何一处修改都要同步全部四份文档和契约测试。

除 `/api/health`、`/api/ready` 和 `/api/demo/merchants` 外，所有接口都必须携带 `Authorization: Bearer <token>`，服务端由此解析可信商家身份。

| 方法 | 接口 | 用途 |
| --- | --- | --- |
| `POST` | `/api/chat` | 发起一轮问答，默认 SSE 流式，见 §11.4 |
| `GET` | `/api/conversations` | 会话列表 |
| `GET` | `/api/conversations/{id}` | 会话详情 |
| `DELETE` | `/api/conversations/{id}` | 删除会话 |
| `POST` | `/api/answers/{id}/feedback` | 采纳、点赞和点踩 |
| `GET` | `/api/exports/{id}` | 下载导出文件 |
| `GET` | `/api/metrics/{code}` | 获取指标口径，路径参数为 `metric_code` |
| `GET` | `/api/demo/merchants` | 演示商家列表与对应 Token，供商家切换器使用 |
| `GET` | `/api/health` | 健康检查，不查库、不调 LLM |
| `GET` | `/api/ready` | 可选，数据库 readiness 探针 |
| `GET` | `/api/admin/ops/status` | 运维状态：预算余量、限流命中、降级计数。**需要 `ADMIN_TOKEN`**，未配置时端点关闭 |

`/api/admin/ops/status` 是 §14.2 费用防护的观察窗口，因此属于 P0。它禁止返回任何 Token、Prompt、商家经营数据或完整请求正文，商家标识以脱敏形式返回。

`/api/demo/merchants` **仅用于演示环境，必须可通过配置关闭，生产环境禁用**。演示 Token 只授予对演示数据的访问权，不属于 §16 中"LLM 密钥和数据库连接串不得进入代码和构建产物"这一条所指的真实密钥；真实密钥仍只保存在 Railway Variables 中。

商家记忆必须对商家**可查、可纠错、可删除**，否则它就是不可审查的黑盒。这三条接口用商家 Token，管理员不替商家修改记忆。

`/api/admin/*` 使用独立请求头 `X-Admin-Token`（值为 `ADMIN_TOKEN`），不复用 `Authorization`；`/api/exports/{id}` 用自带签名的 URL，不要求请求头，以便浏览器原生下载。

### 11.3 Chat Response 字段

本节定义**产品级语义**：有哪些信息、什么时候必须存在。精确的 JSON 键名、类型和可空性由 `docs/backend-development-plan.md` §8 定义，实现后以 FastAPI 生成的 OpenAPI 为最终来源。三处不得各写一套。

响应是单一扁平结构。字段分为两组：**始终必填**的键在任何模式下都存在，**按模式必填**的键只在对应模式下存在。

#### 始终必填

键必须存在，值可为 `null`。

- 回答 ID 和会话 ID；
- 回答文本与回答模式；
- 业务分类；
- 思考或执行步骤；
- Reviewer 状态、尝试次数和备注；
- 分析来源；
- 是否降级和降级原因（未降级时降级原因为 `null`）；
- 推荐问题及其备选组。

**Reviewer 状态枚举：`PASSED`、`DEGRADED`、`FAILED`、`NOT_RUN`。**

状态只表达**最终质量结果**，不表达执行过程。重试次数由单独的尝试次数字段承载：

| 实际发生 | 状态 | 尝试次数 |
| --- | --- | --- |
| 一次通过 | `PASSED` | 1 |
| 重试后通过 | `PASSED` | 2 |
| 重试后仍失败 | `FAILED` | 2 |
| 校验后降级返回 | `DEGRADED` | 1 或 2 |
| 未执行校验 | `NOT_RUN` | 0 |

**Reviewer 最大尝试次数为 2**（`MAX_REVIEW_ATTEMPTS=2`），即最多重试一次。

**分析来源是有序数组**，按贡献度排序，主要来源在前。一次回答同时使用数据库和指标知识时如实返回两项，不做二选一：

```text
["DATABASE", "KNOWLEDGE"]      # 查了数据 + 引用了口径
["ATTACHMENT", "DATABASE"]     # 附件 + 经营数据联合分析
["FALLBACK"]                   # 降级，此时 degraded 必须为 true
["NONE"]                       # 本来就没有来源：CHAT 问候、INVALID 拒绝
```

`NONE` 是必需的：`CHAT` 和 `INVALID` 既没查库也没引知识，若枚举里没有它，"至少一项"的约束会逼实现给普通聊天硬塞一个来源，那是编造的出处，违反降级可见原则。`NONE` 只能单独出现，且不代表降级。

#### 按模式必填

| 字段 | 适用模式 |
| --- | --- |
| 查询计划摘要 | `METRIC`、`DETAIL`、`IDENTITY` |
| 指标标识、展示名、单位、**业务口径**、来源、负责人、状态和是否生成 | `METRIC` |
| **SQL 口径**、维度集合、来源库表、关联报表链接 | `METRIC` 可选，缺失时前端隐藏对应分区 |
| 待核验提示文案 | 「是否生成」为 `true` 时必填 |
| 数据行、总行数和截断状态 | `METRIC`、`DETAIL`、`IDENTITY` |
| 导出信息 | `DETAIL`；以及结果被截断的受控临时 `METRIC` |
| 图表定义 | `METRIC` 必填；`DETAIL`、`ATTACHMENT` 可选 |
| 至少两条经营建议 | `METRIC`、要求分析的 `DETAIL`、`ATTACHMENT` |

会话详情中的助手轮次必须能回放回答模式、执行步骤、质量状态、当前反馈状态和表格元数据；它不返回完整历史明细行或已过期的签名导出链接。精确字段与脱敏规则由后端计划 §8 定义。

不适用的模式下，这些键可以缺省或为 `null`。据此生成的数据模型不得把它们设为无条件必填，否则 `CHAT` 等模式的正常响应会校验失败。

#### 推荐问题的来源

推荐问题（"猜你想问"）**全部来自服务端预置配置，不由模型生成**。

- 服务端按业务域分组维护推荐问题，每个业务域下有多组候选；
- 响应返回当前业务域对应的一组，并把该业务域的其余候选组一并带回；
- 前端"换一换"在已返回的候选组之间本地轮换，不发额外请求；
- `CHAT` 模式返回入门问题组，用于让新用户了解助手能做什么。

这样做有三个原因：推荐问题必须落在指标白名单之内，预置池天然不会越界；缩小模型的结构化输出，减少解析失败来源；"换一换"零延迟。

**经营建议不在此列。** 建议（至少两条）仍由模型基于查询结果生成并受 Reviewer 校验，不可预置。

### 11.4 Chat 传输协议

`POST /api/chat` **默认返回 SSE 流**。这不是可选优化：§14.3 要求 1 秒内显示真实处理状态，而一轮完整问答通常需要 10 秒以上，只实现普通 JSON 无法满足该要求。

| 请求头 | 响应 |
| --- | --- |
| 默认（无 `Accept` 或 `Accept: text/event-stream`） | `Content-Type: text/event-stream`，逐步推送 |
| `Accept: application/json` | 一次性返回完整 `ChatResponse` |

事件类型固定为三种：

| 事件 | 时机 | 载荷 |
| --- | --- | --- |
| `step` | 每完成一个处理节点 | 步骤标签与节点标识，用于渲染"正在识别问题""正在查询经营数据" |
| `done` | 处理成功结束 | **与非流式 `ChatResponse` 完全一致的载荷** |
| `error` | 处理失败 | 与 `ErrorResponse` 一致的载荷 |

规则：

- `done` 或 `error` 必须是最后一个业务事件，两者互斥；
- 前端不得为流式和非流式维护两套解析逻辑，`done` 的载荷直接复用同一份类型；
- 幂等：请求携带 `client_request_id`，流中断后可凭同一 ID 取回已完成结果，不会重复计费；
- 自动化测试必须覆盖真实字节流解析，不能只测已解析好的对象。

完整线协议（事件命名、分块、心跳、取消语义、幂等状态机）见 `docs/backend-development-plan.md` §8.4，前端消费方式见 `docs/frontend-development-plan.md` §6.1。

- 所有经营表包含 `merchant_id`；

- 手机号、地址、证件号等字段默认脱敏；
- 查询结果存在最大行数和最大日期范围。

### 13.1 商家切换器

商家切换器是演示 Token 方案（见 §10.1）新增的控件，**Prototype 中不存在**，因此不属于"1:1 还原"的比对范围。

它的形态**按 Prototype 现有的 560px 断点切换**：

- **> 560px**：顶栏右侧操作区最左侧的独立按钮，与知识库、新会话同一视觉族（高 36px、圆角 10px）。品牌区不动，副行的产品说明保留。
- **≤ 560px**：移入品牌标题下方的副行。Prototype 在该断点本就隐藏这行产品说明，因此不占用新空间、不改动还原规则。

这样设计的原因是**当前商家名必须在任何视口下都常驻可见**——这个控件唯一的用途是让人当场确认"我现在是这个商家，取不到其他商家的数据"。纯右侧按钮方案在窄屏要把商家名折叠成图标，纯副行方案在宽屏要拿掉产品说明，两者都会破坏这个前提。

约束：

- 切换商家的语义是**更换请求携带的 Token**，商家身份仍由服务端解析决定；
- 切换后必须清空当前会话与侧栏，避免跨商家串数据；
- 不引入 560px 之外的新断点。

## 14. Non-Functional Requirements

### 14.1 安全

- 商家隔离必须在服务端完成；
- SQL 参数绑定覆盖率 100%；
- 不提供通用 SQL 执行接口；
- 文件上传检查类型、大小、数量和权限；
- 管理员知识写入需要单独权限；
- 日志和模型输入进行敏感字段脱敏；
- 导出和附件链接使用签名 URL，有效期 15 分钟，并校验权限；
- Backend 公开部署，CORS 只允许 Frontend 的精确 Origin，不使用 `*`；
- 来源 IP 只取自 Railway 代理注入的转发头，不直接采信客户端提供的 `X-Forwarded-For`。

### 14.2 LLM 费用防护

公开部署 + 免鉴权演示接口 + 可获取的演示 Token + 后端真实 LLM Key 的组合，意味着任何访问者都可能重复调用聊天接口并产生真实费用。以下为 **P0 要求**：

| 防护 | 要求 |
| --- | --- |
| 单请求最大模型调用次数 | 可配置上限，超出显式降级而非继续调用 |
| 单请求最大 token 数 | 可配置上限，超出显式降级 |
| 每日 token 预算熔断 | 按日累计，达到预算后拒绝新的模型调用并返回 `LLM_BUDGET_EXCEEDED` |
| 基础限流 | 进程内，按 Token 与可信来源 IP，超出返回 `RATE_LIMITED` |
| 用量记录 | 每次调用写入 `llm_usage`，记录次数与 token |

预算扣减必须是原子操作，不能出现多个并发请求同时读到"预算仍足够"后全部继续调用。

**仅记录用量不能阻止费用继续发生。** 未配置单请求上限、每日预算熔断和基础限流时，不得将真实 LLM Key 部署到公开地址。

Redis 分布式限流、多实例精确配额、告警和运维管理界面属于 P1/P2。

### 14.3 性能

性能目标在下列**基准环境**下测量，脱离该环境的数字不作为验收依据：

| 项 | 取值 |
| --- | --- |
| 部署环境 | Railway Hobby 规格的 Backend 服务 + Railway PostgreSQL |
| 数据规模 | §12.1 的演示数据集：3 个商家 × 180 天，订单约 5 万行、订单项约 12 万行、退款与退货各约 5 千行、工单约 3 千行 |
| 并发测试 | 10 个并发会话，持续 3 分钟 |
| 请求超时阈值 | 非 LLM 接口 5 秒，聊天接口总超时 60 秒 |

目标：

- 健康检查响应小于 200ms；
- 不含 LLM 的普通 API 在基准环境下 P95 小于 500ms；
- 聊天请求 1 秒内推送第一个 `step` 事件（进入可见处理状态）；
- 明细默认最多返回 200 行预览；
- 单次查询最大日期范围 180 天，与 §12.1 的演示数据天数对齐；
- 并发测试期间无请求超过上表的超时阈值，错误率为 0；
- **图表单条序列最多 180 个数据点，多序列合计最多 720 个数据点**，超出时后端先按粒度聚合再返回；
- LLM 和外部服务设置连接、读取和总超时。

### 14.4 可靠性

- 数据库连接具备启动重试；
- LLM 失败进行有限重试或显式降级；
- Reviewer 不得无限循环；
- 异步任务具备幂等键；
- 数据库迁移可以在空库和已有数据环境执行；
- 服务重启后会话和正式数据不丢失。

### 14.5 可观测性

- 请求具备 trace/request ID；
- 记录回答模式、耗时、降级和错误类型；
- 不记录完整敏感问题、附件正文或查询结果；
- 区分应用错误、数据错误、模型错误和权限错误；
- Railway 日志可定位健康检查和启动失败。

16. 数据库或 LLM 失败时页面显示降级或错误；
17. 聊天请求 1 秒内推送第一个 SSE `step` 事件，`Accept: application/json` 可取得同一份完整响应；
18. **确定性路由回归通过率为 100%**（Fake LLM，CI 断言）；真实模型意图准确率 ≥ 90% 作为人工验收项单独记录，不进 CI；
19. **未配置单请求 LLM 上限、每日预算熔断和基础限流时，不得将真实 LLM Key 部署到公开地址**；超出限流返回 `RATE_LIMITED`，超出预算返回 `LLM_BUDGET_EXCEEDED` 并显式降级；

21. 后端单元测试和 API 测试通过；
22. 前端组件测试和核心 Playwright 测试通过；
23. 自动化测试没有真实 LLM 调用；
24. Railway 健康检查通过；
25. LLM 密钥和数据库连接串未进入代码和构建产物；
26. 部署文档可以让新的 coding agent 重复完成部署。

## 18. Risks and Mitigations

| 风险 | 缓解方案 |
| --- | --- |
| 模型理解错误 | 严格意图 Schema、白名单、Reviewer 和显式降级 |
| 模型编造数字 | 回答只引用结构化查询结果，Reviewer 对比数据 |
| 越权查询 | Merchant Context、服务端商家注入、越权返回 403 并审计、多商家测试 |
| 演示 Token 被带入生产 | Token 只授予演示数据访问权；`/api/demo/merchants` 可配置关闭且生产禁用；上生产前必须替换为签名令牌或企业认证 |
| 查询成本过高 | 日期限制、行数限制、索引、超时和查询模板 |
| 知识过期 | 版本、来源、负责人、更新时间和管理员维护 |
| 附件提示词注入 | 附件正文标记为不可信数据，禁止改变系统规则 |
| Railway 文件丢失 | PostgreSQL、对象存储或 Volume，不依赖临时磁盘 |
| LLM 费用失控 | P0 即具备单请求调用与 token 上限、每日预算原子熔断、基础限流、用量记录和超时；Fake 测试不产生费用；未配齐防护不得把真实 Key 部署到公开地址 |
| 公开演示地址被刷 | 演示接口可配置关闭、演示 Token 权限受限、按 Token 与可信来源 IP 限流、来源 IP 只取自 Railway 代理注入的转发头 |
| 初期架构过重 | MVP 只用 PostgreSQL，Redis/Doris 按证据增加 |
| 前后端协议漂移 | OpenAPI 生成 TypeScript 类型和契约测试 |
