# Borough — a two-sided commerce agent platform

> One backend, two agents. The **shopper agent** helps customers find products, fill a cart and handle returns inside a store.
> The **merchant agent** answers business questions, runs inventory and content, and drafts changes for approval.
> Both share one set of identity, order, inventory and audit facts. The model interprets and picks tools;
> **amounts, stock, SQL and every write are decided by deterministic backend code.**

This is a personal engineering project. Its goal is to build out the parts of an agent application that usually get a
single sentence: a bounded tool loop, skills loaded on demand, context compaction, memory on both sides, hybrid retrieval,
an MCP entry point, and an **evaluation suite that is layered and reports its failures**.

`Borough` is a fictional commerce platform. The three demo merchants and all business data are generated by code.

## At a glance

| Topic | Approach | Evidence |
| --- | --- | --- |
| Agent loop | A purpose-built tool loop with hard caps on turns, tool calls, model calls and tokens; hitting a cap produces a visible degradation | At most 8 decision rounds / 16 tool calls / 12 model calls per turn |
| Tools and skills | 26 tools split into role-specific tool surfaces; 12 skills (5 shopper, 7 merchant) loaded on demand instead of living in the prompt | First skill choice correct in 46/48 (real model) |
| Writes | Every merchant write starts as a **draft**, is approved by a person in the approval screen, and is re-checked against current state when applied; saying "approve" in chat does nothing | Concurrent approvals have one winner; repeat approvals have no second effect (deterministic tests) |
| Retrieval | Keyword + vector (pgvector, local `bge-small-zh-v1.5`) fused with RRF; versioned index, atomic switch, no switch if quality regresses | Recall@5 0.759 → **0.907**; citation accuracy 85.19% → **90.74%** |
| Memory | Extracted asynchronously through an outbox after the turn; shopper and merchant memory are isolated, and memory **cannot** ground a number in an answer | 5% wrong-write rate (2/40); 0 leaks across 10 sensitive-information lures |
| Context compaction | Two strategies (tool-result pruning, summarisation) with identity, sources, draft versions and safety constraints kept as anchors | 100% structural retention (scripted model); with a real model only 13/24 kept their sources — **below target** |
| MCP | Read-only MCP server with its own short-lived, revocable credential scoped to one store and a set of tools | Integration test with a standard MCP client |
| Security | 79 security cases as a hard gate: cross-tenant access, identity forgery, SQL injection, prompt injection, model self-approval | 79/79; a skipped case does not count as a pass |
| Cost | Daily budgets at three levels (global / role / store), checked before the request is sent; versioned prices, cost recorded at write time | Zero upstream requests once a budget is exhausted |
| Regression | All automated tests use a scripted model and cost nothing | 4,700+ backend, 793 merchant app, 141 shopper app |

The failing numbers are in the table too. Full results, denominators and review notes are under [Evaluation](#evaluation).

## Capabilities

### Shopper app (Next.js)

- **Discovery to order**: search the store's products by need, compare, add to cart; stock is reserved when the order is placed, with demo payment and a 30-minute payment timeout;
- **After-sales**: return eligibility is decided by the backend from time limits, and a case is created only after the shopper confirms; return shipping, receipt and refund all leave event records;
- **Missing means missing**: when the merchant has not filled in an attribute, the assistant says so and raises a content-gap signal instead of inventing one;
- **Memory**: preferences are saved only after the shopper confirms, expire after 180 days without confirmation, and can be viewed or deleted at any time;
- **Guest and bound identity**: guests can browse and use the cart; orders, after-sales and memory require binding the demo shopper identity.

### Merchant app (Vue 3)

- **Business analysis**: metric queries, trends and breakdowns, five-step attribution; metric formulas and SQL come from backend templates;
- **Inventory**: low-stock alerts feed the daily brief, restocking goes through draft approval, and stock has an event ledger it can be rebuilt from;
- **Content and promotion**: content gap → drafted addition → approval; coupons are guarded by a maximum discount;
- **Service and after-sales**: view cases and draft decisions; shoppers appear only under a store-scoped pseudonym;
- **Definitions Q&A**: retrieves metric definitions and platform rules, answers with citations and states the definition version;
- **Detail export**: CSV through an HMAC-signed URL that expires in 15 minutes, with formula-injection protection.

### Platform

- **Read-only MCP entry**: an external MCP client gets the same numbers as the workspace through a scoped credential;
- **Knowledge admin**: document maintenance, `If-Match` optimistic locking, visible index status;
- **Operations dashboard**: budgets, cost, rate limiting, degradation, route p95 and a Chat BI overview;
- **Chinese and English**: UI, API responses and answer language follow the display language.

Key points:

- **Identity is resolved only from the server-side session.** `merchant_id` and `buyer_key` are never taken from the client or
  the model. Shopper and merchant sessions are not interchangeable; any cross-role, cross-merchant or cross-shopper access
  returns 403 and is audited, and "does not exist" looks exactly like "not yours";
- **The model's tool surface is trimmed by role.** The shopper-side model can only change cart quantities; placing, paying for
  and cancelling an order are UI actions that are not tools at all;
- **The frontends do not proxy the API.** Both call the backend's public address directly, CORS allows exactly two origins, and
  a missing backend address fails loudly;
- **Types flow one way**: `OpenAPI → generated.ts → adapter → domain types → store → component`. The generated file is never
  edited by hand; `codegen:check` enforces that.

## How one turn runs

```text
trusted session identity and role tool surface
  → zero-LLM safety and permission gates
  → load trusted skills and retrieval context on demand
  → tool loop bounded by turns, tool calls, LLM calls, time and tokens
  → deterministic backend queries, calculations and write re-checks
  → shopper confirms in the UI, or merchant approves in the approval screen
  → answer, citations, degradation and quality information
  → asynchronous memory extraction
```

A few design decisions worth spelling out:

**Tool results are untrusted input.** Text returned by tools is wrapped in fences carrying a random identifier before the model
sees it, and "instructions" inside a fence are not instructions. Every number in an answer must be traceable to a tool result
from the same turn; otherwise the answer is held back for a rewrite or degraded. Memory recall tools are explicitly marked as
*not* a source for numbers — otherwise a remembered "net sales were about 500k last month" would let the same figure pass the check.

**Writes have three stages: draft, approve, apply.** The model only produces drafts (price change, coupon, restock, content
edit, after-sales decision). Approval happens in the UI and is bound to a draft version. Applying re-checks against *current*
stock and state, not the snapshot from drafting time. There is no path for the model to approve its own draft.

**What compaction must keep.** In long turns, older tool results are pruned or summarised. Identity, data source and
as-of time, metric definition version, draft version and safety constraints are kept verbatim as anchors; trusted skills are
never compacted.

**Memory goes through an outbox.** A successful turn writes one outbox row; a scheduled job does the extraction, with
idempotency, `SKIP LOCKED`, leases and a retry cap. Extraction only reads what the user said, sensitive content (health,
address, account numbers and the like) is filtered before writing, and guests are never queued.

**Switching an index is one pointer.** Knowledge indexes are built as versions and switched by updating a pointer in a single
transaction. A new version whose Recall@5 falls below 95% of the previous one is not switched in; a failed build keeps the old
version and marks it stale; with no usable version, retrieval falls back to keywords and says so in the answer's sources.

**Degradation must be visible.** When the database, knowledge base or model is unavailable the system may degrade, but
sources, quality status and the reason are part of the API contract and rendered in the UI. A rule-based fallback is never
dressed up as model analysis.

> The repository also keeps a 12-node LangGraph pipeline (`backend/app/agent/graph.py`). It is the previous, single-sided
> implementation, frozen since 2026-09-20 as a **read-only evaluation baseline** for comparison against the new tool loop.

## Evaluation

Results come in three layers that **cannot stand in for one another**:

| Layer | Runs on | What it shows |
| --- | --- | --- |
| Deterministic regression | Scripted model, free, in CI | Identity, gates, tool paths, state transitions and degradation labels behave as designed |
| Exploratory real runs | Real model, criteria not frozen | Finds problems; never used for a selection or an acceptance decision |
| Real evaluation | Real model, with samples and scoring frozen and hashed beforehand, and calls metered against a ledger and a cap | Answer quality |

Datasets: a main set of 104 cases (79 security, 25 quality; 49 shopper, 55 merchant; 74 Chinese, 30 English), plus
dedicated sets — 64 for RAG, 40 for memory extraction and 30 long conversations for compaction.

Real-model results (DeepSeek `deepseek-flash`, October 2026):

| Item | Result | Notes |
| --- | --- | --- |
| Hybrid retrieval Recall@5 / MRR | 0.759 → **0.907** / 0.639 → **0.802** | Against the keyword baseline; refusal rate unchanged at 0.90. Embeddings run locally at no model cost |
| RAG citation accuracy | 85.19% → **90.74%** | Faithfulness 98.15%, honest refusal 100%; 7 of the 9 failures are a retrieval miss followed by an honest refusal |
| New loop vs frozen baseline | **6/6** vs 1/6 | Both generations on the six legacy capabilities they share |
| First skill choice | 46/48 | Two cases asked a clarifying question first |
| Memory wrong-write rate | 5% (2/40) | Both from one multi-sentence correction case; 0 leaks across 10 sensitive lures |
| v2 quality scenarios | **16/19** | 15/19 on a case-by-case human read, 16/19 after fixes and a targeted re-run; the automated judge also said 16/19, but two of the cases it passed were actually wrong |
| Source retention after compaction | 13/24 | **Below target**: after compaction neither strategy fully restores source, as-of time and definition version |

Things the evaluation taught:

- **An automated judge cannot tell whether a fact is right.** Some of the cases it passed were wrong, so a judge verdict is
  never the sole basis for a pass, and whatever code can decide (language consistency, for one) is decided by code;
- **A scripted model hides a whole class of defects.** It returns pre-written valid output, so whether the prompt actually
  tells the model what to produce is invisible to automated tests. Prompt changes therefore come with a contract test that
  derives its expectations from the schema;
- **A real model fails differently.** It did not know today's date, it treated the English duration "30 days" as an
  ungrounded number, and a free-string tool argument with a wrong value silently returned zero rows.

Reports and raw records are in [`docs/history/eval/`](docs/history/eval/) (in Chinese); the summary is
[`n5-full-report.md`](docs/history/eval/n5-full-report.md).

## Security and cost

| Risk | Design |
| --- | --- |
| Model-written SQL | The model only emits a structured intent validated by Pydantic; SQL comes from backend templates with allow-listed tables and columns, bound values, and enforced date ranges and row limits |
| Cross-merchant or cross-shopper access | Identity is resolved only from a verified session; every query is scoped to the merchant, shopper data additionally to `buyer_key`; violations return 403 and are audited |
| Leaking whether an object exists | "Not found" and "forbidden" share one error shape; a timing test guards the response-time gap across 500 requests of each kind on order detail |
| Prompt injection | Tool results and retrieved content are fenced; the model cannot decide amounts, stock changes or approvals |
| Model self-approval | Approval happens only in the UI, bound to a draft version, with a re-check against current state on apply |
| Token abuse | Per-session rate limiting, per-request call and token caps, and three-level daily budget breakers checked before the request is sent |
| Mixing admin and merchant credentials | Merchants use `X-Session-Id`; admin routes accept only `X-Admin-Token` and are not mounted at all when no admin token is configured |
| Degradation passed off as a normal answer | Sources, quality status and degradation reason are in the contract and rendered |
| Secrets in code | Everything comes from environment variables; build output is scanned by `secrets:check` |

## Tech stack

**Backend** — Python 3.12 · FastAPI · Pydantic v2 · SQLAlchemy 2 (async) · Alembic · psycopg · MCP SDK · fastembed (ONNX) ·
structlog · pytest · Ruff · mypy

**Shopper app** — Next.js 16 · React 19 · TypeScript · Vitest · Playwright

**Merchant app** — Vue 3 · TypeScript · Vite · Pinia · Vue Router · vue-i18n · ECharts · Vitest · Playwright

**Data and infrastructure** — PostgreSQL 16 + pgvector · Docker · Caddy · Railway

**Model** — DeepSeek `deepseek-flash`, through an in-house `LlmClient` with adapters for both the OpenAI-compatible and the
Anthropic-compatible protocol

The overall approach to skills and the tool loop draws on Anthropic's
[commerce-agents](https://github.com/anthropics/commerce-agents) blueprint (Apache-2.0). The domain model, contracts, security
boundaries and evaluation are designed and implemented in this project.

## Quick start

### Option 1: the full stack with Docker Compose

Requires Docker. The first build downloads the embedding model (about 95 MB).

```powershell
git clone https://github.com/XuZiHan-010/shopping_assistant.git
cd shopping_assistant

docker compose up -d postgres
docker compose exec postgres createdb -U borough borough_compose_demo
$env:COMPOSE_DB_NAME = "borough_compose_demo"
docker compose up -d --build
```

Then load the demo data (requires Python 3.12 and [uv](https://github.com/astral-sh/uv)):

```powershell
cd backend
uv sync
$env:DATABASE_URL = "postgresql+psycopg://borough:borough_local@127.0.0.1:55432/borough_compose_demo"
uv run python ../scripts/seed_demo_data.py --seed                    # three demo merchants
uv run python -m scripts.seed_demo_analytics --force-full-rebuild    # 180 days of business data
uv run python -m scripts.seed_demo_scenarios --seed                  # scenario data for both apps
```

Open the merchant app at <http://localhost:5173> and use "Customer view" in the sidebar to reach the shopper app
(<http://localhost:3000>). Without `LLM_API_KEY` the assistant shows a **visible degradation notice**; every UI action
(cart, order, payment, approval, after-sales, dashboards) still works.

## Tests and quality gates

All automated tests **use a scripted model and incur no model cost**.

```powershell
# Backend
cd backend
uv run ruff check . ; uv run mypy app
$env:REQUIRE_INTEGRATION_DB = "1"; uv run pytest      # integration tests need a real PostgreSQL and fail hard without one

# Merchant app
cd frontend
npm run lint ; npm run typecheck ; npm run test
npm run codegen:check       # is generated.ts in sync with OpenAPI
npm run test:e2e            # Playwright against a mock API

# Shopper app
cd shop
npm run lint ; npm run typecheck ; npm run test
npm run codegen:check ; npm run tokens:check
```

Latest recorded results: backend full suite **4747 passed / 3 skipped / 0 failed**, merchant app **793 passed**,
shopper app **141 passed** (2026-10-08; backend on real PostgreSQL + pgvector; the 3 skips are symlink tests that need a privilege Windows does not grant).

Constraints that came out of experience:

- Integration tests run on real PostgreSQL, not SQLite — tenant isolation, migrations, concurrency and timing are all verified there;
- Security cases are a hard gate: an unreachable database or a skipped case fails the gate rather than quietly running less;
- Green gates do not mean correct behaviour: any parameter that "should carry a value but was passed empty" needs a test that asserts on the input.

## Deployment

The target topology is four Railway services plus an external PostgreSQL:

| Service | Directory | Notes |
| --- | --- | --- |
| `merchant` | `/frontend` | Vue static build served by Caddy; does not proxy `/api` |
| `backend` | `/backend` | FastAPI; database migrations run once in the release phase |
| `shop` | `/shop` | Next.js standalone |
| `cron` | `/backend` | Runs the dispatcher every 5 minutes: order timeouts, draft expiry, memory extraction, index rebuilds, demo data rolling |

Configuration as code lives in each directory's `railway.json` and in `backend/railway.cron.json`; steps and environment
variables are in [`docs/deployment.md`](docs/deployment.md) (in Chinese). Before a real model key goes onto a public
deployment, rate limiting, the per-request cap and the daily budget breaker are verified on the public domain.

Running only `merchant` and `backend` also works: the merchant workspace is fully usable, the "Customer view" entry is
hidden, and scheduled jobs do not run on their own.

## Status and known limitations

The project is delivered in five milestones, N1–N5. Acceptance checks for N1–N4 are complete (with open defects); N5 is
implemented locally and its overall acceptance is not yet closed. Known and unresolved:

- **The after-sales scenario has not yet run end to end with a real model**: the default compaction strategy prunes tool
  results that are still needed later in the same turn;
- An answer can come back empty when the tool-call cap is reached;
- Shopper product search is not cross-lingual: English keywords do not find Chinese products;
- Memory extraction mis-extracts a superseded fragment in one phrasing, the multi-sentence correction;
- The after-sales documents in the platform rules library are thin, which limits what rule answers can cite;
- The budget breaker reserves a conservative estimate, so a single call can still slightly exceed the daily cap when
  upstream usage is higher than the reservation;
- Performance benchmarks, confidence intervals for a randomised attack set, and judge-versus-human calibration have not been run.

Demo boundaries: the demo merchant and shopper are not real logins; payment and refund are simulated; attachments, OCR, a
real user system, product variants and MCP write tools are out of scope for this version.
